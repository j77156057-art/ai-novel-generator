# 设计稿：整段验收的 coverage 契约（要不要改、怎么改）

> **作者决定（2026-10-24）：契约不动。**
> 保留输出预算的缓解（按需申请额度），并把剩下的悬崖从**静默失败**改成
> **看得见的失败**：额度不够时 unresolved 记 `acceptance_output_truncated`，
> 报告里写明「正文 N 段 / 需回抄 N 个 id / 本次申请了多少 token 仍不够」。
> 本文保留作为将来正文真的长到那个程度时的备选方案。

## 1. 问题

整段验收要求模型在响应里**逐个点名它核对过的正文段落**：

```json
"coverage": {"examined_source_ids": ["G1P001", "G1P002", ... 共 876 个], "complete": true, "reason": "..."}
```

输出量与段落数成正比。实测：

```text
五段正文 876 段 → 回抄约 9.5KB → 撞 max_tokens=4096 被拦腰截断
→ 响应不是合法 JSON → 验收 fail closed（acceptance_failed）
```

模型端已经在做的事（回抄 876 个 id）**占掉了它 4096 token 里的绝大部分**，
真正要写判断的四个维度只剩几百 token。

**已做的缓解**（已提交）：验收按「必须回抄的 id 数量」申请输出额度
（`min(32768, max(4096, 2048 + n*12))`）。这把「输出不够」从「五段正文必现」
变成「正文再长 2～3 倍才会发生」。但悬崖还在。

## 2. 为什么这不只是「调大 max_tokens」

- 输出额度有模型侧上限（MiniMax-M3 有它自己的天花板），再大的正文仍会撞。
- 每一次验收都要模型回抄几万字 id：**慢、贵、且挤占真正要写判断的额度**。
- 更要命的是：**输出的绝大部分是机械复述**，对判定的质量没有贡献。

## 3. 三个可选方案

### 方案 A：改成「只列没核对的」（skipped-list）

模型输出：

```json
"coverage": {"skipped_source_ids": [], "complete": true, "reason": "逐段核对完成"}
```

服务端算 `examined = required − skipped`，**报告里仍然存 `examined_source_ids`**
（与现在同名字段）→ 下游接口（修复卡片、`pending_acceptance`、报告）**一个字不用改**。

- 输出量：**恒定**（通常 0～几条）→ 任意长度正文都不会截断，且验收更快更便宜。
- 校验：`skipped ⊆ sources`；`skipped` 非空 → `coverage_incomplete`（继续 fail closed）。
- **代价（真实的证据弱化）**：现在模型必须逐个点名它看过的段落，
  改后它只要不列 skipped 就「看起来全覆盖」。
  枚举本身是有成本的弱信号；改成「声明例外」就没有这个成本信号了。
  也就是说：一个偷懒的模型，现在会因覆盖不全被挡住，改后可能混过去。

### 方案 B：按块点名（chunk-boundary）

把正文按固定块（比如 20 段一块）切开，模型对每块只回一个 id
（它核对到的**该块最后一个段落 id**），服务端据此推断覆盖到哪：

```json
"coverage": {"covered_through": ["G1P020", "G1P040", ... 每块一个], "complete": true, "reason": "..."}
```

- 输出量：段落数 / 块大小（876 段 → 44 个 id ≈ 500 字节）→ 比现在小 20 倍。
- 保留了「模型必须走一遍并说出边界」的弱成本信号，比方案 A 强。
- **代价**：契约与校验逻辑要复杂一档（要按块校验「覆盖到 id」的前缀完整性），
  且模型若漏掉某块，服务端要能识别缺口（不是简单集合比较）。

### 方案 C：分段验收 + 服务端聚合

把整段验收拆成「每段（或每 N 段）一次模型调用」，各段自己回抄自己那一段的 id，
服务端聚合。

- 输出量：每次调用只回抄自己那段的 id（每段 ~176 个）→ 单次不撞上限，任意总长都行。
- **代价**：「整段验收」的意义正是**跨段一致性**（时间线、人物在场、物件状态跨段是否自洽）。
  拆开以后，跨段的那部分要么丢失，要么另做一次专门的跨段调用 —— 那其实是另一个设计。
- 保留跨段能力的做法：分段调用负责「逐段覆盖 + 段内四维」，再加**一次**跨段调用
  负责「段间一致性」（输入是各段的摘要 + 权威，输出很小）→ 两层证据。

## 4. 我的建议

**先不动契约。**理由：

1. 输出预算的缓解已经把悬崖推远；眼下没有正文长到那个程度。
2. 三个方案都各有代价，而**代价的取舍是作者该做的判断**（证据强度 vs 可扩展性）。
3. 若要动，我倾向 **方案 A + 保留维度引文作为证据锚点**：
   四个维度的 `source_ids` 本来就要求模型指出判断依据（supported 至少 1 个、
   contradicted 至少 2 个不同 id）—— 那是「模型真的看了正文」的证据；
   coverage 只负责「有没有哪几段没看」。两者分工清楚后，
   coverage 改成 skipped-list 的证据损失比看上去小。
   方案 B 更严谨但实现复杂一档，适合正文真的会长到几千段时再上。

## 5. 如果决定改，改动清单（供实施参考）

| 位置 | 改动 |
|------|------|
| `body_acceptance.ACCEPTANCE_SYSTEM` | coverage 那行改成 `skipped_source_ids` 的说法，并说明「全部核对过就是空数组」 |
| `body_acceptance.validate_acceptance` | 接受 `skipped_source_ids`；算 `examined = required − skipped`；返回的 coverage 仍带 `examined_source_ids`（保持下游接口） |
| `body_acceptance.run_body_acceptance` | 纠错重试的提示里同步 coverage 的字段名 |
| `tests/test_body_acceptance.py` | `_good_answer()` 的 coverage 形状；新增「模型必须列出未核对项」的断言 |
| 报告与 `pending_acceptance` | 形状不变（仍存 `examined_source_ids`），无需改 |

验收标准（必须同时满足）：

1. 876 段正文的验收响应**不再截断**（响应长度与段落数无关）。
2. `pending_acceptance.open_items` / 修复卡片 / 报告的字段与现在**逐字段一致**（除 coverage 的内部来源）。
3. 模型漏列某段时，验收**照样 fail closed**（`coverage_incomplete`）。
4. 既有回归脚本 252 项 0 失败；全量 `pytest tests/` 无新增失败。
