# 三类检索需求分开做

## 问题

用户指出：续写和角色聊天需要**次要人物**和**没被蒸馏进去的小事**，而蒸馏只抓主线和
主要人物。所以这两条链路必须检索原文。

实测当前状态（`probe_rag_state.py` / `probe_rag_diagnose.py`）：

| 问题 | 数据 |
|---|---|
| 检索分数无区分度 | top10 的 RRF 分全在 0.023-0.033，最大/最小 1.3x |
| 用用户自造人名检索 | 「沈砚跟周郎中走出破庙」→ 命中第 554/545/529 章，**全部无关** |
| 角色聊天完全不检索 | `PROFILE_RULES["roleplay"]["rag"] = False` |
| prompt 被无关原文占满 | k=4 × ~1100 字 = 4400 字，占 user prompt 70% |

## 根因诊断

拆开 RRF 看两路原始分（`probe_rag_diagnose.py`）：

```
「裴白 楚惊蛰 交手」
  章    bm25    vector     rrf
  357  17.51   0.2508   0.02773
  526  16.98   0.2467   0.02669   ← 真正的相关章
  204  18.48   0.2156   0.02620
```

**BM25 本身是有信号的**：全库 5323 chunk，bm25 中位 2.02、top 18.48，区分度 **9 倍**。
「酒肆说书」查询下，第 262 章得 24.7、第 966 章得 17.6，确实排在最前。

**问题出在 RRF 融合**：`1/(60+rank)` 只看排名不看分数，
24.7 分和 17.6 分都被当成「第 1 名 / 第 2 名」，融合后只差 6%。
而且两路 top1 往往不是同一块，各得一半权重，把相关性高的压了下去。

## 三类需求的性质不同（`probe_rag_strategies.py` 实测）

### A. 次要人物 → 按人名精确检索，用 BM25

「宋庭鹭」检索结果：

```
BM25:   881, 881, 777, 881     ← 都在她出场的章节
向量:   990, 990, 881, 881     ← 990 是全书最长章（8 万字），长文档偏置
```

三个名字（宋庭鹭/温华/红薯）测下来，BM25 全部稳定命中「这个人出现的章节」，
向量每次都会把第 990 章拉进来（那章太长，embedding 天然接近任何 query）。

### B. 闲笔/生活质感 → 按语义检索，用加权融合

query「几个人围着桌子吃饭，边吃边闲聊天」：

```
BM25:      571, 731, 412, 294
向量:      990, 412, 353, 290
加权 0.75: 412, 571, 731, 966   ← 966 是真正的酒楼说书段，被拉进来了
```

加权融合（BM25 0.75 + 向量 0.25，分数归一化后线性相加）把两路的好处都拿到了。

### C. 剧情衔接 → 按章节位置取，根本不用检索

写到第 N 章附近，直接按 `chapter_no` 取前后几块。实测第 300 章附近有 26 块可选，
全部是真正相邻的内容，比任何检索都可靠。

## 方案

### 1. 新增 `weighted_search`（保留 RRF 作为向后兼容）

`app/retrieval/search.py` 新增：

```python
def weighted_search(db, novel_id, query, k=6, w_bm25=0.75):
    """BM25 与向量按分数归一化后线性融合。

    ## 为什么不用 RRF

    RRF 只看排名（1/(60+rank)），丢掉绝对分数。实测同一查询下
    BM25 最高分 24.7、次高 17.6（差 40%），融合后只差 6%——
    区分度被压平，相关性高的块和擦边的块排在几乎一样的位置。

    归一化线性融合保留分数比例：bm25/max(bm25) 与 vector/max(vector)
    各占权重，直接相加。

    ## 权重 0.75

    中文关键词匹配（BM25）在「找这个人出现在哪」这类需求上远强于
    本地 embedding（实测人名检索向量版总是把最长章节排第一）。
    0.75/0.25 是「以关键词为主，语义补充」。
    """
```

### 2. 三种检索策略按用途分开

`app/retrieval/strategies.py`（新文件）：

```python
def retrieve_for_continuation(db, novel_id, chapter_hint, query, k=4) -> list[dict]:
    """续写：位置检索为主 + 语义检索补闲笔。

    位置：当前剧情位置前后 2 章的 chunk（保证情节衔接）
    语义：weighted_search 取 2 块（补「小事/闲笔」）

    返回带 role 标记，prompt 里分块渲染，让模型知道哪块是「紧接着的前文」、
    哪块是「参考语料里气氛相似的片段」。
    """

def retrieve_for_character(db, novel_id, character_name, k=6) -> list[dict]:
    """角色聊天：按人名做 BM25 精确检索。

    只取这个角色出现过的 chunk，按 bm25 排序。不用向量——
    实测向量检索会把全书最长章节排第一，跟角色无关。
    """
```

### 3. 角色聊天开启检索（改动 profile 规则）

`PROFILE_RULES["roleplay"]["rag"]` 从 `False` 改为 `"character"`：

原设计的理由是「角色不该知道相关剧情」——这个判断对**剧情**成立，
但对**角色自己的往事**不成立。角色聊天需要：

- 这个角色说过的原话（口头禅、语气）
- 这个角色的经历（见过谁、去过哪、发生过什么）
- 与对话者的关系史

这些都在原文里，且只跟这个角色有关。用 `retrieve_for_character`
定向检索，不会引入剧情走向。

### 4. 检索结果分块渲染，带来源标记

现在把 RAG 结果拼成一段纯文本塞进 prompt，模型不知道哪块是「前文」哪块是
「风格参考」。改为：

```
【前文衔接（紧接着当前剧情位置）】
<位置检索的结果>

【参考语料相关片段（同类场景的写法，仅供气氛参考）】
<语义检索的结果>
```

## 不做的事

- 不改 RRF 原有实现（有测试依赖，且它在「两路质量相当」时是合理的）
- 不引入外部向量模型（本地 embedding 够用，且换模型要重算 5323 条 embedding）
- 不为「次要人物」单独建表（原文 chunk 已经够，建表会引入同步问题）

## 验收

1. `test_retrieval_strategies.py`：
   - 人名检索只返回该角色出现过的 chunk
   - 位置检索返回连续章节
   - 加权融合的相关章排名优于 RRF
   - 角色聊天 profile 的 rag 不再是 False
2. 真实数据实测：三个次要人物各检索一次，命中章节必须含该人名
3. 续写 plan 预览里能看到分块渲染的两类上下文
