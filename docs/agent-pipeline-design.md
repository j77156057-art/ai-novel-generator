# 设计稿：助理 agent 编排的「交稿 → 全流程」工序链

> 目标（作者口径）：用户把一篇小说交给助理 agent，agent 自己分工推进：
> 清洗（错字/漏字/广告水印）→ 抽检审核 → 蒸馏 → 审查 → 决定采用还是修复 → 以此类推完成全流程。
> 审计 / 验收 / 定点修复 / 派生重建 / 解锁 / 扩展规划这些工序**不再让用户点按钮**，
> 由 agent 驱动，写操作仍走审批闸门。

## 2. 分层：读工序 / 写工序 / 编排

现有注册表有一条硬规则：**Assistant 工具必须 read_only=True，写工具按前缀拒绝**
（`FORBIDDEN_PREFIXES`）。这条不能为了「让 agent 自己干」而放松 ——
放松了，agent 就能自己把正文改了、把自己解锁了。所以分工是：

```text
读工序（agent 直接调，只读）
  清洗预览/抽样复查、抽检审核、闭环审计、验收状态读取、工序状态读取
      ↓ agent 据此判断「下一步该做什么」并提出动作
写工序（agent 只能提，不能做）
  清洗入库、启动蒸馏、整段验收关闭、定点修复落地、派生重建、解锁、扩展规划
      ↓ 落到 proposal（有证据、有风险等级、可预览 diff）
审批闸门（人批）
  批准 → 应用 → 回读
```

**agent 的产出从「答案」变成「工单」**：它不再直接回答「检查完了没问题」，
而是推进一条**工序链**，在需要写的地方停下来等批准。

## 3. 工序链（两条轨，每道工序都有派发对象）

```text
【提示词轨】writer 吃进去的那份提示词是怎么来的
  交稿 → ①语料已就位 → ②清洗抽检 → ③文风蒸馏 → ④档案审查 → ⑤提示词体检
【正文轨】writer 写出来的正文能不能放行
  ⑥正文审查 → ⑦修复待批 → ⑧收敛
```

每道工序都是四段式：**审核（只读工具）→ 修复（提案，等人批）→ 派发（谁做）→ 编排（下一步）**。

| 工序 | 审核（只读） | 修复（提案） | 派发给谁 |
|------|------------|------------|---------|
| ① 语料已就位 | `read_attachment` / `audit_chunks` | — | 作者投放语料 |
| ② 清洗抽检 | `check_ingest_clean` / `audit_chunks` | `ingest_clean` | 清洗 agent（错字/漏字/水印） |
| ③ 文风蒸馏 | `audit_corpus` | `start_distill` | 蒸馏 agent（抽取文风档案） |
| ④ 档案审查 | `audit_narrative` | `start_distill`（换档重跑） | 审查 agent（审档案本身） |
| ⑤ **提示词体检** | `audit_prompt`（新） | `prompt_override` / 重蒸馏 | 提示词审核 agent（审组装后的系统提示词） |
| ⑥ 正文审查 | `run_diagnostic_task` + 整段验收 | `close_acceptance` | 审查 agent（封闭清单审计 + 整段验收） |
| ⑦ 修复待批 | `get_plot_timeline` | `apply_body_repair` | 修复 agent（Writer 候选 + 独立复验） |
| ⑧ 收敛 | — | — | — |

### ⑤ 提示词体检：补上的那一环（作者指出「抽取的系统提示词也要审」）

「蒸馏跑完了」**不等于**「writer 吃到了」。中间隔着几道**静默失败**的门 ——
它们不报错，只会让文风蒸馏白做、或让正文开始像参考书：

| 检查 | 判据 | 级别 |
|------|------|------|
| `prompt_narrative_not_injected` | 档案存着，但渲染成提示词块是空的 → 蒸馏白做 | error |
| `prompt_voice_leak_in_original` | **原创模式的渲染块里**含【角色声音词典】（参考书角色怎么说话） | error |
| `prompt_forbidden_self_conflict` | 档案说「禁用 X」，**规则正文**里就在写 X | error |
| `prompt_system_too_long` | 静态系统提示词超预算（挤正文额度、也击穿缓存收益） | warn |
| `prompt_override_overlong` | 运行期提示词覆写块超长（易变成注入超长提示） | error |

实现：`backend/app/agents/prompt_audit.py`（组装一次 writer 的静态提示词再查，
产出九字段 issue，与其它审核同构）；agent 只读工具 `audit_prompt`。

与 `audit_narrative` 的分工：那个审**档案 JSON 本身**（规则太短、维度膨胀、剧情泄漏），
这个审**组装后的提示词**（注入是否生效、长度、禁词矛盾、声音词典泄漏、覆写越界）。互补，不重复。

**一条判据纪律：查「实际生效的那份东西」，不查代理指标。**
这两条检查最初都查错了对象，在真书档案上必然误报（详见
`docs/stage3-real-rerun.md` §4）：

- 声音词典泄漏：要查**渲染块里有没有**，不是**档案里有没有**。
  档案里留着声音词典是**对的**（续写模式正需要它），
  原创模式靠 `include_voice=False` 在渲染时剔除；
- 禁用词自相矛盾：要拿**规则正文**去比，不能拿整个渲染块 ——
  渲染块里**含禁用清单本身**，拿整块比等于禁用清单和自己匹配，恒真。

误报的代价不是「报告不好看」：生成闸门是「体检有 error 就 409」，
误报等于**把真活堵死**（真书项目当时连正文都写不出来）。

### 正文轨的修复回路（作者指出「writer 写出来的文本也要有审核/修复/派发/编排」）

```text
⑥ 正文审查（闭环审计 + 整段验收）
     ↓ 有违例
⑦ 修复：修复 agent 产出 Writer 候选 → 独立复验 → **提案** → 等人批准 → 应用
     ↓ 正文变了（审计证据失效）
⑥ 重审（必须重跑，不能沿用旧账本）
     ↓ 通过
派生重建 → 解锁 → 继续生成下一段 → 回到 ⑥
```

**「以此类推」的终止条件是确定性的**（查库 + 只读规则），不让模型自己说「差不多了」：

- 清洗：抽样复查残留 ≤ 阈值（错字/水印/漏字三类都为 0）
- 抽检：无 error 级 issue（warn/info 可留，但要在报告里列出来）
- 蒸馏：`DistillRun.status == success` 且档案必需字段齐
- 提示词：无 error 级体检项（档案真的进了提示词）
- 正文：`pending_acceptance.unresolved == []` 且 `plan_coverage.blocking == []`
- 修复：无待批提案（每一条都已批准或撤回）

任一条不满足 → 继续下一轮，并**说明卡在哪一条**。

## 4. 需要新建的东西（三个件）

### 4.1 工序链的状态（`WorkflowRun`）

一张表，记录「这个项目现在走到哪一步」：

```text
project_id / status / current_step / round / steps(JSON: 每步的状态、结果摘要、证据 run_id)
                / gates(JSON: 待批提案 id 列表) / created_at / updated_at
```

理由：`DistillRun` 已经证明了「作业状态机 + 进度回调 + 失败落库 + 并发防重」这条路走得通；
工序链是同一个形状，只是粒度更大、步骤更多。**不要新造第二套 job 机制。**

### 4.2 工序定义（`app/agents/workflow.py`）

工序表（代码里的常量，不是数据库配置）：

```text
Step(id, 名称, 前置条件, 读工具, 写提案类型, 判据, 下一跳)
```

每一步的「读」是现有工具的组合，「写」是提案类型。**工序不自己实现业务逻辑** ——
一律调用既有模块（清洗、审核、蒸馏、验收、修复、重建、扩展规划），
这样工序链不会变成第二套实现。

### 4.3 写工序的提案类型（proposals.py 扩种）

现有 proposal 模型已经有：证据、风险等级、preview diff、approve/apply。
需要新增的提案 kind：

| 提案 kind | 对应动作 | 审批理由要写清楚 |
|-----------|---------|----------------|
| `ingest_clean` | 清洗结果入库 | 会写入语料表（幂等：按指纹去重） |
| `start_distill` | 启动蒸馏（档位） | 会烧模型额度 |
| `close_acceptance` | 关闭整段验收义务 | 会解锁生成 |
| `apply_body_repair` | 定点修复落地 | 改正文（有 diff 可预览） |
| `derived_rebuild` | 重建 KG/事实/摘要 | 派生数据整体重算 |
| `unlock_generation` | 解除生成守卫 | 放行后续生成 |
| `extend_plan` | 扩展规划 | 会改时间线（新增节点） |

## 5. 框架选择：不引 langchain / langgraph / deepagents，**借鉴它们的模型**

作者提到可以参考 langchain / langgraph / deepagent。我的建议是**借鉴，不引依赖**，三条理由都基于这个仓库的现状：

1. **等价物已经在本地**：langgraph 提供的四件事——「图」（ReAct 循环 + 工序表）、
   「检查点」（AgentRun + Evidence 证据链 + 工序状态）、「人工中断」（proposal 审批闸门）、
   「追踪」（AgentRun 历史）——这里都有对应实现。再叠一层框架，等于把同一件事实现两遍。
2. **硬边界会被削弱**：这个仓库最要紧的一条设计是「assistant 只能提、不能写」
   （注册表强制只读 + 写工具黑名单前缀）。langgraph 的通用节点/工具机制会绕开这层，
   要保就得自己再包一层 —— 那等于又写了一遍边界。
3. **成本与重复**：引框架会带来依赖体积、学习成本，以及与 proposals / jobs / AgentRun
   三套账的重复（同一个动作两处记账必然对不上）。

**要借鉴的三个具体模式**（照着做，不需要依赖）：
- **工序图**：状态机的节点 + 条件边（上面的工序表就是）；
- **人工中断（interrupt）**：agent 走到写工序就中断，产出提案等人批（proposals 已有）；
- **检查点/可恢复**：每步完成即落库（工序状态 + 证据 run_id），断点续跑从最后一步继续。

如果将来工序分支变复杂（并行、多角色互评），再评估框架；现在的形态不需要。

## 6. 前端：工序面板

用户看到的不是六个按钮，而是一张**工序进度条**：

```text
交稿 ✓ → 清洗 ✓ → 抽检 ⚠ 2 处待修 → 蒸馏（排队）→ 审查 → 修复（待你批准）→ …
```

- 现有 `DistillProgress.vue` 就是样子（阶段 + 进度）；
- 工序状态用**人话**（沿用 `utils/assistantDisplay.ts` 的口径）：
  不出现「pending_acceptance」「plan_coverage」「derived_state」这类内部词；
- 待批提案直接给「看 diff / 批准 / 拒绝」三个动作。

## 6. 三条产品决定（作者拍板）

### 6.1 需要用户决断的地方 → 给**选择框**，不给开放问题

有些岔路口系统不能替作者决定（蒸馏用哪一档、每段多少字、一次生成几章）。
这些点的卡片不是「确认 / 取消」，而是**选项**：

```text
┌─ 文风蒸馏用哪一档？ ────────────────────────┐
│ 蒸馏档位决定提炼多少语料：越完整越准也越慢越费额度。 │
│ [完整档]  [平衡档]  [快速档]                     │
│ 全量语料提炼，最准；耗时长、额度消耗最大。            │
│ 采样语料提炼，效果与成本居中（多数项目选它）。          │
│ 少量采样试跑，先看方向再决定要不要跑完整档。            │
│ 点一个即执行 POST /api/projects/7/distill             │
│ （请求体与选项的对应关系由服务端下发，前端不参与构造）    │
└──────────────────────────────────────────────┘
```

- 决策点注册表：`backend/app/agents/decision_points.py`（选项 + 端点 + 请求体补丁，
  唯一真源；模型**不参与编选项**）。
- 卡片契约复用既有的待确认卡片（多一个 `kind='choice'` 与 `detail.options`）。
- 什么时候弹：**确定性关键词**（该决策点的触发词，或「开始 / 走流程 / 下一步」这类
  通用启动词）。不然每条消息都弹同一个框 —— 用户问「第 3 段写得怎么样」也被问
  「蒸馏用哪一档」，那是噪音不是帮助。
- 前端：选项就是按钮（点一个即执行）；选项卡片不显示「确认执行」。

### 6.2 提交文本统一收到助理 agent

`POST /api/novels/upload` **已关闭**（409 明确报错 + 指向助理）。它绕过整条流程：
文本直接入库，不经清洗预览、不经抽检、不经蒸馏与审查。实测那类语料里大量
空/超短分片、切分停在半句话中间 —— 文风也就不可信了。

关掉**没有丢能力**：清洗 + agent 抽样复查跑在助理那条路上
（`/api/assistant/attachments` → agent 投放入库 → 同一套 `ingest_text`）。

前端同步：语料库页不再有上传按钮（留一个必然失败的按钮会被读成「功能坏了」），
改为说明 + 「去助理页投放」。

### 6.3 不许越过流程生成

`/api/generate`、`/api/generate-stream`、`/api/generate-loop` 现在先过**工序链闸门**：

- 有待批的写回建议 → 409（正文要改完才能继续生成）；
- 文风档案没真进到提示词里（提示词体检有 error）→ 409（生成出来也是白写）。

自由生成（没选参考语料、没有文风档案）一律放行 ——
闸门拦的是「流程没走完」，不是「用户没准备」。

### 6.4 工序面板：状态词由服务端给，待处理的改动看得见

面板只做两件事：**显示**走到哪、卡在哪；**处理**等着你的改动。

**状态词（`state_label`）由服务端给，不在前端映射。** 原因有三：

1. 「没有待批项」和「已完成」在中文里差得很远 —— 前者说明**没东西可批**，
   后者说明**该做的都做完了**；混成一个词，用户会以为正文已经改过；
2. 「下一步」只有服务端知道（它是第一个还没做的工序）；
3. 「还差 N 步」要数前面开放了几道工序，前端拿不到这个事实。

所以每道工序的状态词由**判据**给，判据没给才回退到默认映射。

**待处理的改动挂在工序链上，不另开一个查询口子。** `open_proposals` 同时包含
`pending`（等人批）与 `approved`（批了、等人写进正文）—— 只查 pending 会有个
流程坑：用户点完「批准」，提案状态变 approved，于是它从清单里消失，
用户再也点不到「应用」，这件事就卡死了。

**批准与「写进正文」刻意分成两步**（`approve` → `apply`），不合成「一键生效」：
审批是人的判断，落库是系统的动作；合在一起就取消了「先看清楚改了哪儿再决定」
这一步（这与 `assistant_proposals.py` 里既有的端点拆分是同一条纪律）。
面板还提供「看改动」（只读拉 diff），让人在做决定前看到改了哪几个字。

写回闸门本身没变：提案仍走既有端点、漂移仍会 409(stale)、应用仍写版本历史。

### 工序判据的一条纪律：看**产物**，不看执行记录

每道工序的判据要问「这一步的**产物**在不在位」，而不是「这一步的
**执行记录**有没有」。文风档案有两条来路（自己蒸馏 / 从蒸馏库应用），
只看 `distill_runs` 会把「应用来的」判成「还没做」，与同一时刻
「档案审查 done」自相矛盾（实测：《北荒刀歌》真书档案的两个项目全中）。

同理，**产物在但还没生效**要给出**下一步动作**（「蒸馏库里已有这份语料的
文风档案，应用到本项目后这一步才算完」），而不是含糊的「还没跑过」。

## 8. 这一轮不做的（要作者点头）

- **不放松「agent 只读」这条硬边界**（写一律走提案）；
- **不引 langchain/langgraph/deepagents**（借鉴，不引依赖）；
- **不让模型自己判定收敛**（收敛判据是确定性的，模型只负责执行与说明）。
