# 两件待设计的事：文字质量审核维度 / agent 起草·用户定稿

> 这一篇是**设计稿，待审阅**。两件事都源于真书全流程的实测：
> 一件是「写出来的正文有瑕疵，但两道审核都抓不到」，
> 另一件是「agent 起草的东西没有定稿的通道」。

## 0. 起点：真书正文里的两处瑕疵

真书全流程写出来的那两段正文（`docs/realbook-full-flow.md`）里，肉眼可见两处：

```text
① 沈娘子一句台词里混进了英文词：
   「怕不是 River 里头翻了肚皮。」
② 年龄前后不一致：
   叙述写「那年他十四岁」，沈娘子却叫「十三岁的娃娃」。
```

**两道现有审核都抓不到**：

| 审核 | 判据 | 为什么抓不到 |
|------|------|------------|
| 封闭清单审计 | **越界**（正文里出现了契约之外的物品/角色/地点） | 「River」不是越界；年龄矛盾不是越界 |
| 整段验收 | 与**保存权威**一致（时间/地点/参与者/物品状态） | 项目是原创分支，权威很薄；它核的是「有没有超出授权」，不是「自己跟自己对不对」 |

所以这不是「判据写错了」，是**缺一维审核**：文字本身的质量 + 正文**内部**的事实自洽。

# A. 文字与事实自洽（新增一道正文审核）

## A.1 它审什么、**不**审什么

**审**：

1. **文字质量**（外来文字、标点、明显的排版事故）；
2. **正文内部自洽**（同一实体在同一段正文里属性打架：年龄、数量、身份）。

**不审**（分工要清楚，否则三道审核互相抢活）：

- 越界 → 封闭清单审计（已审）；
- 与保存权威一致 → 整段验收（已审）；
- 文笔好坏、审美、节奏 → **不审**（那是作者的事，机器判不了也不该判）。

## A.2 判据分层：确定性优先，模型只做它擅长的

这条分层不是风格偏好，是因为**误报会堵死真活**：生成闸门是「审核有 error 就 409」，
一道误报就能让项目写不出字（这次体检的两条误报已经演示过一遍了）。

**第一层：确定性规则（免费、不会瞎报，允许 error 级）**

| 规则 | 判据 | 例 |
|------|------|-----|
| 外来文字 | 中文叙事里出现拉丁单词，且不在白名单（型号/单位/代码/专名/已登记的外文词） | `River 里头` |
| 中英标点混用 | 中文之间出现半角 `,` `.` `;` `:` | 正文里的 `他，将砂粒捏碎` |
| 重复标点 | 连续两个以上相同标点（`。。`、`，，`） | —— |
| 排版事故 | 空行/缩进异常、超长无标点段落 | —— |

这四条**可复现、可解释、无模型参与** —— 出错时能直接指到位置。

**第二层：模型判断（贵、且模型会自相矛盾 → 一律先降级）**

| 规则 | 判据 | 降级口径 |
|------|------|---------|
| 同实体属性矛盾 | 同一实体（**规范名 + 正文原词**两键归并）在正文里出现两个不同的年龄/数量/身份 | 矛盾 → **unknown（判不出）** → 开放项，**不阻塞** |

**为什么必须降级**：真实判官在 4380 个候选里判出的 4 处「违例」**全部**是
自相矛盾型（同一实体别处判了「不越界」）—— 矛盾就是**证据不足**，
不是「确认有问题」。沿用既有纪律 `inconsistent_verdicts()`：矛盾 → unknown。

**所以第一层才允许 error 级，第二层一律 warn/开放项。** 这条守则要写进代码注释和测试。

## A.3 挂在工序链的哪一步

**建议：并进「⑥ 正文审查」，作为第三块**（封闭清单审计 → 整段验收 → 文字与事实自洽）。

| | 并进去 | 单独一步（⑥b） |
|---|---|---|
| 链的长度 | 不变（九道工序） | 多一道 |
| 重审成本 | 与审计/验收一起跑，一轮出全结论 | 可单独重跑（比如只改了文字没改越界） |
| 职责清晰度 | 「正文审查」变成三件事，标题变宽 | 名字直白：文字与事实自洽 |
| 修复回路 | 三块的提案汇到同一个「修复待批」 | 同 |

**取舍**：正文审查那一步本来就重（几百次调用），再加一道会让人不想重跑。
但**单独一步的坏处更大**——链上多一道工序，而它审的东西（文字瑕疵）本来
就是「正文审查」的一部分。**我倾向并进去**，并把报告分成三段展示。

## A.4 修复回路

命中处 → 生成**文本提案**（`EditProposal`，`type='text_edit'`）→ 走**既有**审批闸门
（批准 → 写进正文）→ 正好复用现成的提案表、审批端点与面板的「等着你处理的改动」区。

**不新建修复机制**：这条链上已经有一套「提案 → 批准 → 应用」，
新的审核维度只负责**发现问题并定位**，修复照样走它。

**一条红线**：第一层（确定性）发现的，可以**自动**生成提案（改哪个字很明确）；
第二层（模型）发现的**不自动生成**（证据不足，改了可能改错）——
只作为开放项显示，让人自己决定要不要提。

## A.5 实施顺序

| 片 | 内容 | 验收 | 状态 |
|----|------|------|------|
| A1 | 确定性规则 + 报告（新模块 `app/agents/text_quality.py`） | 真书正文上跑：**紧贴中文的外文**必须命中 | ✅ 已做 |
| A2 | 挂进工序链「⑥ 正文审查」第三块 + agent 工具 `audit_text_quality` | 链上多一块结论；error 级挡住、warn 级只报 | ✅ 已做 |
| A3 | 模型版「同实体属性矛盾」（**显式动作**，先只报不阻塞） | 假渠道回一个矛盾 → 报成 warn；答得不合格 → 降级不拖垮 | ✅ 已做 |
| A4 | 第一层命中 → 起草修正（走 B1 的可编辑草稿通道） | 标点事故 → 草稿改对 → 确认 → 应用 → 复审干净 | ✅ 已做 |

### A3 的两条设计决定

- **只问「同一实体」**：不同实体之间「对不上」往往是正常的（两个角色各说各话）；
  只有同一实体的属性打架才是硬矛盾。
- **一律 warn，永不阻塞**：模型的判断会错 —— 时间推进、角色撒谎、视角人物的
  猜测，看上去都像矛盾。跟封闭清单那边的教训是同一件事：矛盾 = 证据不足。

**它不在工序链的读路径上**：要调模型，所以它是**显式动作**（跟整段验收一样），
由 agent 工具 `audit_text_quality` 触发。否则面板每刷新一次就烧一次额度。

### A4 的闭环（端到端跑通）

标点事故的修法是**机械唯一**的（`。。` → `。`、中文旁的 `,` → `，`），
所以「改后长什么样」由**规则**算，模型只负责**提出**，人在卡上确认：

```text
原正文：少年把竹篙插进石缝，船身晃了晃。。他稳住气,又撑了两下。
【审核】2 处标点事故（error，blocking=1）
【agent 起草】草稿：少年把竹篙插进石缝，船身晃了晃。他稳住气，又撑了两下。
  本项目的提案行数 = 0（只构造，没落库）✓
【确认】提案 id=4 status=pending
【应用后】少年把竹篙插进石缝，船身晃了晃。他稳住气，又撑了两下。
标点已改对：True
复审：blocking=0（原来 1）
```

**为什么不让模型改正文**：修法唯一确定，模型改反而可能把好字改坏，还多烧一次调用。
分工是：规则算「改后应该长什么样」，模型只提出，人确认。

### 一条实测换来的纪律：**降级不许静默**

事实自洽那一层包在 `try/except` 里（模型挂了就只跑确定性规则）。第一次跑时
**漏了一个 import**，`NameError` 被静默吞掉，测试看到的现象是
「没发现矛盾」——和正常结果**长得一模一样**。

所以：这一层挂掉时，统计里要看得见（`stats['fact_error']`）。
「没报」不能被读成「查过没问题」——那条 `stats` 就是为此存在的。

### A1 的实测（真书正文）

规则在真书正文上跑出来的结果：

```text
project 2「雪中续写验证」  stats: punctuation=0, foreign_latin=1（紧贴=1）, blocking=0
  [warn] 1 处疑似外来英文
    证据: 掌拍在他后脑勺上：“你这张嘴，迟早惹祸。”  “Already惹了。”  徐凤年捂着后脑退回老黄身边…

project 7「旧北站夜班读数」 stats: 全 0（干净正文不误报）✓
project 8「真书提案化验证」  stats: 全 0 ✓
```

**两条设计决定在实测里被验证了**：

1. **外来词只 warn 不挡**：那个 `Already惹了` 确实该改，但它判不准
   （换个项目可能合法）—— 报出来给人看，不挡链。
2. **「紧贴中文」和「分开」要分开看**：真书正文里那个案例是**紧贴**的
   （`Already惹了`，中英之间漏了空格）—— 这是明确的排版事故；
   而分开的外文（`River 里头`）判不准。规则据此分档：
   引号的豁免只对**分开的**词有效。

**顺带修掉两个自己写出来的 bug**（都是测试逼出来的）：

- 规则只在词**前面**找中文字符 → 段首的「Already」会漏 → 改成前后都看；
- 「中文旁半角标点」的正则用了**变长 lookbehind** → `re` 直接编译失败 →
  改成两个定宽分支。

# B. agent 起草 · 用户定稿（提案通道）

## B.1 冲突在哪

**红线**（写在代码里，不是我发明的）：提案的 `after_text` **必须由用户填写** ——
服务端替用户写新正文就是越权。

**但 agent 现在只能起草「结构」，起草不了「内容」**：

| agent 能起草 | agent 起草不了 |
|-------------|---------------|
| 剧情大纲（几行、给人看结构） | 提示词覆写（一段真正的提示词） |
| 蒸馏档位（一个枚举） | 改写正文的某一句 |
| 扩展规划的剧情点（骨架） | 语料清洗后的具体文本 |

而且**界面上没有提案录入入口**：`api.createProposal` 只有 client 方法，
前端没有任何地方调用它 —— 这条通道目前**只有 API 能走**。所以「agent 起草 →
人定稿 → 落库 → 批准 → 应用」这条闭环，缺的不是能力，是**中间那一段**。

## B.2 解法：三段式（草稿在卡上，定稿在落库那一刻）

```text
① agent 起草（只构造卡，不落库）
        ↓  卡上带一个可编辑的文本框，默认是草稿
② 用户改 / 或原样确认
        ↓  前端把「用户看到并确认的那一版」回传
③ 落库：EditProposal.after_text = 用户确认的那一版
        ↓
④ 走既有审批：批准 → 应用（漂移仍 409 stale）
```

**关键在第 ③ 步**：落库的必须是**用户确认时看到的那一版**，
不是 agent 的原版。这样「服务端替用户写内容」的红线没破——
服务端写的是**用户点头的那份**，不是它自己生成的那份。

## B.3 界面要什么

- 卡片上给一个**可编辑的文本框**，默认填 agent 的草稿；
- 框旁边写清「这是草稿，可以改」（**不要出现 `after_text` 这种字段名**）；
- 改完点「确认」→ 前端把编辑后的文本放进请求体 → 既有 `POST /api/assistant/proposals`；
- 界面上不新增交互形态：还是那张待确认卡，只是多一个可编辑的正文框。

**前端参与构造请求体了吗**：会（把用户编辑的文本放进 body）。
但这不是「前端替服务端拼协议」——`type` / `target_kind` / `target_id` 仍由服务端下发，
前端只填**用户输入的那一个字段**。这与既有约定（「前端不参与构造」）有一处**受控的例外**，
要在代码注释里写清楚：*用户输入的文本由前端回传，协议字段仍由服务端给*。

## B.4 `prompt_override` 走这条通道 —— 但它**只能加不能减**

先验过能力边界（这条差点写错）：

```text
PROMPT_KEYS = (STYLE, CONSTRAINT, DIRECTIVE)   # 三个追加槽
CODE_DEFAULTS = {每个槽: ""}                    # 默认什么都不加
MAX_OVERRIDE_LEN = 4000
```

所以覆写是**往提示词里追加三段文字**，**改不了任何既有内容** ——
「原创模式不该带角色声音词典」这种**维度级**行为，覆写解决不了，
要去改 `PROFILE_RULES`（那是代码，不是用户能覆写的东西）。

而且**现在没有任何一个真实的提示词问题要修**：真书档案上体检报的那两条
（声音词典泄漏、禁用词自相矛盾）**都是误报**，本轮已经修掉了
（见 `docs/stage3-real-rerun.md` §4），现在体检是 0 问题。

所以 B 的定位要说准：**它补的是「通道」，不是「修一个已知问题」**。
它服务的是将来出现的这类情况 ——

- 作者要加一条自己的写作规矩（「本章不超过 3000 字」「少用破折号」）；
- agent 针对**某次具体体检结果**起草一段补充说明，人确认后生效；
- 覆写**生效后要能被体检看见**（体检本来就读生效中的覆写
  `resolve_prompt_block`，所以这条天然成立）。

**优先级因此排在 A 之后**：A 有实测出来的瑕疵要抓，B 还没有具体案例。

## B.5 实施顺序

| 片 | 内容 | 验收 | 状态 |
|----|------|------|------|
| B1 | 卡片支持「带草稿的可编辑正文」+ 前端回传用户编辑后的文本 | 手工走一遍：改一个字，确认后落库的是**改后**那版 | ✅ 已做 |
| B2 | agent 起草 prompt_override 草稿 → 卡 → 确认 → EditProposal | 真书项目：体检转绿，生成闸门放行 | ⏳ 待做（**没有具体案例**，见 B.4） |
| B3 | 「修复待批」工序用同一条通道（第一层确定性命中 → 自动起草提案） | 与 A4 合并做 | ⏳ 待做 |
| B4 | 提案列表界面（当前只有 API 能列） | 面板里能看到该项目全部提案 | ⏳ 待做 |

### B1 的端到端验证（已跑通）

```text
原正文：少年把竹篙插进石缝，撑了两下，船身才稳住。
agent 草稿：少年把竹篙插进石缝，船身晃了晃，稳住了。
库里提案行数 = 0（只构造，没落库）✓
提案已创建 id=1 status=pending
落库的 after_text：少年把竹篙插进三石缝里，撑了两下，船身稳住了。
落库的是**用户改过的那一版**（不是 agent 的草稿）✓
应用后的正文：少年把竹篙插进三石缝里，撑了两下，船身稳住了。
正文已改成用户确认的那一版 ✓
```

**红线守住了**：服务端写的是**用户点头的那份**，不是它自己生成的那份。

## B.6 一条要注意的边界（已验）

`prompt_override` 是**三个只增不减的追加槽**（B.4）——所以：

- 它能加东西，**不能减东西**；
- 想改「某模式该不该带某个维度」，要去 `PROFILE_RULES`（代码），不是覆写；
- 覆写生效后**能被体检看见**（体检读 `resolve_prompt_block`），这条成立。

动手前若发现「某问题其实靠覆写解决不了」，那就**别做这一条** ——
宁可不做，也不要做一个改不动问题的通道。

# C. 这一轮不做的

- **不审文笔/审美/节奏**（机器判不了，也不该判）；
- **不自动改写**（一律走提案闸门）；
- **不动「after_text 必须由用户填写」这条红线**（B 方案是绕开它，不是取消它）；
- **不新建第二套审批流**（提案闸门、动作提案闸门各一套，不加第三套）。
