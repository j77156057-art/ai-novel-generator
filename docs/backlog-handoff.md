## 2. 任务清单

### T1（最高优先）出带修复：让产出更像参考书

**为什么这条最重要**：E1 人评已收线，结论是「人眼分辨不出引擎臂与裸写臂」
（`ENGINEERING.md`「E1 收线」）⇒ 风格保真**只能靠机器侧测**。
而现在机器侧的数字是硬的：**E1 都市臂 13 段，33 项里只有 12 项在带**，
参考书自己的单元是 **30/33**（阳性对照，尺没问题）。

**现状证据**：`docs/dushi-style-gap-design.md` 已做完定位，出带项分两类：

| 类 | 特征 | 出带 | 改写能不能修 |
|---|---|---|---|
| **（甲）碎句类** | 句长均值 13/13、句长p90 13/13、段均句数 13/13、句号密度 13/13、长句占比 12/13、句长CV 7/13 | 严重 | **能**（改写就是干这个的） |
| **（乙）标点/词汇类** | 感叹号 13/13、四字格 13/13、逗号密度 13/13、逗号句内位置 13/13、冒号/省略号 11~13/13、比喻 7/13 | 严重 | **结构上碰不到** |

一条很说明问题的对照：**`短句占比` 只有 1/13 出带** ⇒ 产出不是"碎片堆"，
而是**句子整体偏短且长度均匀**（参考书有大量 35~49 字长句，产出几乎没有）。

**落点**：
- `backend/app/generation/engine.py::_rewrite_targets()` —— 现在**只返回到「句长均值」一项带**，
  且档案缺失时返回 `{}` ⇒ **判据 5 静默失效**。要做（甲）就得让它能返回多项带。
- `backend/app/generation/rewrite.py` —— 六道判据在这；判据 5「不许离带更远」只有句长一道
  （**已拍板不加**别的特征上限，理由见 `ENGINEERING.md`「§10.5 两条拍板落地」，别推翻）。
- `backend/app/style/spec.py` —— `build_spec()` / `render_spec()` / `spec_deviation_lines()`：
  规格书由档案导出，是**注入提示词与事后验收的同一份尺**。
- 提示词层改动**只能走覆写表**（硬规则 1）。

**两条候选方向（需要先取证，见 §3「第一件事」）**：
- （甲）把改写目标带从 `p10~p90` **收紧到 p50 附近** / 提高改写预算 / 生成前就要求写长句；
- （乙）从档案 `spec` 取该书的**标点与词汇习惯**注入提示词（不是手写规则）/
  或允许改写动标点（= 扩改写职责）。

**验收（缺一条不算过）**：
1. **阳性对照**：参考书自己的单元在带数 **≥ 25/33**（实测 30/33）——尺先自证；
2. **在带项数**（33 项，中位）+ **配对差**（同一段产出 vs 参考书留出集）一起报，
   **只报"带内率上升"不算通过**（带内是二值口径，±2 项即噪声）；
3. **离线回放**：对**已有的同一批产出**重算，**不重跑生成、不烧额度**；
4. 跑全量 `pytest tests/`（0 失败）—— 改的是策略代码，必须全量。

**边界**：不改判据阈值去"让数字好看"；不动"哪些特征算在带内"的口径；
不许为了单本书堆特例（机制必须对下一本书同样成立）。

### T2 全书摘要「切块抽 + 合并」那一档真跑一次

**为什么**：README 的「已知限制」写着这条**从来没有真跑过** ——

**落点**：
- `backend/app/style/digest.py::choose_digest_mode()` —— `MODE_WHOLE`（整本）vs
  `MODE_RETRIEVAL`（切块抽后合并）；触发条件是"书太大、或渠道没声明能吃下这么多字"；
- `backend/app/style/jobs.py::run_book_digest_job()` —— 执行入口；
- `backend/verify_book_digest.py` —— 四项验收的验证器。

**验收**：
1. 四项验收全绿：**证据留存 / 主线覆盖 / 角色覆盖 / 压缩比**；
2. **阳性对照必须仍然被判不通过**：只覆盖开头的摘要、整份编造的摘要
   —— 如果它们也能过，说明闸门坏了，先修闸门；
3. 报三个实测数字：**条目数、逐条可回查原文的比率、总耗时**；
4. 说清这一轮用的是哪个渠道、块大小多少、书多长。

**已知坑（别当 bug 报）**：摘要**条数由模型自己定**，同一本书两次真跑分别是 26 条与 113 条
（都过闸门）。闸门管质量不管体量 ⇒ **接进上下文时不能假设长度稳定**。

**为什么**：`style_candidate_pool` 默认 `1`（关），理由是"多采样 = 多花时间与额度，

**验收**：同一份提示、同一份档案，跑 **N=1 vs N=3**（够的话再 N=5），至少 **5 段**，报：

**边界**：**不许因此把默认改成开** —— 除非数据明确支持，且要写成"可配置 + 默认关 + 说明"。

## 4. 交付与汇报格式

**提交**：
```powershell
# 只按路径 add，别 add -A
git add backend/app/style/jobs.py tests/test_xxx.py README.md
git commit -F <TMP>/commit_msg.txt          # 中文 message 走文件
```
commit message 里要写：**改了什么 / 为什么 / 验收结果**（不是"优化了一下"）。

**汇报**（每条任务一段，缺项要明说"没做/没验"）：
1. 改了什么（文件 + 一句话）；
2. **实测数字**（对比改前/改后，同尺同口径）；
3. **阳性对照**（尺自证过没过）；
4. 全量 `pytest` 的结果（`PYTEST_EXIT_CODE` + 项数 + 失败数）；
5. 没做的部分与原因。

**别做的事**：不要声称"已验证"而只跑了定向脚本；不要把"带内率上升"当成功；
不要在汇报里省略失败项。
