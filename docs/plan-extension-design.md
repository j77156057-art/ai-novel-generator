# 规划用尽后如何扩展规划（新剧情点写进契约的路径）

## 0. 现状：只有关门，没有出路

有规划、且规划里的剧情点都写完时，生成现在被**拒绝**（409 `plan_exhausted`）。

拒绝是对的：没有段契约就没有**保存权威**可核对，新写的那段只能自己编前情
（实测：规划 3 个节点写出 4 段，第 4 段自己编出「复查结果/待查」「压放时间十点二十七分」，
审计只能报 `missing_saved_authority`）。

但现在作者想继续写时**没有路径**——只有一句「请先扩展规划」，而扩展规划这件事
本身没有机制。这份文档定义那条路径。

## 1. 语义与边界

**扩展规划 = 在保存权威允许的范围内，追加新的剧情点，并把它们写成新的段契约。**

| 边界 | 说明 |
|---|---|
| 权威只读 | 不改 `premise`、不改已冻结契约、不改已写正文 |
| 只追加 | 节点、契约都往后加；已写段落绑定的节点不动，段号不复用 |
| 不越清单 | 新剧情点里出现的物件/人物/地点必须在权威的封闭清单内 |
| 边界即失败 | 权威没有余量时**显式失败**并说清差在哪，不替作者编剧情 |

「不替作者编」是这条机制的底线：权威写到哪儿就是哪儿，扩不动就说扩不动。

## 2. 余量的两种来源（通用，不针对任何一篇）

**R1 剧情余量**：权威声明的范围（时间窗 / 场景 / 情节阶段）里，规划还没覆盖的部分。

**R2 粒度余量**：某个**还没写完**的节点，它的段数预算还没用完 → 把它的 scope
细分成更小的子剧情点（例如权威写「第一节点允许三段预算」，但模型一段就写完了）。

R2 的边界很重要：**只能细分尚未写完的节点**。已经判完成的节点再细分，
等于把同一段剧情写第二遍——那正是系统要防的「越界」。

## 3. 流程（四步）

### Step 1 算余量（服务端）

1. **权威来源**：最后一个已冻结段契约里的 `authority`（premise + causal_node）。
2. **封闭清单**：对权威跑一次封闭清单的 **constraints 阶段**
   （`closed_inventory_v2`，维度 object/person/place），拿到权威的封闭清单
   （含**逐字引用**，可回查）。这一步与正文审计用的是同一套推导，不另造口径。
3. **时间余量**：权威里声明的时间窗 —— 由模型**结构化回答**（起止时间），
   服务端**逐字校验**返回的窗口字符串确实在权威原文里；校验不过按 `unknown` 处理，
   不采信。
4. **段数余量**：权威里声明的段数预算（同上口径），或项目配置的 `total_segments`。

### Step 2 提新点（模型）

提示里给足三样东西，缺一不可：

- **权威**（含封闭清单与时间窗）——新点必须长在权威里；
- **已有节点**的标题与覆盖范围——不许重复已写过的剧情；
- **已写正文的末尾状态**——新点的起点状态要从这里接上。

输出 K 个新剧情点（`title` / `entry_condition` / `exit_condition` / `beats` / `emotion`）。

### Step 3 服务端校验（模型只答关系，政策由服务端推导）

沿用协议 5 的分工：模型不直接回答「这个新点合不合格」，只回答可问清楚的关系，
结论由服务端按封闭清单推导。

- 新点里出现的**物件/人物/地点**必须都在封闭清单内
  （部件、别名按协议 5 的口径判定：`part_of_authorized` / `in_authority_context` 放行，
  `independent` / `contained_in_authorized` 在封闭清单下即越界）；
- 越界 → **把具体越界项回灌给模型让它自己改**（有界重试）；仍犯 → 拒绝；
- 新点的时间窗必须落在权威窗口内，且与已有节点不重叠；
- 新点与已有节点不重复。

### Step 4 写进契约

- 新节点追加到 `timeline.nodes` / `timeline.order`（续号 `n4`、`n5`…）；
- 新契约追加到 `planning.segment_contracts`（续段号 `'4'`、`'5'`…），
  `authority` 与节点绑定一起**冻结**（premise + causal_node）；
- 段数预算从权威余量里扣；
- `current_node` 指向第一个新节点 → 生成可以继续（不再 409）。

## 4. 接口

```
POST /api/projects/{id}/plan-extension   {"count": 1..3}
```

- 200：`{"status":"extended","nodes":[...],"contracts":[...],"headroom":{...}}`
- 409：`{"status":"no_authority_headroom" | "out_of_authority_items" |
  "time_window_exceeded" | "duplicate_node", "message":"..."}`

## 5. 与生成、验收的关系

- 扩展**不改正文**，因此不触发验收义务换绑，派生状态不变；
- 扩展后 `current_node` 非空，`/api/generate` 正常走同一条路径；
- 新写的段在提交时照样冻结自己的契约（权威随提示一起进模型），
  并接受同一套段长闸门与完成判定。

## 6. 验证计划（真实跑，不靠断言）

| 场景 | 期望 |
|---|---|
| 权威窗口已被节点用完（本项目当前状态） | 409 `no_authority_headroom`，且说清权威写到哪 |
| 权威留了余量（新项目：权威写 09:00–12:00，规划只覆盖到 11:00） | 扩展出新节点 + 新契约，随后能续写一段 ≥3000 汉字 |
| 模型提了清单外物件 | 回灌具体违规项 → 自改通过；不改则 409 `out_of_authority_items` |
| 扩展后生成 | 新段进审计，封闭清单下 0 违例（与本轮「权威进提示」的口径一致） |

## 7. 不做 / 不声称

- **不**自动替作者扩写权威：权威到边界时只能请作者扩写，系统不编；
- **不**做段号重排或正文合并：扩展只往后加，不动历史；
- 本文档描述的是**设计与验证计划**；实现落地前，阶段三那三段正文仍是
  「规划用尽 → 拒绝生成」的状态。
