Baseline: foundation-release 4ec7db8; ReAct protocol inspected at 9ba8275. Do not alter react_loop.py. Register run_diagnostic_task as a read-only ToolSpec; dynamic catalog integration uses explicit primitive parameters. The ReAct branch has a richer ToolSpec.parameters field; integration owner should preserve it when merging registry changes.

Task: project-scoped foundation_diagnosis, timeline_review, binding_review, claim_review or repair_verification. Explicit experimental opt-in required. Independent Assistant provider call with diagnostic role, task ID and parent run association. No conversation transcript is inherited. Read only the capability needed by the task. Model conclusions are advisory unknown/inferred/observed, never authorization to mutate business state. Missing capability or invalid skill fails before model invocation. Model failure remains unknown.

Capabilities have independent versioned metadata and local Python bindings. Skill JSON is loaded exclusively from a fixed repository root with strict schema and dependency checks. New versions start experimental, validated requires provenance, deprecated is not loadable. No runtime promotion or arbitrary attachment paths/code. First skill foundation_input_health v1 remains experimental after local acceptance.

Read capabilities: persisted plot_timeline plus existing timeline_progress; actual ordered chunk content hash plus project/shared cache comparisons using existing fingerprint predicates; selected L2 character claim ledger plus quote coordinates against real chapters. No KG/summary substitute, project_narrative/ensure/build calls or repair execution. Quote location is not semantic proof.

Reports persist only AgentRun/Evidence, complete JSON report in AgentRun.note (existing schema has no trace_json). Coverage and fingerprints are explicit; model input is bounded and claims paginated. Suggested existing pending action kind proposal only for local review, never silently executed. Future unavailable repairs appear as missing capabilities. Reverification is a new task with original evidence fingerprint and acceptance baseline; changed input cannot resolve an earlier finding.

Acceptance: RED/GREEN targeted tests, malformed manifest, missing capabilities, scope/quote limits, experimental lifecycle, real role participation, unknown model errors, SQL business-write guard, affected registry/timeline/profile regressions. Real acceptance uses SQLite read-only backup of current DB and Assistant provider loaded from its persisted settings. Preserve source hash/stat; only copy receives audit logs. No full distillation or generation.

## API and extension

`invoke_tool('run_diagnostic_task', db, project_id=1, task_type='binding_review', skill_id='foundation_input_health', skill_version=1, allow_experimental=True)` is the main-assistant entry. Optional primitive arguments: question, novel_ids, character, cursor, limit, parent_run_id, previous_run_id. No provider or arbitrary code/path argument is exposed. The callable has explicit type annotations for dynamic tool introspection; this branch does not replace the ReAct branch's richer ToolSpec schema or edit its core. Dynamic scheduling integration itself remains the integration owner's acceptance task.

`load_skill(id, version)`, `discover_skills(allow_experimental=...)`, `register_capability(Capability(...))` and `read_capability(db, project_id, id, scope)` are independent product interfaces. Add trusted `skills/<id>/vN.json`, preserve old files, declare tasks/roles, minimum capability versions, ordered steps, acceptance evidence, failure boundaries, provenance and supersedes. Select it via skill_id/skill_version; new task names execute its declared capabilities. New capability implementations require an audited local binding branch and explicit register_capability; JSON cannot import code. Missing IDs/versions fail explicitly. Lifecycle promotion is a repository review decision, never a runtime write.
