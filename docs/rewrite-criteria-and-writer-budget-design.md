# §10.5 剩余两条待拍板：改写判据的上限、写手的预算与思考开关

> 2026-11-02。来源：`docs/blind-eval-v2-design.md` §10.5「待拍板」那两条。
> 这份稿子**只做两件事**：把两条待拍板背后的代码现状与实测数据摊开，
> 给出可选方案与推荐。**不动代码** —— 拍板之后才实施。

---

## 0. 两条待拍板的原文

> - 改写判据要**不要按特征分别设上限**（现在只有句长一道）；
> - 写手的 `max_tokens` 在**开思考**的渠道上要不要默认抬高
>   （产品侧已经是 32768，但配置层对 `deepseek-v4.1-flash` **不提供思考开关** ——
>   实测名单里只有 `deepseek-chat / deepseek-reasoner / deepseek-flash / deepseek-v4-pro`）。

## 1. 现状（一）：改写判据

### 1.1 六道判据在哪

`backend/app/generation/rewrite.py::rewrite_style`，全部通过才采纳：

| # | 判据 | 阈值常量 |
|---|---|---|
| 1 | 字数不能缩水过多 | `MIN_LEN_RATIO = 0.60` |
| 2 | 对白引号不能明显丢失 | `MAX_QUOTE_LOSS = 0.20` |
| 3 | 字数不能膨胀过多 | `MAX_LEN_GROWTH_ABS = 45` / `MAX_LEN_GROWTH_RATIO = 0.15` |
| 4 | 句长必须有**实质改善** | `MIN_SENTENCE_LEN_GAIN_ABS = 2.0` / `MIN_SENTENCE_LEN_GAIN_RATIO = 0.10` |
| 5 | **不许修过头**：句长离目标带不能比改写前更远 | 目标带 = 档案 p10~p90 |
| 6 | 对白形态不能被改坏 | `MAX_BARE_RATIO_INCREASE = 0.05` |

**「不许离带更远」只有句长这一道**（判据 5，`rewrite.py:395-413`）。

### 1.2 一个前提：判据 5 只在「目标带拿得到」时才存在

`engine._rewrite_targets()`（`engine.py:1554`）从**档案**取「句长均值」的 p10~p90，
取不到就返回 `{}` ⇒ `target_sentence_range=None` ⇒
**判据 5 静默失效**（提示词里同时也没有目标句长，只剩兜底说法）。

所以「按特征分别设上限」的技术前提是：`_rewrite_targets` 要能返回**多项**特征的目标带。
现在它只返回一项。

### 1.3 实测：判据 5 在真实跑次里抓到过什么

用本机 `<TMP>/cross_book_v2`（21 段）与 `cross_book_v3`（12 段）的真跑产物
（每段都记了 `rewrite_info.before/after/target`）：

| 批次 | 段数 | 改写采纳 | 被判据 5 拦下（句长修过头） | 拦下时的实际数值 |
|---|---|---|---|---|
| v2 | 21 | 13/21 | **3** | 23.1→35.8、24.7→35.7、21.0→43.5（目标带上限 ~26 ⇒ 冲到 1.3~1.7 倍） |
| v3 | 12 | 9/12 | **2** | 23.8→42.0、21.3→29.8 |

⇒ **判据 5 是活的，而且真的在挡「修过头」**（5/33 段，15%）。
其余未采纳的段里，5 段是「偏离未达闸门」（成本闸门，压根没调模型），1 段是「句长未改善」。

### 1.4 实测：再加一道「句号密度也不许离带更远」会多拦多少

在 §10 的 A/B/C 跑次里（`<TMP>/cross_ab`、`cross_ab2`，**10 次被采纳的改写**）
模拟这道新判据：

> 句号密度带（如 19.2~32.0）取 `band.detail['句号密度']`，
> 比较改写前后「离带距离」是否变远。

| 结果 | 段数 |
|---|---|
| 被采纳的改写 | 10 |
| 句长更远（现有判据 5 能抓到） | **0** |
| 句号密度更远（新判据能抓到） | **0** |
| ⇒ **新判据额外拒掉** | **0** |

**为什么两者几乎同进同退**：句号密度 ≈ 1000 / 句长（仓库自己的注释，`rewrite.py:95`），
两者方向相反 ⇒ 「句长冲过头」与「句号密度掉出下界」是同一件事的两种说法。
只有当分句器口径与字数口径不一致时才会分叉。

## 2. 现状（二）：写手的预算与思考开关

### 2.1 三个地方各说各的

| 事实 | 位置 |
|---|---|
| 产品侧写手默认 `max_tokens: 32768` / `timeout: 300` | `backend/config/providers.yaml` |
| Writer 的 `max_tokens` / `timeout` **由基线固定**：PUT 端点对 writer 带这两个字段直接 400 | `backend/app/routers/settings.py:642` |
| 前端对 writer 只读展示（assistant / distiller 才可改） | `frontend/src/components/RoleModelPanel.vue:414-430` |
| MiniMax adaptive thinking：**思考关不掉**（`thinking=disabled` → 400），只能调 `reasoning_effort`；provider 层已有**预算地板**（low/medium/high ⇒ 8192/180s；xhigh/max ⇒ 32768/300s） | `backend/app/llm/provider.py:683-762` |
| opencode-go（`deepseek-v4.1-flash`）：**渠道层默认关思考** | `provider.py:936`（`thinking_off=True` 默认） |
| 配置层只给 4 个 deepseek 模型名提供思考开关 ⇒ `deepseek-v4.1-flash` **没有开关** | `backend/app/routers/settings.py:105,114` |
| 这个模型是思考型的，**思考 token 与正文共用同一份 max_tokens**；实测 `max_tokens=64` 时正文一个字都没有 | `settings.py:164-166` |

### 2.2 实测：预算不足的代价是「慢」，不是「跑不完」

三批真跑（`<TMP>/cross_book{,2,v3}`）：

| 批次 | 写手条件 | 段数 | 空正文 | 截断 | 中位秒/段 | 最慢段 |
|---|---|---|---|---|---|---|
| 旧批 | 开思考 + **8000** | 21 | 0 | 0 | 158.2 | **3089.2** |
| v2 | 开思考 + **16000** | 21 | 0 | 0 | 228.9 | 729.1 |
| v3 | 开思考 + 16000 | 12 | 0 | 0 | 163.8 | 426.4 |

⇒ 「3089 秒那一段」= 多轮重试凑出来的（`ENGINEERING.md:7196-7198` 记着
「`max_tokens=8000` + thinking 开着 ⇒ 候选常被拦腰截断，引擎要靠多轮重试才凑出一段」）。
⇒ **54 段的最终正文没有一段是空的** ⇒ 「跑不跑得完」在 16000+ 上已经不是问题；
真正剩下的是**时间成本**（中位 164~229 秒/段）。

### 2.3 一个现存的口径不一致

**实验脚本写死 8000，生产默认是 32768。**
§10 的跑次结论（`docs/blind-eval-v2-design.md:558`）写着
「**写手预算** 8000 → **16000**（8000 下写手反复交空正文/被拦腰截断，实测）」——
那是**实验条件**的修正，不是生产配置的修正。
⇒ 今天若照抄脚本跑，仍会得到「慢 4 倍」的旧现象。

## 3. 决策一：改写判据要不要按特征分别设上限

### 选项

| | 方案 | 代价 | 收益（实测） |
|---|---|---|---|
| **A1（推荐）** | **不加**。把「为什么只有句长一道」写进代码注释与文档；并立一条纪律：**新增上限特征前，先拿真跑数据证明它会拦下什么** | 0 改动 | — |
| A2 | 加「句号密度也不许离带更远」 | 要把 `_rewrite_targets` 扩成多项带；拒绝率上升 ⇒ 被拒的段**保留更碎的原文** | 实测 n=10 ⇒ **额外拒 0 段** |
| A3 | 给所有改写可动的特征都设上限 | 拒绝率明显上升；这些特征高度相关，一道不过整段作废 | 未测（必然更大） |

### 推荐 A1 的理由

1. **收益未被证明**：现有真跑数据里，这道新判据一次都没触发（n=10）。
2. **代价是实的**：拒绝 = 保留原文 = 那段更不像参考书。当前采纳率只有 13/21、9/12。
3. **两项判据同进同退**：句号密度 ≈ 1000/句长，方向相反 ⇒ 多一道多半是重复拒。
4. **判据 5 本身已被真跑证明有效**（5/33 段被它拦下），不是死代码。

### 若将来要加，必须先满足

- 拿一批真跑产物（≥ 20 次被采纳的改写）算出「新判据会额外拦下几段」；
- **额外拦下数 = 0** ⇒ 不加；
- 额外拦下的每一段都要人工看一眼，确认它确实「改坏了」而不是「模型换了个写法」。

## 4. 决策二：开思考渠道上写手的 max_tokens 与思考开关

### 选项

| | 方案 | 代价 | 收益 |
|---|---|---|---|
| **B1（推荐）** | **一张「模型 → 思考行为」的实测表**，由它推导两件事：**预算地板**（思考型 ⇒ 地板抬高）与**是否给思考开关**（关得掉才给） | 要维护一张表；新增渠道/模型时按表查 | 把散在三处的默认值收成一处；「按了没反应」与「预算不够」两类静默失效一起治 |
| B2 | 把写手的 `max_tokens` 改成**可配**（放开基线固定的 PUT） | 与「基线固定」这条既有约定冲突；用户调小 ⇒ 回到「空正文」 | 灵活 |
| B3 | **什么都不做** | 实验脚本与产品口径继续不一致；`deepseek-v4.1-flash` 没有思考开关这件事仍然只有后端 note 知道 | 0 |

### B1 的具体形态

1. **实测表**（新增一张，例如 `backend/app/llm/thinking_models.py`）：
   每个渠道/模型一行 —— `关得掉` / `关不掉（只能调档）` / `强制思考` / `思考占多少预算` / `实测依据与日期`。
   已有事实直接进表：MiniMax M3.1（关不掉、只能调档、effort 压得下来时 8192 够）、
   MiniMax M3（关得掉）、DeepSeek 四个模型名（关得掉）、`deepseek-v4.1-flash`（**没测过**⇒ 先测或先标「未验证」）。
2. **预算地板由表推导**：思考型模型 ⇒ 写手预算不低于地板（沿用 MiniMax 的 `_EFFORT_THINKS_LESS` 判据：
   「这个档位有没有把思考压下来」，而不是「有没有发 effort」）。
3. **思考开关只给表里标了「关得掉」的模型**；`deepseek-v4.1-flash` 要么补一次实测（有则加进表），
   要么**在界面上写清楚「这个模型没有思考开关」**（而不是让选项消失、用户猜）。
4. **实验脚本与产品共用同一份预算口径**（脚本不再写死 8000）。

### B3 为什么不够（但也不算错）

生产路径今天其实是安全的：opencode-go 渠道**默认关思考** + 写手 32768 ⇒
「思考吃预算」不会发生在默认路径上。B3 的问题是**知识散落**：
「哪个模型是思考型」「哪个模型关得掉」「预算地板多少」这三件事分别写在
provider 的构造函数、`settings.py` 的白名单、config 的注释里，
**没有任何一处能一次看全** ⇒ 新加渠道时只能靠人记得改三处。

## 5. 本版不做什么

- 不改提示词、不改改写提示词的文体注入内容；
- 不动盲评包与判定脚本；
- 不改 33 项特征本身、不动「哪些算在带内」的口径；
- 不动 6 道判据里除「新增上限特征」以外的任何一道；
- 不改写手 max_tokens 的可配性（不碰 B2）；
- 不为了「支持更多模型」去猜厂商字段 —— 未实测的一律标「未验证」，不给开关。
