# 文风档案体检：判据改准 + 自愈入口 + 抽取口径说真话

> 2026-10-28 真机验收逼出来的三件事。每一件都先取证、再定判据，判据的每个数字都有实测出处。

## 0. 背景：真机验收撞上的第一道坎

发布版跑通一次真实生成之前，先撞上一个 409：

```
POST /api/generate {"project_id": 1}
→ 409 workflow_prompt_not_ready
   文风档案还没过关（1 个问题，第一件：档案的禁用词与档案正文自相矛盾）—— 先处理它再生成。
```

定位到 `backend/app/agents/prompt_audit.py` 的 `forbidden_conflict` 规则：
拿档案的**规则正文**（渲染块在 `FORBIDDEN_SECTION_MARKER` 之前的部分）
去比对档案自己的**禁用清单**，**子串命中即 error** ⇒ 挡住生成。

命中的词与位置（实测）：

- 禁用清单：`禁用转折词 = [然而, 但是, 不过, 与此同时, 紧接着, 下一刻, 旋即, 随即, 顷刻间, 刹那之间, 电光火石之间]`
- 规则正文：「场景常先以人物当**下一刻**的细微反应或即时判断切入，再补环境与前因」

⇒ 这里的「下一刻」是**名词性状语**（「下一刻的细微反应」＝下一个时刻的反应），
跟清单要禁的**转折连词**用法（「下一刻，X 发生了」）不是一回事。

量化（不是孤例）：

| 样本 | 结果 |
|---|---|
| 蒸馏库 4 份档案 | 2 份命中（id=2「紧接着」、id=4/当前档案「下一刻」） |
| 验收库有档案的 2 个项目 | 2/2 命中（同一份档案应用过去的） |
| 蒸馏库 id=1 / id=3 | 0 命中 |

产品内现成的绕法（实测有效）：换一份档案 ——
`POST /api/projects/1/style-distills/apply {"distill_id": 3}` ⇒ 体检过 ⇒ 生成直接成功。
⇒ **「蒸馏库」不只是省 LLM 的缓存，它还是档案体检的筛子**。

但「换一份」不是解法，是绕路：档案是蒸馏产物，重蒸馏一轮 ≈ 42 分钟 LLM；
而体检明明已经把原因说清楚了（"删掉这些词，或从禁用清单里去掉"），
**产品里却没有让人动手的地方**。这三件事就是补这个洞。

## 1. 判据改准：禁用词按**语法角色**区分（不再纯子串命中）

### 1.1 角色怎么定

对一个禁用项 `w` 在规则正文里的一次出现：

| 情形 | 角色 | 判定 |
|---|---|---|
| `w` 紧跟「的 / 地 / 得」 | **名词性用法**（w 被当名词/状语修饰语用） | 不是清单要禁的那种用法 |
| 其它一切用法 | **连词/短语用法** | 就是清单要禁的那种用法 |
| `w` 本身含标点、或长度 ≥ 7 | **整句/整段模板** | 一律按字面判（这类没有「用法差别」这回事） |

第三条是必要的：禁用清单里混着两类东西 ——
「然而/下一刻」是**功能词**（同一个字串在不同位置角色不同），
「你知道吗？」「他终于明白了活着的意义。」是**整句模板**（出现即冲突，没有角色差别）。

### 1.2 为什么落在「助词」上，而不是词表

`然而/但是/不过` 在任何位置都只能作连词；`下一刻/紧接着` 才会出现名词性用法。
判据落在**紧跟的助词**上，就与具体哪个词无关 ——
换一本书、换一批禁用词、换一个模型蒸馏出来的档案，同样成立。

反例（阳性对照，必须判成冲突）：

```
「然而，」        「但是，」       「不过，」
「正文紧接着展开」                「下一刻，风起了。」
```

真例（必须判成非冲突）：

```
「场景常先以人物当下一刻的细微反应或即时判断切入」
```

### 1.3 严重级别

- **连词/短语用法** ⇒ `error`（与今天一致，仍然挡住生成 —— 真冲突就该挡）。
- **名词性用法** ⇒ 从 `error` 降为 `warn`：
  - 不再挡住生成（这正是「能做出产品」要解决的那道坎）；
  - 但**不隐藏** —— 报告里仍然列出来，带维度与原文；
  - 并且给出一条**可执行**的修复入口（见第 2 节），
    「模型仍可能照抄这个字串」的风险由用户自己点头处理，不由系统替他决定。

这就是「配套更严的判据而不是简单放宽」的落点：**放宽的只是角色判别这一处，
其余一律照旧（error 仍然挡生成），并把被放宽的那部分从「静默放过」改成「可见 + 可修」**。

### 1.4 判定落在哪份文本上

- **主判据**：档案的**结构化规则**（`narrative['rules']` 的每个维度每条规则）——
  它能给出维度与原文，修复动作也作用在它上面。
- **可见性过滤**：一个词若在渲染块里被截断掉（`_clip` 按标点边界截断），
  模型就看不见它 ⇒ 不该为它挡生成。所以最终判据 = **结构化规则里的用法 ∩ 渲染块里看得见的词**。
- 截断不会把「下一刻」和「的」切开（`_clip` 只在标点处断，
  而「下一刻的」中间没有标点）⇒ 角色判定在两处一致。

## 2. 自愈入口：让用户能自己动手修档案

### 2.1 修什么

体检报出冲突时，用户要能在产品里点一下就改掉。三种修法：

| 修法 | 动作 | 适用 |
|---|---|---|
| `remove_word` | 在含该词的规则里**删掉这个词**（连同紧跟的「的」） | 默认推荐：规则还在，只是不再含禁用词 |
| `drop_rule` | 删掉含该词的**那一条规则** | 删词会把句子改坏时 |
| `unban` | 从禁用清单里**去掉这个词** | 慎用：削弱的是整本书的文风约束 |

修的是**项目当前应用的档案**（`projects.style_narrative`），
**不动蒸馏库条目**（库条目是全局共享的，替别人改档案不是用户该做的事）。

### 2.2 落点

- `GET /api/projects/{id}/style-narrative/conflicts` —— **只读**、不调模型：
  把冲突列出来（词、禁用分类、所在维度、那条规则原文），外加一个
  `can_generate`（现在生成会不会被挡住）。界面靠它渲染。
- `POST /api/projects/{id}/style-narrative/repair`
  - `{"word": "...", "mode": "remove_word"|"drop_rule"|"unban", "preview": true|false}`
  - `preview=true` ⇒ 只返回「将要改什么」（改前/改后逐条），**不落库**；
  - `preview=false` ⇒ 落库 + 留痕 + **重跑体检**并把新报告一起返回（当场自证修好了）。
- 界面：项目工作台第 ① 步的「文风蒸馏库」面板下面，加一块「文风档案检查」——
  一行提示说明「禁用词与正文自相矛盾 ⇒ 生成会被挡住」，
  一个「检查文风档案」按钮，冲突逐条列出，每条两个动作
  （「去掉这个词」/「删掉这条规则」）。

### 2.2.1 为什么不做成「助理的工具」

本项目的规矩是 **agent 只能提卡、不能落库**（改数据的事一律人点头）。
「修档案」是改数据 ⇒ 它是**人点的按钮**，不是助理能自己调的工具。
助理仍然可以用只读的 `audit_prompt` 把冲突报出来，并告诉用户「在项目工作台里可以改」。

### 2.3 留痕与可回退

档案里记 `repair_history`：每次修的**模式、词、维度、改前/改后原文**。
改动是「删除」，所以改前的原文就是回退所需的全部信息 ⇒ 不需要另存整份档案（几十万字）。

### 2.4 边界

- 档案不是 dict / 没有规则 ⇒ 明确报错，不静默成功。
- 词不在档案里 ⇒ 报「没找到这个词」，不做任何改动。
- 修完**必须**重跑体检并把结果返回：修好了就是没有 conflict issue，没修好要看得出来。

## 3. 抽取统计口径：把「模型吐了几条」和「落库了几条」分开

### 3.1 现在的口径（实测不准）

`agent_runs.note.batch_stats.foreshadows` 记的是**模型吐出的条目数**。
真机验收那次：note 写 `foreshadows: 11`，而账上实际是
**7 条同名复用、0 条新增** —— 模型在同一次响应里吐了重复的名字，
落库按 `(project_id, name)` 去重，重复的那几条落到已有行上。
读这份 note 的人会以为「新增了 11 条伏笔」。

### 3.2 新口径

| 字段 | 含义 |
|---|---|
| `foreshadows_extracted` | 模型吐出的条目数（今天的 `foreshadows` 语义） |
| `foreshadows_reused` | 命中账上已有的名字（同名复用） |
| `foreshadows_duplicate_in_batch` | 同一次响应里重复的名字 |
| `foreshadows_new` | 真正新落库的条数 |
| `foreshadows_near_variant` | 新落库中与某条老名字**高置信相似**的条数（子集） |
| `foreshadows_suspect` | 疑似对话碎片（既有，2026-10-28 加） |

恒等式：`extracted = reused + duplicate_in_batch + new`（守门测试会断言）。

### 3.3 「近似变体」的阈值：**0.50**，量出来的

账上 102 条真名字，两两算字符 bigram Jaccard，把高分对逐条看过：

```
0.889  断刀刀镡上的陌生姓氏   ||  断刀刀镡上的陌生姓            ← 同一件事
0.545  沈铁山临死前未说完的话 ||  沈铁山未说完的话              ← 同一件事
────── 下面是另一档（有的同一件、有的两件事，不能一刀切）──────
0.435  瘸腿男人、陈叔、周郎中与沈家在二十年前的旧事 || 周郎中与陈叔二十年前的旧事
0.429  沈铁山未说完的话 ||  沈铁山未说完的师承与断刀来历
0.417  断刀刀鞘上的陌生刻痕 ||  断刀刀镡上的陌生姓              ← 刻痕 ≠ 姓
0.400  断刀与铁链锁木匣之间存在异常共鸣 || 断刀与窄长木匣之间的异常共鸣
...
0.278  沈铁山临死前未说完的话 ||  沈铁山未说完的师承与断刀来历
0.167  断刀上的‘萧’字 ||  断刀上的“柳”字与柳家往事             ← 一字之差，两件事
```

（全部 5151 对的分位：p50=0.000、p90=0.050、p99=0.158、p999=0.400、max=0.889。）

⇒ **0.435 与 0.545 之间是一段空档**（这一段里没有别的对）⇒ 阈值取 **0.50**，
落在空档正中：两对「同一件事」收进来，「刻痕 vs 姓」「萧 vs 柳」这类**两件事**挡在外面。

再往下（0.15~0.30）**真同假混**（0.278 是同一件事、0.167 是两件事）
⇒ 宁可少报（放过），不可误报（把两条线索说成一条，比漏报更坏）。

> 记一笔踩坑：第一次量的时候用「四舍五入到 0.05 的直方图」看，
> 0.545 被归进了「0.55~0.60」桶，差点把阈值定成 0.55 ——
> 结果那一对（0.545）刚好落在阈值下面，**该报的没报**。
> 直方图是用来**找空档**的，阈值要用**原始数值**定。

判定与处置：**只计数 + 警告日志，不改账本**（沿用 2026-10-28 定的规矩：
抽取层只留痕，删数据要人点头）。

## 4. 验收项

1. **阳性对照**：标准转折词清单里的每一个词，用它的**连词用法**写进规则正文 ⇒
   必须全部判成 `error`（尺先自证，否则尺是坏的）。
2. **阴性对照**：「下一刻的细微反应」这种名词性用法 ⇒ 不判 `error`，判 `warn`。
3. 旧档案（蒸馏库 id=4 / 验收库两个项目）跑体检 ⇒ conflict 从 error 变 warn ⇒ **不再挡生成**。
4. 真档案（蒸馏库 id=2：「正文紧接着展开」）⇒ **仍然 error** ⇒ 真冲突照样挡。
5. `repair` 端点：preview 不落库；apply 落库并重跑体检，冲突消失；`repair_history` 有留痕。
6. 抽取口径恒等式成立；同名复用、批内重复、近似变体分别计数。
7. 界面链路：点「去掉这个词」⇒ POST 200 ⇒ 横幅消失、显示「已改动 N 处，检查通过」。
8. 全量 `python -m pytest tests/` 0 failed；前端 `npm test` + `npm run build` 通过。

## 5. 顺带修掉的一个真 bug（不在原计划里）

真机点按钮时发现 POST 返回 **422**，查下来是前端 `jsonInit` 的老问题：
不带 body 时**不设 headers**，调用方自己补 `body` ⇒ 浏览器发 `text/plain`
⇒ FastAPI 不当 JSON 解析 ⇒ 422。

⇒ **已发布的「应用到本项目」按钮从来就没通过**（蒸馏库这个主力入口在界面上等于不存在）。
后端接口一直是对的、前端类型检查一直过、CI 全绿 —— **真机点出来才发现的**。

改法：body 传进 `jsonInit`，让它决定 headers（顺带把真值判断换成 `!== undefined`）。
守门测试：`frontend/tests/jsonBodyContentType.test.ts`。
