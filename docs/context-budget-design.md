# 上下文预算：别再按「怕撑爆」设限（2026-11-01）

> 触发 = 主人一句「加大上限，模型一百万上下文问做的畏手畏脚的」。
> 状态：**设计稿**（P0 已落地的部分标 ✅，其余待实施）。
> 关联：`docs/final-distillation-design.md`（最终蒸馏）、`docs/style-log-buckets_design.md`。

---

## 0. 一句话

仓库里有**一批因为「怕上下文/体积撑爆」而设的保守上限**，
其中**一部分是假限制**（瓶颈根本不在那儿），**一部分是真限制**（瓶颈是 TPM 不是 context）。

⇒ 本设计的做法：**先量清每个限制的真实瓶颈，再决定动不动它**；
**绝不**因为「模型有一百万上下文」就无脑放大 —— 那会把 429 限流变成新的瓶颈。

---

## 1. 盘点：仓库里所有「怕撑爆」的限制

| # | 限制 | 位置 | 原值 | 真实瓶颈 | 处置 |
|---|---|---|---|---|---|
| 1 | 单本档案 JSON 体积 | `style/pipeline.py` `PROFILE_MAX_JSON_BYTES` | 32,768 | **不是瓶颈**（见 §2.1） | ✅ 已放开到 4MB |
| 2 | 蒸馏块字数 | `style/narrative.py` `TARGET_BLOCK_CHARS` | 20,000 | **TPM**（默认渠道约 28K TPM） | ⏳ 见 §3 |
| 3 | 角色卡取材窗口 | `style/narrative.py` `budget = 6000` | 6,000 字 | 角色抽取要**聚焦** | ⏳ 不动（理由见 §4.3） |
| 4 | 提示词覆写单条长度 | `agents/prompt_overrides.py` `MAX_OVERRIDE_LEN` | 4,000 | 防注入/爆库 | ⏳ 不动（理由见 §4.3） |
| 5 | ReAct 工具参数长度 | `agents/react_loop.py` `MAX_ARGUMENT_CHARS` | — | 防退化调用打穿上下文 | ⏳ 不动（理由见 §4.3） |
| 6 | 前情块 / RAG 上下文裁剪 | `generation/` | 有界 | **每次生成的输入成本** | ⏳ 不动（理由见 §4.3） |

**关键判据**：一个限制该不该放大，看它的**瓶颈是不是 context window**。
不是 ⇒ 放大它只会把问题从一头挪到另一头。

---

## 2. 已实施：放开档案体积上限（✅）

### 2.1 为什么 32KB 是**假限制**

原注释的理由是：「档案要存进 JSON 列、还要在预检响应里下发摘要，膨胀到几十 KB 会让两边都难受」。

这条理由**早已不成立**：

- **预检响应刻意不下发整份档案** —— `routers/generation._style_profile_digest`
  只挑固定字段（`MARK_FIELDS` 等），档案再大也不影响预检响应；
- **JSON 列没有 32KB 限制** —— `Column(JSON)` 落 SQLite TEXT / PostgreSQL JSONB，
  上限是 MB 级。

### 2.2 而这个上限的**实际代价**很实在

规格书（34 项，10.5KB）塞不进 32KB 的档案 ⇒ 两条路都不好走：

- 把规格书踢出档案（它本该是可复用的产物，设计稿 §3.6 明写「规格书可以独立缓存」）；
- 或者让大档案「静默超限」—— 实测《十日终焉》**去掉规格书也有 36KB**，
  四本合集 44KB ⇒ 多本参考书的项目本来就超。

### 2.3 改法

`PROFILE_MAX_JSON_BYTES`：32,768 → **4MB**。

**上限的语义变了**：从「档案要瘦」改成「**病态输入兜底**」——
远超任何真实档案（四本合集实测 55KB），但不会误伤。

同时改掉 `verify_style_pipeline.py` E 段的措辞（它还在引用旧理由）。

## 3. 待实施：蒸馏块大小跟着**渠道能力**走（⏳）

### 3.1 现状与它的真实代价

`TARGET_BLOCK_CHARS = 20_000`，原注释：「2 万字时模型能稳定输出 7 维规则且不截断；
再往上（4 万字）rejected 明显上升」。

**代价**：一本 110 万字的书（30% 采样 → 33 万字 → 17 块）× 每块多次调用
⇒ 实测 833 章完整档 **42 分钟**；「全量」档按此推算约 **2 小时**。
主人的诉求「百万字压缩成十万字」「整本投喂」在 2 万字/块下**根本做不到**。

### 3.2 为什么在**默认渠道**上不能直接放大

蒸馏链路的默认渠道是 **distiller 角色 → 智谱 GLM-4-Flash**，
而它的实测约束（`provider.py` `ZhipuChatProvider`）是：

```
并发 1  4/4   成功，15K TPM
并发 2  8/8   成功，27K TPM   ← 上限
并发 3  4/12  成功，8 个 429，32K TPM
```

⇒ **瓶颈是 TPM（每分钟 token），不是 context window**。
把块从 2 万字放大到 20 万字 ⇒ 单次请求 token 涨 10 倍 ⇒ 429 立刻变多，
**净效果是更慢，不是更快**。

⇒ 这就是「怕撑爆」这个直觉的**真实来源**：它不是拍脑袋，是被 429 教出来的。
但它教错了对象 —— 该放开的是**换渠道**，不是**换块大小**。

### 3.3 改法：块大小由**渠道的实测能力**决定

给 provider 增加一个能力声明：

```python
class LLMProvider:
    #: 该渠道**单次请求**能安全吃下的输入字数（蒸馏块按它装箱）。
    #: 0 = 未声明 ⇒ 用保守默认值。
    #:
    #: 为什么是「实测」而不是「厂商标称」：厂商标的 context window 是**能收**的上限，
    #: 不是**能用**的上限 —— 超了会被截断或 429，而截断会静默产出半截结果。
    distill_block_chars: int = 0
```

各渠道按**实测**填：

| 渠道 | 依据 | `distill_block_chars` |
|---|---|---|
| 智谱 GLM-4-Flash | 28K TPM ⇒ 单请求 2 万字已接近上限 | 20,000（现状不变） |
| OpenRouter nemotron-ultra | 注释已写「1M 上下文」，长文用 | **待实测** |
| MiniMax M3.1 | 实测 114K TPM（并发 15） | 按 TPM 反推 |

**未声明 ⇒ 保守默认 20,000**（现状不变 ⇒ 不会因为这次改动而让任何现网行为变差）。

### 3.4 验收口径

1. **块大小真的跟着渠道走**：换 provider ⇒ 块数变化，**用同一份语料**。
2. **rejected 率不上升**：块放大后，规则的证据通过率不能比 2 万字时更差
   （这才是「模型能处理这么大」的判据 —— 不是「请求没报错」）。
3. **墙钟时间真的下降**：同一本书，块放大后总耗时更短（否则放大没有意义）。
4. **不牺牲规则数**：规则条数不显著下降（视野变大不该让规则变少）。

### 3.5 与 P1（蒸馏范围轴）的关系

P1 要加「全量」模式。全量 × 每块 2 万字 = 几十块；
全量 × 每块 20 万字（1M 上下文的渠道）= 5~8 块 ⇒ **成本差一个数量级**。

⇒ **P1 的「全量」档必须与本节的「块大小跟着渠道走」一起做**，
否则「全量」只是把 2 小时的等待拉长，没有实际意义。

## 4. 不动的限制，以及为什么

### 4.1 前情块 / RAG 上下文裁剪

这些裁剪控制的是**每次生成的输入成本**，不是「能不能塞进去」。
1M 上下文下塞满 100 万字，每次生成都要重付这笔钱 ⇒ 成本上升而质量未必提升。

⇒ **不动**。（且仓库已有「前情无洞」的证明机制，动它要重跑那条验收。）

### 4.2 提示词覆写单条 4,000 字

这是**用户输入**的边界（防注入、防爆库），不是「模型吃不下」。

⇒ **不动**。

### 4.3 角色卡取材窗口 6,000 字

这个窗口的目的是**聚焦**（`roleplay/bio.py` 的「最像一件事」判据）：
取材太宽 ⇒ 抽出来的不是「这个角色在做什么」，而是「这章有什么」。

⇒ **不动**（放大它会**损害**质量，与上下文大小无关）。
