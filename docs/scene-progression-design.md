# 生成侧场景推进与叙事档案可读性修复

## 问题（五章实测，v3）

修完切分/场景分类/蒸馏 prompt 后重跑蒸馏（570 条规则、零审核问题），
生成五章的结果是：

| 层面 | 结果 |
|---|---|
| 文风 | 成功。句长 27.2、对白 238 处、AI 腔 0、参考语料专名 0 |
| 剧情 | 失败。第 3/4/5 章全部困在「船上 + 黑水 + 陈叔」同一场景 |

大纲要求第 3 章客栈、第 4 章药铺、第 5 章追兵走水路，实际三章都在船舱。

## 根因分析（三个独立原因，都要修）

### 原因 1：叙事档案被压成 894 字的一句话

`describe_narrative` 把 13 个维度各取 2 条规则，用「；」「、」缝成一段：

```
参考作者的行文习惯是：用夸张的外貌反衬人物内在…；人物之间大量使用带地域色彩的称呼…；
极短段占绝对主导…；空间切换以人物走位作为硬切标志…；父爱等强烈情绪不直陈…；
对话密集段突然插入长篇背景铺陈…；官职门派兵器等级通过角色对白自然带出…；
伏笔通过器物异常埋设…；悬念以揭示一半+暗示另一半…；铺垫、升温；来客提出安排→主人
预先铺垫→目标者拒绝或僵持→居中者介入并说服→目标者接受、归来者抵达→…；反话正说、
转移话题；场景开场先交代空间格局与社会声量…
```

**维度边界完全消失**。模型分不清哪句是「节拍」、哪句是「场景套路」、哪句是
「语序编排」，只能抓住最显眼的动作链反复执行。

历史包袱（v2.274 的结论）说「散文式一段话」最好，因为 `【维度】` 小标题会让模型
把维度名当正文小标题写进小说。那个结论针对的是**方括号标记**，不是「分维度」本身。
用不带方括号的自然语言标签分行，两个问题都能避开。

### 原因 2：大纲是「全量参考」，没有「本节目标」

`build_user_prompt` 把 `project.outline` 整条渲染成 `- 第N章 …` 列表，
7 章全给，续写指令只说「不要重复前情提要里已经写过的场景」——软约束。

模型手里有全部 7 章，又刚写完「上船」，顺势就继续写船。它没做错什么：
prompt 里没有任何东西告诉它「本节该写第 3 章客栈」。

时间线模式（`node_prompt`）本来能解决这个，但只对有 `timeline` 节点的项目生效；
普通列表大纲的项目走不到那条路。

### 原因 3：蒸馏规则「同一动作重复加重」被字面执行

叙事档案里有一条（蒸馏自参考语料）：

> 冲突升级以同一动作的重复描写逐步加重力度，避免一次写尽

模型完全照做：三章都在「陈叔爬船」这一个动作上加重力度。

规则本身是真实文风特征，但缺少对冲约束。需要一句通用的限定：
单节内同一动作最多两次，加剧要换手段或换场景。

## 方案

### 1. 叙事档案分维度渲染（`narrative.py::describe_narrative`）

改成每维一行、带自然语言标签、不带方括号：

```
叙事手法（下面每行是一种，讲的是怎么写，不是要写的内容）：
人物——用夸张外貌反衬身份反差，以连续动作替代静态心理
对白——长对白用连续转折和反问制造调侃，不追求简洁写实
分段——极短段占主导，段间用动作或场景切换代替连词
场景——环境描写集中于器物陈列，而非自然风光
情绪——强烈情绪不直陈，借自嘲动作或对白调侃承载
节奏——对话密集段插入长篇铺陈制造停顿
设定——官职门派等级通过角色对白带出
情节——冲突由对话来回拉锯升级，旁观者评论调节节奏
伏笔——通过器物异常埋设
节拍——铺垫 → 升温 → 僵持
场景套路——来客抵达→主人接待→试探交谈→达成或谈崩→一方离去
潜台词——反话正说；转移话题
语序——场景先交代空间格局，再缩小到人物；新场景以时间或光线定位
```

关键约束：

- **不用 `【】`、不用 `·`、不用 `1. 2. 3.`** —— 这三种都会被模型当成正文小标题
- 每维最多 2 条，每条截断到约 42 字（长句压成短语）
- 总长上限 1200 字，超出按维度顺序截断（后面的维度对文风贡献小）
- 标签用 `——` 连接，是自然语言，不是结构化标记

同时保留一条**通用防重复约束**（解决问题 3）：

```
单节内同一动作最多重复两次；要加剧就换手段或换场景，不要靠反复描写同一个动作拉长篇幅。
```

### 2. 大纲本节目标（`prompts.py::build_user_prompt` + `engine.py`）

新增两个可选参数（默认 `None`，四个调用点全部向后兼容）：

- `segment_no: int | None` —— 当前写第几节
- `prev_scene: str | None` —— 上一节尾部的场景要素（几个词）

行为：

1. 大纲列表里给当前项打标：`→ 【本节】`，并在前面插入目标块

```
【本节大纲目标】
本节要写第 3 项：「第三章 客栈：三名刀客围住沈砚要刀…」
必须在本节内完成这一项的事件；标题里的地点、人物、事件不能替换成别处。
上一项（已写完，不要重写）：第 2 项：…
```

2. 续写指令追加场景推进硬约束：

```
本节必须发生场景转移：上一节结束在「船、水、木匣、刀」这些要素上，
本节不得继续以它们为主要场景。若本节大纲要求的地点与上节不同，
必须在本节前三分之一内完成转移。
```

`prev_scene` 的来源：取上一段正文尾部的 600 字，用 `scene_signature()`
按 `SCENE_KEYWORDS` 命中数排序取前 5 个词。零 LLM，本书语料自适应
（沿用已有的词表，不新增题材依赖）。

### 3. 不做的事

- 不改蒸馏产物内容（规则是数据，不因为生成侧问题去改数据）
- 不加运行期 LLM 判断（如「这章是否推进了剧情」）——成本高、不稳定
- 不动时间线模式（`node_prompt`）路径，它对有 timeline 的项目已经正确

## 验收

1. 单元测试：分维度渲染不含 `【】`/`·`/编号；每维一行；总长受限；
   大纲目标指向正确的项；`prev_scene` 命中上一段真实场景要素
2. 五章实测（同一故事、同一蒸馏产物、M3 + 改写），对比 v3：
   - 第 3/4/5 章不应再困在同一场景（关键词分布变化）
   - 各章开头对应的地点与大纲一致
   - 文风指标不退化（句长 ≥ 27、AI 腔 0、专名 0）
3. 全套件 63+ 个测试文件保持绿
