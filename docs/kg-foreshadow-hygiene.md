# 伏笔进入提示词的卫生：不重复、有界、不造假（设计稿 · 2026-10-28）

## 这份文档回答什么

上一轮把提示词里三块噪声治了（实体 context 压成完整句、对话碎片伏笔不进约束块、
空关系不列 `None`）。当时留下**这一块没动**：KG 切片里的【未回收伏笔】。

现在数据量齐了，可以定方案。**先说结论：上一轮我对这块的判断错了一半**——
我以为是「大量近义重复」，实测**不是**。

---

## 一、实测（同一份验收库数据、同一段渲染代码）

| 项 | 实测 |
|---|---|
| 账本伏笔 | **102 条**（9 段正文抽出来的） |
| 其中 active（planted/developing） | **97 条** |
| 切片【未回收伏笔】块 | **97 行 / 2,639 字** —— 占 user 提示词两成 |
| 字符层面近义重复 | **只有 6 对 / 3 簇**（bigram Jaccard ≥ 0.4） |
| 按埋下章归并 | 第 1 章 33、第 2 章 26、第 3 章 21、第 4 章 22（`planted_chapter` 是模型自报的，按段归并不是按章） |
| 单段抽取条数（真跑） | **3~5 条** |
| 永不到期 | 102 条里只有 3 条 `paid_off`、2 条 `dropped` |

**所以重复不是字符级的，是语义级的** ——「断刀刀镡上刻有的字」「断刀镡上半边不认识的姓」
「刀镡半个残字的真实身份」在字面上几乎不重叠（Jaccard 0.2 上下），但说的是同一件事。
按字符去重这条路**只能捞到 3 簇**，不值得做。

真正的病是**无界增长 + 名字每段重新发明**：抽取器每段独立给同一件事起一个新名字，
而切片把**全部** active 伏笔一条不落地渲染出来。

### 顺带查出来的第二处造假

| `planned_payoff_chapter` | 条数 | 判断 |
|---|---|---|
| `0` | **72** | **第 0 章不存在，不可能** |
| `50` | **18** | **等于抽取提示里 JSON 示例的字面值 50** |
| `12` / `30` | 各 1 | 可信 |
| `None` | 5 | 空 |

- 72 条同时满足**一般不变式**「回收章 ≤ 埋下章」⇒ 一条与剧情无关的通用规则就能判死。
- 18 条 `50` 是**示例值泄漏**：`docs/journey_glm_versions_compare.json` 里能直接看到
  模型把示例整行照抄（`{"name": "公司收购", "status": "planted",
  "planted_chapter": 1, "planned_payoff_chapter": 50}`）。
- 后果：切片的 97 行里有 **18 行**写着「计划第 50 章回收」，
  等于给模型下发了一条**编出来的约束**。
- 好消息：`0` 在渲染时被 `if f.get(...)` 挡掉了（0 是假值），所以它没进提示词；
  它污染的是账本与界面。

## 二、三条路

| | 做什么 | 治什么 | 代价 / 风险 |
|---|---|---|---|
| **A 抽取契约** | 抽取时把**现有未回收伏笔名单**给模型，要求「已有线索**同名复用**、只抽本段**新埋**的」；回收章只在文本明确时填、**不许照抄示例** | **根因**（名字每段重新发明） | 改抽取行为，要用真跑验证；名单会占抽取 prompt 预算 |
| **B 渲染层压缩** | 伏笔块从「名字（状态，计划第 N 章回收）」压成更紧凑的格式 | 块的字数 | 会丢掉状态/回收章的展示（但回收章 82% 是假的） |
| **C 渲染层预算** | 给这一块设**条数上限**，超了按某个顺序截断 | 块的上界 | **截断 = 决定模型看不到哪些线索**，这是政策不是守卫 |
| **D 归一化不变式** | 落库前判死不可能值（`回收章 ≤ 埋下章`、`回收章 = 0`）⇒ 当作未知 | 那 72 条 + 18 条假约束的下游影响 | 几乎零；但**只作用于新抽取**，历史数据不动 |

### 数字（同一份 97 条数据）

| 做法 | 块大小 | 省 |
|---|---|---|
| 现状 | 2,639 字 | — |
| B 紧凑格式（只列名字） | 1,457 字 | **44%**，**一条线索都不丢** |
| C 上限 30 条（最近优先） | 820 字 | 69%，但**丢掉 67 条**（第 1~3 章的全部线索） |
| C 上限 60 条（安全阀） | 1,648 字 | 38%，丢掉 37 条 |

**关于顺序的一个坑**：按「最近埋下的优先」截到 20 条，留下的**全是第 4 章**、
把第 1~3 章的**全部铺垫**丢掉 —— 对一个要写第 5 段的模型来说这恰恰是最坏的丢法
（大纲往往要靠前面的铺垫）。按现状的「埋下章升序」截，丢的又全是最新的。
**两种固定顺序都有明显坏处** ⇒ 上限只该当**安全阀**，不该当主要手段。

## 三、建议的组合

**A + B + D，C 作为宽松安全阀。**

1. **A（根因）**：抽取器拿到「当前未回收伏笔名单」，被要求同名复用。
   - 这是**通用**做法（不是给这一篇打补丁）：提示词的 `upsert` 本来就是按名字去重的，
     缺的只是「让模型知道已有名字」。
   - 预期：同一件事不再每段新建一条 ⇒ active 条数从「每段 +25」降到接近故事真实线索数。
2. **D（不变式）**：`回收章 ≤ 埋下章` 判为不可能 ⇒ 归一化成未知；
   同时**不从示例里给具体数字**（`planned_payoff_chapter` 示例改成说明性写法），
   并在规则里写明「没有明确回收章就留空，不要照抄示例的数值」。
3. **B（渲染层压缩）**：块压成紧凑格式，省 44% 且不丢线索。
4. **C（安全阀）**：上限设得宽（默认 60 条），触发时**如实写出省略了几条**，
   不静默隐藏。它只在抽取层失灵时兜底。

### 边界（明确不做）

- **不改历史账本**：那 72 条 `0` + 18 条 `50` 仍在库里（`D` 只作用于新抽取）。
  这是与上一轮一致的纪律：清理已积累的数据要人点头。
- **不做语义聚类合并**：需要embedding/模型判断，误合并会**把两条真线索并成一条**，
  代价比「多占一行」大得多。
- **不给抽取 prompt 加硬性条数上限**（比如「每段最多抽 3 条」）——
  那等于让模型为了凑数而丢真线索。

## 四、验收怎么算过

1. **抽取层真跑**：同一段真实正文，用**新契约**跑一遍抽取，
   看**新增名字数**是否显著下降（对照：旧契约第 1 章 33 条）。
2. **不变式**：造 `回收章 ≤ 埋下章` 的输入，断言落库为未知；
   `0` 同样判死。
3. **渲染层**：同一份数据，块大小从 2,639 字降下来；**一条线索都没丢**（条数不变）。
4. **安全阀**：造一个超上限的输入，断言渲染**如实写出省略条数**、且截断顺序是文档写的那一种。
5. **默认路径**：伏笔块的内容与现在**逐条一致**（除格式）——
   不给没批准的行为变化搭车。

## 五、落地结果（2026-10-28）

### 采纳的组合：**A + B + C + D**

| | 做什么 | 状态 |
|---|---|---|
| **A** | 抽取时给「账上已有的未回收伏笔名单」，要求同名复用、只抽本段新埋的 | ✅ 落地 |
| **B** | 渲染层压成**只列名字**（不陪标状态与回收章） | ✅ 落地 |
| **C** | 切片加**条数上限 60**（安全阀），触发了如实写出省略数 | ✅ 落地 |
| **D** | 归一化不变式：说不通的回收章 ⇒ 当作未知 | ✅ 落地 |

### 真跑对照（三臂，同一批真实正文、同一模型 MiniMax-M3）

A 臂的提示词**从 git HEAD 取**（不手抄），三臂只差「提示词」与「给不给名单」：

| 臂 | 抽取提示 | 给名单 | 6 段后账本 | 抽出合计 | 复用 |
|---|---|---|---|---|---|
| A | 原始 | 否 | 26 条 | 26 | 0 |
| B | 新 | 否 | 24 条 | 24 | 0 |
| **C** | 新 | 是 | **18 条** | 31 | **13（42%）** |

### 真跑之二：重复抽取一遍（真实增长机制）

验收库的 117 条账本里有 **117 个不同的 created_at**（成小组出现）
⇒ 后台 worker 对同一批段落**反复抽过很多轮**。真正的增长机制是
**每重抽一轮就多一批同义新名字**。

同样 6 段**再抽一遍**：

| 臂 | 第 1 遍 | 第 2 遍 | **第二遍又长** |
|---|---|---|---|
| A 原始提示（无名单） | 31 条 | 52 条 | **+21** |
| C 名单放 **user** 消息 | 18 条 | 26 条 | **+8** |
| **C′ 名单放 system 消息** | **12 条** | **15 条** | **+3** |

**名单位置有显著差异**：放 user 消息（正文之后）时，第二遍那 8 条多数是
同一线索换了说法；挪到 **system 消息**（与「必须沿用原名」这条规则同一段上下文）后，
同样的重抽**只长 3 条**。抽取这条路**不走提示缓存**（普通 HTTP + JSON，
没有 cache_control）⇒ 放 system **零缓存代价**。

### 渲染层效果（同一份数据、同一段渲染代码）

| | 改前 | 改后 |
|---|---|---|
| 【未回收伏笔】块 | 97 行 / 2,639 字 | **60 行 / 876 字**（+ 一行「另有 37 条未列出」） |
| 假的「计划第 N 章回收」 | **18 条**（0 与示例值 50） | **0**（整个不进提示词） |
| 提示词总字数 | 13,096 | **11,326（-13.5%）** |

- **不做语义聚类合并**：要 embedding/模型判断，误合并会**把两条真线索并成一条**，
  代价比「多占一行」大得多。
- **不给抽取 prompt 加硬性条数上限**：那等于让模型为了凑数而丢真线索。
