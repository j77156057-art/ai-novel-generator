# L2 角色档案接入蒸馏主流程

## 目标

全量/平衡档蒸馏在既有通用文风规则（`rules`）之外，按主要角色单独抽取可供续写和角色聊天使用的档案，并作为 `characters` 层持久化到同一份叙事档案 JSON。

## 设计决策

- 使用蒸馏已有的图谱候选和清洗策略，不另建角色识别器。
- 每本参考语料独立处理，档案项保存 `novel_id`，不跨书混合角色。
- 每个角色独立调用已有 `character_profile` prompt，避免一个多角色 prompt 导致字段过浅。
- 每个角色最多使用 6 个高频出场章节；每章取首次命中角色附近的局部窗口，总输入约 6K 字，避免长章造成 token 膨胀。
- 完整/平衡蒸馏对各自的前 8 个主要角色生成 L2 档案；快速档不增加该成本。
- 单角色失败只记日志并跳过，不中断该书其余维度。
- 档案保留 `source_chapters`，便于追溯事实依据。
- 叙事版本递增，确保旧缓存不会静默跳过 L2 重算。

## 输出形状

```json
{
  "rules": {"对白风格": []},
  "characters": [
    {
      "name": "角色名",
      "身份": "...",
      "说话方式": "...",
      "行为倾向": [],
      "性格底线": [],
      "关系网": {},
      "关键经历": [],
      "novel_id": 1,
      "source_chapters": [12, 18]
    }
  ]
}
```

既有消费者读取 `rules` 不变；新增 `characters` 是独立顶层层，不将具体人物信息误混入可迁移文风规则。

## 验证

- helper 单测验证逐角色调用、七字段规范化、来源书籍与章节落盘。
- `project_narrative` 使用版本号失效旧缓存；蒸馏库保存完整 profile JSON，因此 `characters` 随 profile 一起保存与复用。
- 完成后需要对真实语料强制重蒸馏，检查主要角色覆盖率、档案字段完整率、关系网/经历依据以及新增 LLM 调用与 429 情况。
