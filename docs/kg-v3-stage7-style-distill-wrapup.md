## 1. 本轮解决的三个真问题

### 1.1 全本 588 万字蒸馏跑不通 → 14.3 min 跑通

**问题**：v2.225 用 100% 全量跑斗破 588 万字，fit profile 阻塞超过 1800s client timeout，失败。

**根因**：跑错档位。之前会话的「全本蒸馏」是 **v7 完整档 15% 百分比采样**（大奉 510 万字采 764 章、42 min 跑通），不是 100% 全量。v2.225 自创了「100% 整本」这个不存在的档位。

**修复**：走回 v7 完整档（15% 采样），配合并发改造：
- `7dd7dc9` 每 chunk 内部 5 个 LLM 调用并发（`_gather_chat` + semaphore 限流 5）
- `c555535` chunk 间并发（flat_prompts 一次 gather 后按 ci 桶回）
- `39975ac` 角色声音 extraction 并发（11 次串行 → 1 次 gather）

**实测结果**：
| 版本 | 语料 | 耗时 | 采样 |
|---|---|---|---|
| v2.225 | 斗破 588 万字 100% | timeout | 全量 |
| v2.226c | 斗破 588 万字 15% | 23.2 min | 958 章 |
| v2.227e | 斗破 588 万字 15% | **14.3 min** | 958 章 |

并发改造实际加速 1.6x（23.2 → 14.3 min），不是理论 5x——智谱免费档 5 req/s 限流是硬天花板。

### 1.2 角色声音维度静默 0 条 → 12 条

**两层嵌套 bug**，都不是报错型故障，属于「静默无效」：

**第一层 `57f42d3`**：蒸馏入口不建参考语料图谱。
`_build_character_name_index` 唯一数据源是 `KgNode(type="character", source=f"novel:{nid}")`，
这张图由 `kg/build.py::build_graph`（纯规则、零 LLM）建，入口是前端「建图」按钮。
用户直接蒸馏 → 图谱不存在 → 候选池空 → `_extract_character_voices` 在
`if not char_names: return []` 静默返回空。

修复：`extract_narrative_profile` 主循环前置 `_ensure_reference_graphs()`，
逐本检查 character 节点数，为 0 才建（幂等），失败只记 warning 不阻断。

**第二层 `b9bdc41`**：候选池判据 `(speaking or mentions>=200) and mentions>=10` 双向失效。
- 漏真角色：`speaking` 是「至少命中一次『名字+言说动词』」的一次性布尔值，且
  `_SPEAK_RE` 要求两者**紧邻**。网文写法「萧战叹了一口气，沉默了片刻，忽然道：」
  中间夹状语，正则不命中 → 77 个节点只有 4 个 speaking=True
- 收伪角色：其中 2 个是「满脸冷笑道」「冷笑一声」
- `mentions>=200` 兜底在 30 章语料上只有萧炎（1265 次）过线

修复：改为纯 mentions 排序 + `_FAKE_CHARS` 黑名单 + 子串归一。probe 实测取前 30 名
覆盖 7/7 真角色。

**实测结果**：
| 指标 | 修复前 | 修复后 |
|---|---|---|
| character 节点 | 0 → 77（建图） | 0 → 77 |
| 角色声音词典 | 2 条 | **12 条** |
| 14 维度有产出 | 13/14 | **14/14** |

女主萧薰儿终于进池，提取结果与原著一致：
「自称『我，薰儿』口头禅『薰儿、萧炎哥哥』语气温柔，关切，清雅
节奏停顿，欲言又止 关系动态：对萧炎温柔，对萧媚冷淡」

### 1.3 文笔量化审计维度冗余 → 改零 LLM

**问题**：该维度是 L1 `stylometry.py` 20 个特征的文字复述，让 LLM 再读一遍原文
「审计文笔」属于重复计算。

**修复 `7821ad6`**：
- 新增 `build_deterministic_features()`：零 LLM 算六类硬指标（句长/段落/对白/
  情绪/场景/悬念）
- 该维度改由它生成，从 LLM 输出 schema 中移除
- extract prompt 的 user 前置这段硬指标，并写明「数字已算出，不要再估数，
  你的任务是解释作者为什么这样写」

**关于提速——实测没有提速，反而略增**：
| 项 | 实测值 |
|---|---|
| 新增输入前缀 | 311 字（占块 2.40%）|
| 省下输出 token | ~180 字（该维度原 3 条 × 60 字）|
| 净变化 | **+131 字/块** |

原因：该维度与其余 10 个维度**共用同一次 extract 调用**，移除它只减输出 token，
不减少调用次数。收益在别处：指标精确、LLM 输出被数字锚定、LLM 失败时仍有产出。

## 2. 被 probe 证伪的方案（勿重复尝试）

### 2.1 言说动词邻接率做候选池判据

**假设**：真角色后接言说动词的比例高于虚词。

**第一次实现**：复用 `kg/extractor.py::_SPEAK_RE` 逐名统计。
**结果**：斗破 30 章全部角色邻接率为 0。该正则要求名字与动词紧邻，网文实际
写法中间夹状语，几乎不命中。

**第二次实现**：窗口式（名字前后 N 字内出现言说动词或引号）。
**结果**：window=2/3/4/5/6/8 全部不可分——

| 名字 | 邻接率 | 真实身份 |
|---|---|---|
| 冷笑 | 0.929 | 伪角色 |
| 萧族 | 0.900 | 伪角色 |
| 闻言 | 0.529 | 伪角色 |
| 萧宁 | 0.077~0.128 | 真角色 |

伪角色分数反而高于真角色。原因是这些词本身就常出现在言说动词旁边，而真角色的
高频出现多是「萧炎的」「萧炎心头」这类所有格/主语位——排除所有格后真角色分母
骤减，比率反而难看。引号信号更糟：引号在网文里几乎遍地。

**结论**：放弃比率判据，改用 mentions 排序 + 黑名单。

### 2.2 段落编排/节奏控制/情绪表达完全规则化

**假设**：这三个维度可以纯规则提取，省掉 LLM 调用。

**probe 结果**：规则能算出骨架——
- 段落编排：1-2 句短段占 92.4%、对白开头段 33.8%、段长 mean 57 字
- 节奏控制：句长 45.4±31.5、短句占比 2.4%、最长连续短句 1 句
- 情绪表达：直陈 0.23/千字 vs 动作承载 1.24/千字，比值 0.18
- 对白风格：657 句、平均 26 字、短对白 33%、长对白 13.5%

但算不出「为什么这样写、起了什么叙事作用」——那仍是 LLM 的价值。

**结论**：没有砍这三个维度的 LLM 调用，只加了事实前缀。

## 3. 多 provider 提速的评估结论

用户提供的 鑫旺Neko API（`https://api.790053500.com/v1`）当前不可用：

| 检测项 | 结果 |
|---|---|
| `GET /v1/models` | 200，返回 6 个 DeepSeek 模型 |
| 不带 key | 401 `API_KEY_REQUIRED`（鉴权链路正常）|
| 请求未配置的模型（gpt-4o-mini）| 404 `model_not_found`「not supported by any configured account in this group」|
| **6 个 DeepSeek 模型全部调用** | **502 `Upstream access forbidden`** |

**结论**：key 和账号有效（models 列表能拿到、鉴权通过），是平台侧到上游 DeepSeek
的转发被拒。试过标准 Bearer / x-api-key / stream=true / 无 max_tokens /
带 temperature / system+user 全部同一 502，排除调用方式问题。

需用户在平台后台确认模型是否需单独开通，或等待平台修复上游。

**架构已预留**：`_gather_chat` + `_DEFAULT_MAX_CONCURRENT` 已是多 provider 基础，
等有可用 key 时，接入只需在 `providers.yaml` 加条目 + `_gather_chat` 改轮询。
