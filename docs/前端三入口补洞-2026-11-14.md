# 三项档 3 能力的前端显式入口（语料清洗 / 快照回滚 / 批量应用提案）

## Context

`action_catalog.py` 已把 `clean_corpus`、`snapshot_rollback(_group)`、`proposal_apply_selected`
登记为 `frontend_only`（档 3），但三者的 `frontend_entry` 都写着「当前未接」——后端端点齐备，
前端没有任何入口，用户根本用不到。档 3 的前提是「前端保留显式入口 + 二次确认 + 可核对结果」，
本轮把这三个洞补上；**不允许从对话框直接触发**（助手仍只能引导用户去页面）。

另一条本轮只记待办：provider 无 function calling，模型不能自主调用工具，`list_actions`
只解决「目录存在」，没解决「模型主动用」。

## 后端契约（只读参考，不改语义）

| 能力 | 端点 | 关键约束 |
|---|---|---|
| 语料清洗 | `POST /api/assistant/clean-corpus` | 不写 `novel_chunks`；只产 `pending` 提案；`limit` 1–200 默认 20；单次最多 50 条提案；命中判据才送模型；落 AgentRun |
| 快照列表 | `GET /api/assistant/snapshots?project_id&status=applied&limit` | 项含 `id/segment_no/generation_id/batch_id/operation/status/before_chars/after_chars/before_hash/undoable/created_at` |
| 整组列表 | `GET /api/assistant/snapshots/groups?project_id&limit` | 项含 `batch_id/operation/created_at/segments[]/applied/failed/rolled_back/undoable` |
| 单段回滚 | `POST /api/assistant/snapshots/rollback` | body `{project_id,snapshot_id,mode}`；成功含 `restored_snapshot_id/rollback_snapshot_id/segment_no/chars/warnings/derived` |
| 整组回滚 | `POST /api/assistant/snapshots/rollback-group` | body `{project_id,batch_id,mode}`；成功含 `segments[]/count/warnings/derived` |
| 提案列表 | `GET /api/assistant/proposals?project_id&status=approved&limit` | 返回 `{count, proposals[]}`；项含 `id/type/target_kind/target_id/risk_level/reason/after_text/diff/impact/status` |
| 批准 | `POST /api/assistant/proposals/{id}/approve` | body `{action:"approve"}`；只改状态，不写业务表 |
| 批量应用 | `POST /api/assistant/proposals/apply-selected` | body `{action:"apply", proposal_ids[]}`；显式枚举、`MAX_BULK_APPLY=50`、任一 stale/blocked → 409 且整批零写入；成功 `{applied[],stale[],blocked[],reason}` |

409 结构：回滚 `detail={code,message,...}`，`code` ∈ `bible_changed_since_snapshot`
（带 `options[]`）/ `text_drifted` / `batch_not_rollbackable`；批量应用 `detail={ok:false,stale[],blocked[],reason}`。

### 2. `frontend/src/api/client.ts`

在上次的「已从前端收起」注释旁补回 **7 个显式入口专用封装**（不是恢复死封装，是给档 3 页面用）：

```
cleanCorpus(body)                      -> POST /assistant/clean-corpus
listSnapshots(projectId, status?, limit?)
listSnapshotGroups(projectId, limit?)
rollbackSnapshot(body)
rollbackSnapshotGroup(body)
listProposals(projectId, status?, limit?)

```

约定：`actor` 由 UI 传固定串（`"ui:corpus"` / `"ui:workspace"`），注释写明来源。

### 3. `frontend/src/views/CorpusView.vue` —— 语料清洗入口

新增一张 `section.card`「语料清洗（规则 + 模型复核）」，放在「已入库语料」之后：

- **入口可见**：无选中语料时按钮禁用并提示「先选中一本语料」；选中后显示「扫描并复核」。
- **表单**：`limit` 数字（默认 20，1–200，注明来自后端 `MAX_CLEAN_CHUNK_LIMIT`）、
  `dry_run` 复选框（「只检测，不创建提案」）。
- **二次确认（模态）** 文案固定四段：
  1. 扫描对象：语料《{title}》(novel_id={id})，最多 {limit} 个分片（按 idx 升序）；
  2. 数据影响：**不写 novel_chunks**；本次最多创建 {min(limit,50)} 条 `pending` 提案（每命中分片最多 1 条）；
     要生效必须再到「待应用提案」批准并应用；
  3. 模型调用：八条确定性判据先跑，只有命中可复核判据的分片才送模型；模型不可用会降级并标注；
  4. 留痕：写一条 AgentRun。`dry_run` 勾选时额外一行「本次只检测，proposal_count 将为 0」。
  按钮：取消 / 确认扫描。
- **执行后可核对**：`chunks_scanned`、`findings_by_rule` 逐判据计数、`proposal_count` + 提案 id 列表、
  `model_participated` + `model_note`、`agent_run_id`、`scope.novel_id`。
- 样式：复用本文件 `.card/.notice/.tag/.btn`，模态用新增 scoped `.clean-modal-mask/.clean-modal`
  （与 ProjectWorkspace 的 `.bible-modal-*` 视觉一致，但不跨文件引 scoped 类）。

### 4. `frontend/src/views/ProjectWorkspace.vue` 步骤 6 —— 快照回滚入口

在「已生成段落」卡片之后新增「重写快照与回滚」卡片：

- **列表**：`listSnapshots(status="applied", limit=50)` 单段快照 + `listSnapshotGroups(limit=20)` 整组；
  两个子标题「按段回滚」「按整组操作回滚」，空态给明确说明。
- **二次确认（复用 `.bible-modal-mask/.bible-modal`）** 单段文案：
  - 目标：第 {segment_no} 段（generation #{generation_id}）；
  - 覆盖：该段当前正文将被替换为快照 #{id} 的 before_text（{before_chars} 字，before_hash 前 12 位）；
  - 不动：其它段、剧情圣经；
  - 可再撤销：回滚本身会生成新快照 #{rollback_snapshot_id}；
  - 拒绝条件：正文在快照后被改过则整段不动。
  整组文案：一次 `{operation}` 操作共 {count} 段（列段号），全部退回快照；任一段不自洽则整组零写入。
- **409 处理**：`code=bible_changed_since_snapshot` → 模态内切换为三选项
  （`options[]` 原样渲染；`restore_bible_then_text→mode=with_bible`、`text_only→mode=text_only`、`cancel→关闭`，
  映射表加注释说明 id 来自后端）；`text_drifted` / `batch_not_rollbackable` → 模态内 err 展示 message。
- **执行后可核对**：`restored_snapshot_id`、`rollback_snapshot_id`、`segment_no` 或 `segments[]`、
  `chars`、`warnings`、`derived`（键值对展开）；成功后刷新 generations 与快照列表。

### 5. `frontend/src/views/ProjectWorkspace.vue` 步骤 6 —— 批量应用提案入口

新增「待应用提案」卡片：

- **列表**：`listProposals(projectId, "approved", 50)`，多选；每行显示 id / type /
  target_kind + target_id（`generation_text` 时用本地 `generations` 反查显示「第 N 段」）/
  risk_level / reason / 折叠 diff。
- **必要前置**：同一卡片增加「待批准」分段（`status=pending`），每行一个「批准」按钮
  （`approveProposal`，即时生效，行内注明「批准只改状态，不写任何正文」）。
  不加这一步，清洗产出的 pending 提案永远进不了批量应用，入口等于不可用。
- **上限**：勾选超过 `MAX_BULK_APPLY=50` 时禁止再选并提示分批（常量注释来源）。
- **二次确认（模态）** 文案：
  - 将覆盖 {n} 个目标（逐条 `target_kind · target_id`，能定位段号就显示段号）；
  - 整批同一事务，同成同败；任一 stale/blocked → 零写入；
  - 每条写一条 Version，事后可逐条回滚；
  - 单批上限 50 条。
- **执行后可核对**：成功 → `applied[]` 表（proposal_id / version_id / kind / content_hash 前 12 / status / applied_at）；
  409 → `reason` + `stale[]`（proposal_id/原因）+ `blocked[]`。成功后刷新提案与 generations。

## 验证

1. `cd frontend && npx vue-tsc --noEmit`（类型）
2. `cd frontend && npm run build`（构建）
3. `python -m pytest tests/test_action_catalog.py -q`（目录文案改动不破断言）
4. 手工三链路（后端已起）：
   - 语料页选中一本 → 先勾 `dry_run` 跑一次（提案数应为 0）→ 取消勾选再跑一次 → 核对提案 id 与 `findings_by_rule`；
   - 项目页步骤 6 → 回滚一条 applied 快照 → 核对 `restored/rollback_snapshot_id` 与正文变化；再造一次正文漂移验证 409 文案；
   - 待应用提案 → 批准清洗产出 → 勾选批量应用 → 核对 `applied[]` 的 version_id 与正文。

## 回退

全部为**新增**：新增卡片/模态/状态、client 与 types 追加方法、catalog 只改描述字符串、
文档追加记录。回退 = 删除新增块与文档段落；不动生成链路、蒸馏、既有端点与状态机。
