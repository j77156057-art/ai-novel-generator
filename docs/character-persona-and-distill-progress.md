> 2026-10-28。用一本新投放的长篇语料（《雾港守夜录》，自造示例名）真跑一遍之后暴露的三件事。
> 每一条都是先量后改：量出的数字都在下面，不是估的。

## 0. 触发这次改的那次真跑

用那本新语料（10 MB / 1177 章 / GBK 编码）走完整链路：
投放 → 平衡档蒸馏 → 合成剧情圣经 → 生成两段。

产物能看、能连上、形态在带内、抄书 0 命中、专名 0 泄漏 —— **但人读起来是扁的**：
所有角色说话一个腔调。顺带查出蒸馏慢、进度条早 100%。

## 1. 角色扁平：平台根本没有「我们角色的个性」这条数据通路

### 1.1 取证：提示词里到底有什么

项目《雾海之影》system 提示词 3875 字，角色相关的只有一块：

```
【角色人设约束】续写时必须保持以下角色一致，不得凭空新增主要人物，不得扭曲已确立的关系：
  · 顾星河（人类最后灯塔的执灯人，曾参与弑神之战的天命者；动机：先想证明守灯能够救人…）
  · 伊芙琳（从地底归来的失落神女…；动机：阻止末日预言应验…）
  …共 6 人
```

「动机」出现 **6** 次，「说话」「口头禅」「口吻」出现 **0** 次。

### 1.2 四条可能的信息来源，逐条查

| 来源 | 实际字段 | 够不够写活人 |
|---|---|---|
| 剧情圣经 `characters[]` | `name` / `role` / `motivation` | ❌ 只有「他是谁、他要干什么」 |
| KG `character_constraints` | `name` / `mentions` / `first_chapter` / `last_chapter` | ❌ 纯出现统计，没有人设 |
| KG `kg_character_state` | goal / mood / inventory / injury | △ 有状态，但**没进提示词** |
| L2 角色档案（`app/style/character_profile.py`） | **身份 / 说话方式（自称·口头禅·句长·语气）/ 行为倾向 / 性格底线 / 关系网（七字段）/ 关键经历 / 内心设想** | ✅ 正是缺的 |

第四行**早就写好了**，但它绑在「参考书角色」上：

- `prompts.py:_character_profile_block` → `if mode == "original": return ""`（原创路线不注入）
- `profiles.PROFILE_RULES["original"]["include_voice"] = False`（角色声音词典也不注入）

⇒ **原创路线下，我们自己的角色拿不到这套东西；而参考书侧的角色档案抽了也不进提示词。**
模型只拿到「身份 + 动机」，写对白时没有「这个人怎么说话」的依据 ⇒ 所有人一个腔调。

### 1.3 修法（两处一起做）

**A1：剧情圣经的角色条目带个性（首段就有）**

`characters[]` 里每个角色加一个 `persona`：

```json
{"name": "顾星河", "role": "…", "motivation": "…",
 "persona": {
   "说话方式": "自称「我」，句子短，从不解释只给结论",
   "行为倾向": ["被质疑守灯职责时→先沉默三秒，再反问一句"],
   "性格底线": ["不会当着陌生人承认弑神者身份"],
   "关键经历": ["七年前神陨之夜，他是唯一活下来的执灯人"],
   "来源": "model"}}
```

- 字段与 `character_profile.py` **同形**（中文字段名）⇒ 那套渲染器/校验能直接用；
- 由「合成剧情圣经」那一步生成（`wizard.build_bible` 的 system prompt 加要求）；
- 渲染进【角色人设约束】：`· 顾星河（身份；动机：…）｜ 说话：… ｜ 会：… ｜ 不会：… ｜ 经历：…`；
- **只增字段，不改** `name` / `role` / `motivation`（用户写的是权威）。

**A2：从已写正文反推（越写越活）**

- 输入：**我们自己已写的正文**里该角色的片段（KG `kg_mentions.context_window`），
  不是参考书；
- 产出：同 schema 的 `persona`（`来源=derived`）；
- 时机：**每段生成前**，若 persona 缺失或比最新正文旧 ⇒ 跑一次（1 次 LLM 调用，fail-open）；
- 落点：`plot_bible.characters[i].persona`（不动用户写的三个字段）；
- 注入：同 A1 的渲染路径。

⇒ 首段用 A1 的「想象版」，第二段起用 A2 的「实测版」，角色随文本一起长。

## 2. 蒸馏慢 + 进度条早 100%：三个阶段串行，而进度只算了中间那段

### 2.1 实测（平衡档，语料 = novel 3，force=True，计量跑）

```
总耗时 134.6s；模型调用 55 次；峰值并发 15；单次中位 8.7s / 最长 38.4s
串行等效 686.3s ÷ 15 = 理论最快 45.8s ⇒ 并行效率只有 34%（长尾拖的）
```

进度时间线（相对秒 / 阶段 / current-total）：

| 时刻 | 阶段 | 进度条显示 |
|---|---|---|
| 0.2s | 正在准备参考语料 | 0/0 |
| 0.2s | 参考语料 3 缺角色图谱，正在补建 | 0/0 |
| 50.4s | 已采样 30 章，切 6 块 | 0/6 → **0%** |
| 101.9→102.5s | 提炼第 1/6 块 → 第 6/6 块 | 17% → **100%（0.6 秒内跳满）** |
| 102.7s | 提取角色声音 | **100%** |
| 128.7s | 提取 L2 角色档案 | **100%** |
| 134.5s | 文风漂移分析 | **100%** |
| 134.6s | 正在汇总提炼出的规则 → 完成 | **100%** |

### 2.2 前置那 50 秒是什么（单独量）

| 动作 | 耗时 |
|---|---|
| `build_graph`（1177 章参考书建角色图谱，**零 LLM 纯规则抽取**） | **48.2s**（抽出 1364 个角色） |
| `_load_novel_chapters`（读 1139 章） | 1.8s |
| 采样（30 章） | 0.0s |
| 图谱已存在时跳过 | 0.0s |

⇒ 前置那 50 秒**全是建图**，与蒸馏产物无关。

### 2.3 三处根因

1. **分母是块数（6），不是工作量。** 6 块是**并发**跑的 ⇒ 百分比是阶跃的；
2. **后三个阶段（角色声音 / L2 档案 / 漂移分析 / 汇总）占 24% 的时间，却全程显示 100%**；
3. **建图（48s，零 LLM）压在关键路径上**，而它只服务「参考书角色」相关的产物。

### 2.4 修法

**B：阶段化进度** —— 进度改成六个阶段的推进，不再用块数当分母：

```
① 准备参考语料 → ② 采样切块 → ③ 提炼规则 → ④ 角色声音 → ⑤ L2 角色档案 → ⑥ 漂移分析与汇总
```

后端 `progress(stage, current, total)` 的语义改为「已完成阶段数 / 总阶段数」，
阶段内不再单独报百分比；前端百分比条按阶段走 ⇒ **绝不提前 100%**。

**C：参考图谱提前建** —— 建图是「参考语料的预处理」，与蒸馏产物无关，
不该压在蒸馏的关键路径上：

- 投放语料落库时 / 项目保存参考语料时 → **后台**触发 `build_graph`（零 LLM、幂等）；
- 蒸馏开始时图已建好 ⇒ 直接跳过那 48 秒；没建好 ⇒ 仍然兜底建（现状不变）；
- 口径不变：每本语料在每个项目下**各自成图**（不混），跨项目复用是后续优化。

## 3. 验收项

1. 合成剧情圣经后，`characters[].persona` 四项齐全（说话方式 / 行为倾向 / 性格底线 / 关键经历）。
2. system 提示词的角色约束块里能看到「说话：… ｜ 会：… ｜ 不会：…」；「说话」不再出现 0 次。
3. 写完一段后跑反推：persona 的 `来源` 变 `derived`，且内容**来自正文里真出现过的台词**。
4. 判据：反推出来的说话特征不得编造正文中没有的台词（逐字回查）。
5. 进度条：六阶段单调推进，**采样/提炼完成后不到 100%**，直到「蒸馏完成」才 100%。
6. 同一份语料第二次蒸馏（命中蒸馏库）耗时 ≤ 5s；投放后立刻蒸馏，前置建图 ≤ 5s。
7. 全量 `python -m pytest tests/` 0 failed；前端 `npm test` + `npm run build` 通过。
8. 真跑：用《雾海之影》重生成一段，肉眼判「几个角色说话能不能分辨出不同的人」。

## 4. 补：人写 + AI 完善（用户追加的需求）

> 「有没有什么办法让用户可以自己写角色的性格，自己来决定出现的角色应该有什么样的表现，
> 再由 ai 来帮忙完善」

### 4.1 三条规矩（与后端 `app/generation/persona.py` 一致）

1. 人写的标 `来源=user` ⇒ 之后的「从正文反推」**不覆盖**它；
2. AI **只补不改**：只能在人写的内容**后面追加**，且要去掉 AI 对用户原文的重述；
3. AI **不落库**：它给的是建议，**采纳与否由人点**。

### 4.2 四个端点

| 端点 | 作用 | 落库 |
|---|---|---|
| `GET  /api/projects/{id}/style-narrative/personas` | 列出角色与现有四栏 | — |
| `POST /api/projects/{id}/style-narrative/personas` | 人写保存（`来源=user`） | ✅ |
| `POST /api/projects/{id}/style-narrative/personas/complete` | AI 给补充建议 | ❌ |

### 4.3 界面上有两个坑（都不是逻辑问题）

1. 弹窗原本在「⑤ 构思剧情」那一节，而个性面板在「⑥ 生成控制台」⇒ `personaOpen` 为 true
   但组件不渲染。⇒ 挪到根模板层。
2. `.bible-row .k` 少一个 `}` ⇒ Chrome 原生 CSS 嵌套把 5 个弹窗样式全吞了
   ⇒ 弹窗在 DOM 里、屏幕上却没有。详见 `ENGINEERING.md`「CSS 少一个花括号」。

### 4.4 验收项（人写 + AI 完善）

1. 弹窗能打开，四栏**预填**该角色现有的四栏内容（人写 / 反推 / 想象版都能读到）。
2. 点「AI 帮我完善」→ 返回的是**建议**，界面按四栏分条显示（不是原始 JSON），且**库里没变**。
3. 点「采纳」→ 四栏变成「用户原文 + AI 追加」，重复项被去掉；**库里仍然没变**。
4. 点「保存」→ 库里 `来源=user`，条数按合并后的数落；界面上标出「你写的（不会被自动改）」。
5. 下一段生成时，提示词里该角色的行带 `｜ 说话：… ｜ 会：… ｜ 不会：… ｜ 经历：…`。
6. 守门：`frontend/tests/styleBlockBraces.test.ts` —— 样式块花括号必须配平、
   普通规则里不许出现嵌套（防 §4.3 第 2 条复发）。

### 4.5 实测（真实通道 MiniMax-M3）

- 手写「句子短，从不解释」→ AI 补三条 → 采纳 → 保存：
  库里 `来源=user`，条数 4→6 / 4→6 / 2→5，重复项被去掉。
- 带个性重生成一段（3,196 字，70 句台词）：**0 个感叹号**；
  顾星河均长 5.1 字 / 最长 10 字；伊芙琳短答；陆沉舟先问再推测、用词偏档案；
  白烬一句话带称谓。→ 「几个角色说话能分辨出不同的人」成立。
