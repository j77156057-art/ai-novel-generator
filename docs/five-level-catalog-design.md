# 五级目录检索设计稿（v0.1）

> 状态：已批准（2026-11-12），进入 P1 小样。本稿定五级路径命名、卡片 schema、anchor 语义与验收口径；P1 跑完 500 条再决定是否全量。
> 本稿替代上一版「L1 卡 / L2 主题」的两层说法：五级是**导航骨架**，60–80 个主题降为卡片上的软聚类字段，不再单独占一层。

## 0. 已确认（2026-11-12 批复）

1. **anchor 天花板**：按「单次 anchor 左右合计 ≤4,000 字（每侧最大 2,000）」执行，不再改。单轮所有 anchor 调用合计 ≤8,000 字。
2. **60–80 主题降为 `topic_ids` 软召回字段**：同意。五级用固定 14×6×8 路径；小样仍聚 8 个主题，但**只作 `topic_ids` 字段附报，不进验收**（验收改用 14 个 L2 场景，见 §7.4 第 2 项）。
3. **非节拍维度判不出 L3 就停在 L2**：同意，但加可测量护栏——「停在 L2 的比例」>40% 即判不合格，回看 L3 词表或补类，不接受该比例（见 7.4 第 4 项、7.5）。
4. **量化指标一卡一条观察**：同意。一张卡里那组数字是一体的，不按数字拆卡。
5. **L3 不补词表，改三种路径形状**（2026-11-12 定稿）：`structural` / `technique` / `global` 并存，维度 → 形状的映射写死；护栏只看 `structural`。见 §2.7。
6. **骨架四种改动**：分「通用/结构/技法」三节且通用排前；只列条数 ≥5 的路径；上限 1,800 → 2,200 字；结构层写死、计数随档案、缓存键不变。见 §5.12.1。
7. **旧验收口径作废**：「停在 L2」按全部维度统计的 28.4%（500 小样）/ 58%、74%（全量）不再引用，改用 §7.4 第 4 项的 structural 口径。
8. **structural 只留节拍序列**（2026-11-12 二次定稿）：剧情编排模式、伏笔与悬念设计改判 `technique`——它们是章级乃至卷级骨架，不发生在某个场景的节拍上，判不出 L3 不是模型问题，是问题本身不成立。护栏分母只剩节拍序列（15%/14%），**「书 5/6 换书风险」记录销掉**，不单独设阈值、不动词表。见 §2.7、§7.4 第 4 项。
9. **L2 判定改用粗定位**（2026-11-12 三次定稿）：规则来自哪个 chunk，就看那个 chunk 的上下文在写什么，不再只看规则正文关键词；规则正文里的场景词降为次级信号。词表去掉全部单字场景词、按「最长匹配」当整词用（`战车`/`战斗机`/`挑战` 不得命中 `战`），词表与黑名单落在 `app/retrieval/catalog_config.py`，可从配置直接核对。见 §2.3。
10. **检索加 query 场景先验**：query 命中场景词就给对应 L2 子树加权；权重可调、可一键关掉（对照实验）。理由：纯文本匹配会让命中率贴在「不挂场景」的基数上，场景层等于白建。见 §5.3、§7.4 第 2 项。
11. **验收口径换 14 个 L2 场景**：`topic_ids` 保留为软召回字段，但不再用它证明检索质量（`topic_7` 占 51% 是聚类偏斜）。分散度、命中占比一律按 14 场景算。见 §7.4 第 2 项。
12. **锚点只报三类分布，不卡 ≤15% 的门**（2026-11-12 三次定稿）：证据 ≥15 字做章内精确匹配；<15 字用首尾各 3 字两端锚定做模糊定位；找不到标 `anchor_missing`，**如实报 exact / fuzzy / missing 三类比例**，不编造、不硬凑。原「missing ≤15%」验收门作废，改为「报告当前上限」。见 §4.1、§7.5。
13. **上游修正写进抽取提示词**：新蒸馏要求证据句 ≥20 字，短于 20 字不作为证据；历史档案不重蒸，靠粗定位兜。见 §3.2。
14. **纯文本匹配比随机基线更差（−9pt），场景先验是必需项、不是优化项**：首轮 500 小样先验关时 Q1 的 combat 占比只有 **10%**，而全样本 combat 基数是 **19%**——比随机抽 10 条的期望还低 9pt。原因是「短句 / 对白 / 描写」这类高频通用词在所有维度里都反复出现，纯文本排序被它们主导，场景词反而没有区分力。**因此不得以「简化先验」为名把权重关到 0 或删掉先验层**；真要动，先看本节和 §7.4 第 2 项的扫描表。2026-11-12 按全量形状比例重抽后，先验关 Q1 是 50% vs 基数 16%（+34pt）、先验开 90%（+74pt），方向一致。
15. **先验默认权重 = 0.20**（2026-11-12 定）：扫描结果（旧样本）0.10→70%/3 场景、0.20→90%/1、0.35→100%/1；重抽样本 0.10→80%/2、0.20→90%/1、0.35→100%/1。取 **0.20**：既压住通用词，又不把结果锁死成单一场景。写进 `catalog_config.SCENE_PRIOR_WEIGHT`，并保留开关供对照实验。
16. **锚点字段落库**（2026-11-12 定）：新蒸馏每条规则必须写 `chunk_id`（真实 `novel_chunks.id`）与 `evidence_chapter_no`（**证据实际所在章**，不是蒸馏块的起始章）；证据 **20–60 字**，不足 20 字不落库。历史档案不改写，检索侧用 5 章窗口兜底并如实标为弱锚点。见 §4.1。
17. **决定重蒸 novel 7**（2026-11-12 定）：77.4% 的证据短于 20 字是抽取提示词不够硬造成的，重蒸一次换掉；`chunk_id`、`evidence_chapter_no`、时间线描述本来就要补，合在一次跑最省。成本按实测 2h15m / $10.5，不重估。执行先 5 块试跑（≥20 字占比 ≥80% 才继续），跑完重跑 500 条验收。`NARRATIVE_VERSION` **不 bump**，但 v7 档案存在两代证据质量，见 §8.1 与 §3.2。
18. **块级场景标签改成「1 主 + 0–1 次」，禁止凑数**（2026-11-12 定）：首轮 5 块试跑 5/5 块全标满 3 个（均 3.0），是提示词要求「0–3 个」造成的系统性过标，不是真实分布。改为：`primary_scene` **有且只有一个**；`secondary_scenes` **0–1 个**，没有就写空数组；过渡段/设定说明段没有明确场景时写 `"none"`，不许硬套；提示词明写「不要为了凑数而上报标签」。解析侧保留旧 `场景标签` 兼容（取第一个作主标签），`scene_labels` 只作兼容字段（主 + 次，`none` 不入列），**检索只认 `primary_scene`，`secondary_scenes` 不给权重**。标签偏多的批次按「降级使用」处理，需重标。
    - 验证三项（跑完直接出数）：① 14 个 key 的分布，若 80% 集中在前 3 个 key 且每块固定标满即判过标；② 与 `catalog_config.SceneMatcher` 的一致率，模型标签与关键词无交集的块单列（模型标错 / 词表缺词，两种都要看）；③ 从 `combat` 块随机取 30 个锚点窗口贴原文人工抽检。
    - 新提示词 5 块试跑（2026-11-12）：主标签 `daily`×2 / `groupchat` / `travel` / `combat`，`none` 0/5，secondary 为空 1/5（20%），另一次同轮 0/5；两次 secondary 取值均与块内第二个真实场景对应（如 `groupchat + daily`、`travel + []`），不再出现「三标签铺满」。

## 1. 目标与非目标

### 目标

- 把 32,378 条原子规则变成**可按级浏览、按场景检索、能回原文**的知识库。
- 同一套只读工具开放给作者 agent 与助理 agent，权限与实现完全一致。
- 检索结果可追溯：`命中卡 → 原子规则 → 章号 → 证据句 → 章内 offset`。
- 卡片摘要**只从原文抽取**，不允许模型自由概括；摘要与原文对不上，整条索引作废。

### 非目标

- 不改现有蒸馏产出格式；卡片是**派生索引**，原文规则仍是唯一事实源。
- 不做写操作：agent 不能改规则、不能改卡、不能改路径。
- 不推翻现有四维打分；它变成卡片排序分，继续用。

## 2. 五级路径命名表

### 2.1 路径语法

```
path = l1 [/ l2 [/ l3 [/ l4 ]]]
```

- 叶子是 L5 规则卡，不写进 path。
- 允许**短路径**：证据不足以判定场景/节拍/技法时，停在 L1 或 L2。空路径不建。
- 存储用 ASCII key，展示用中文 label；两者一一对应，禁止同义 key。
- 例：`style/combat/climax/action`，展示为 `文风规则/战斗对峙/爆发/动作`。

### 2.2 L1 资源族（5）

| key | 中文 | 现有维度映射 | 说明 |
|---|---|---|---|
| `style` | 文风规则 | 人物描写手法、对白风格、段落编排、场景构建、情绪表达、节奏控制、剧情编排模式、伏笔与悬念设计、节拍序列、高频场景模板、潜台词模式 | 主体，量最大 |
| `voice` | 角色声音 | 角色声音词典 | 按角色挂卡，可混查多个角色 |
| `world` | 世界设定 | 世界观呈现 | 设定类，通常不挂节拍 |
| `timeline` | 剧情时间线 | 剧情时间线 + KG timeline | 可挂场景/节拍 |
| `metric` | 量化指标 | 文笔量化审计 | 程序实测，硬锚 |

### 2.3 L2 场景域（14）

| key | 中文 | key | 中文 |
|---|---|---|---|
| `combat` | 战斗对峙 | `reveal` | 揭示爆料 |
| `daily` | 日常琐事 | `intimacy` | 情感亲密 |
| `groupchat` | 群聊多声部 | `farewell` | 离别告别 |
| `trade` | 交易交换 | `banquet` | 宴席聚会 |
| `cultivate` | 修炼疗伤 | `misunderstand` | 误会冲突 |
| `travel` | 赶路移动 | `rescue` | 救援脱困 |
| `interrogate` | 审讯盘问 | `night` | 夜谈独处 |

判定顺序（2026-11-12 三次定稿：粗定位优先，不再看规则正文关键词）：

1. **粗定位**：先定位规则证据落在哪个 chunk，取该 chunk ±1 的原文（约 1,200–3,600 字）
   判「这段在写什么」。`chunk` 级上下文是主信号。
2. **章级兜底**：证据定位不到时，用所在章内「场景得分最高的连续 3 个 chunk」作上下文；
   章文本缺失才退回规则正文。
3. **场景判定**：在上下文里用 14 场景词表做**最长匹配整词计数**，最高分 ≥2 才算命中；
   判不出 → **不写 L2**，路径停在 L1。
4. **次级信号**：上下文判不出、规则正文能判出时，允许挂场景，但标
   `scene_src=rule_text_secondary`，进报告可核对。
5. 多场景冲突时取上下文得分最高者，不取规则正文里的举例场景。

**词表与开关全部在 `backend/app/retrieval/catalog_config.py`**：

| 配置项 | 值 | 说明 |
|---|---|---|
| `SCENE_LEXICON` | 14 域 / 123 词 | 全部 ≥2 字；单字场景词已删 |
| `SCENE_COMPOUND_BLOCKLIST` | 10 词 | `战车/战斗机/挑战/战术/战斗力/…` 优先命中但不计场景 |
| `SCENE_MIN_SCORE` | 2 | 上下文里至少命中 2 次才挂场景 |
| `SCENE_PRIOR_ENABLED` | `True` | 检索先验总开关（关掉即纯文本基线） |
| `SCENE_PRIOR_WEIGHT` | **0.20** | 先验加分；0.20 是默认值（理由与扫描见 §7.4） |
| `ANCHOR_EXACT_MIN_CHARS` | 15 | ≥15 字走精确匹配 |
| `EVIDENCE_MIN_CHARS` | 20 | 新蒸馏的证据句下限 |

匹配方式：中文无空格，用**最长匹配**代替分词——从每个位置起优先匹配词表里最长的词，
命中即整词消费该段（`战斗` 不会同时再命中 `战`）。blocklist 命中只消费字符、不加分。

| key | 中文 | 来源 |
|---|---|---|
| `setup` | 建置 | 节拍序列标签「建置」 |
| `build` | 升温 | 「升温」 |
| `climax` | 爆发 | 「爆发」 |

### 2.5 L4 技法（8）

| key | 中文 | 典型信号 |
|---|---|---|
| `dialogue` | 对白 | 引号、称谓、敬语、说话归属 |
| `action` | 动作 | 动词链、拟声、短句、招式 |
| `psych` | 心理 | 内心、吐槽、犹豫、情绪 |
| `environment` | 环境 | 天气、光线、空间、器物 |
| `pacing` | 节奏 | 长短句交替、时间压缩、段落切分 |
| `pov` | 视角 | 第三人称限知、切换视角、旁观者反应 |
| `infocontrol` | 信息控制 | 伏笔、留白、延迟揭示、误导 |
| `rhetoric` | 修辞 | 比喻、夸张、排比、反讽 |

一张卡只写一个**主 L4**（进 path），其余技法放 `technique_tags[]` 供检索过滤。
L4 在三种形状里都挂：structural 在 L3 之后，technique 直接接在场景之后，global 直接接在 L1 之后。

### 2.6 稀疏树

- 上界 14×6×8=672 条 L2/L3/L4 路径；实际只建有内容的，预计 200–300 条。
- **条数 <5 的路径不单独占行**，计数并入上一级只留总数（骨架同此规则，见 §5.12.1）。
- `browse` 在某一级没有子路径时，展示 `未细分` 虚拟桶（不落库），避免用户点进去是空的。

### 2.7 三种路径形状（维度 → 形状写死）

2026-11-12 二次定稿。全量实测证明：6 个节拍词表在节拍维度上停留率 15%/14%，
是有效的；对白/场景/人物描写 93–100% 判不出 L3——不是词表缺词，是这些技法规则
本身不挂在节拍上。同理 style 卡 82% 停在 L1，是多数文风规则跨场景，不是分类失败。
**剧情编排模式、伏笔与悬念设计虽然结构性强，但它们是章级乃至卷级骨架**
（「三章一反转」不发生在某个场景的笑点上），同样判不出某个场景内的节拍，
硬标就是猜。因此**不补词表**，改成三种形状并存，维度 → 形状的映射写在代码里，
不靠模型判断。

| 形状 | 路径语法 | 维度 | novel 7（style 16,068） | 书 5/6（style 5,832） |
|---|---|---|---|---|
| `structural` | `L1 / 场景 / 节拍 / 技法 / 规则` | 节拍序列 | 2,268（14%；其中到 L2 1,351） | 308（5%；其中到 L2 173） |
| `technique` | `L1 / 场景 / 技法 / 规则`（跳过 L3） | 对白风格、人物描写手法、场景构建、情绪表达、高频场景模板、剧情编排模式、伏笔与悬念设计 | 8,061（50%） | 3,890（67%） |
| `global` | `L1 / 技法 / 规则`（不挂场景、不挂节拍） | 潜台词模式、段落编排、节奏控制 | 5,739（36%） | 1,634（28%） |

规则：

1. 上表是**封闭映射**：未列出的维度按「style 族默认 technique、其他 L1 族按族归位」处理，
   不允许运行时改判形状。
2. technique 的卡若判不出场景，路径退为 `L1 / 技法`（短路径），**形状仍是 technique**，
   不改挂到 global——形状由维度决定，不由单条规则的判定结果决定。
3. 只有 structural 形状参与「停在 L2」护栏（§7.4 第 4 项），technique / global 不计入。
   现在 structural 只剩节拍序列，护栏分母就是节拍维度，不再有「两个维度拖低整块」的问题。
4. 计数随档案变；形状与路径语法不随书变。换书只换数字，不换结构。
5. **剧情编排模式、伏笔与悬念设计改判 technique 的连带**：它们判不出场景时走
   `style / 技法`，不挂节拍；换书时不再对它们设任何「停在 L2」阈值，也不为它们补词表。
   novel 7 的 technique 因此从 5,348 涨到 8,061、书 5/6 从 2,689 涨到 3,890；
   structural 从 4,981 降到 2,268（其中到达 L2 的只有 1,351 张）。

```jsonc
    "evidence_chapter_no": 16,        // 证据实际所在章（新蒸馏落库）
    "chunk_id": 12345,                // 真实 novel_chunks.id（新蒸馏落库）
    "char_start": 8120,
    "char_end": 9010,
    "excerpt": "……",                 // 锚点段落摘录
    "method": "exact",                // exact / fuzzy / missing
    "anchor_missing": false
  },
  "timeline_desc": "宋书航与羽柔子在街头被五个醉鬼堵住，对方盯上羽柔子，冲突一触即发。",
  "timeline_src": {"chapter_no": 16, "quote": "那是一条人烟稀少的小路……"},
  "topic_ids": ["topic_03"],          // 软聚类，可选
  "created_at": "2026-11-12T..."
}
```

### 3.2 摘要抽取规则（硬约束）

`summary` 只能由程序从 `text` 抽取：

1. 去掉「证据：」及之后内容。
2. 取第一个分句（按 `，。；：` 切），最长 30 字；超长在分句边界截断，不补写。
3. 专名替换为角色词或直接删除，避免摘要带跨书人名。
4. 不改变原句语序，不合成新句子，不加评价词。
5. 摘要与 `text` 的首个分句做包含度校验；低于 0.8 判为不合格，整卡不建。
6. 「证据：」前面通常还有一个孤立的「（」，剥离证据后要一并清掉，不允许卡片正文以括号结尾。

**证据句下限（写进抽取提示词，`narrative.py` 5 处）**：

- 新蒸馏要求**证据句 ≥20 字**，短于 20 字不作为证据（提示词原文：`引用一句原文（20–60 字，少于 20 字不作为证据）`）。
- 落库处**只硬卡下限 20 字**；上限 60 字只作提示词引导，不硬卡——超长引文仍是真实原文，
  硬卡只会误杀好规则。
- 理由：短证据在章内无法唯一定位，只能做两端锚定，等于没有锚点。
- 历史档案不重蒸，短证据靠 §4.1 的两端锚定 + 章窗口兜底，但**必须如实计入 `fuzzy`**，不能算 `exact`。
- 例外：**novel 7（`style_distills id=4`）已于 2026-11-12 重蒸**，重蒸后是新标准；
  在此之前生成的 v7 档案仍是旧标准。两代同 `narrative_version=7`，区分依据是规则是否带 `chunk_id`，见 §8.1。

### 3.3 建卡时的硬过滤

**硬过滤只在建卡阶段做一次，检索阶段不再重复。**

直接复用 `_score_rule` 的 `_HARD_FILTER_MASK`：

- 无引号证据（现有 13,425 条）
- 模糊词 / 通用套话
- 超长（沿用 `max_rule_chars`；节拍按已落库的骨架长度）
- 近重复（`near_dup_similarity`）
- 无章号

被淘汰的规则不进卡表，但原文仍留在 L0，可通过 `rule(id)` 的旧 id 回查（标记 `card_missing=true`）。

### 3.4 兜底池

检索命中 <3 条时，回落到「跨书通用约束」约 400 条。它们是低区分度基线，正好补位；返回里标 `fallback=true`，让 agent 知道这不是场景定制规则。

### 3.5 口径对账：生成端 style_check 与蒸馏档案**不同源**

这一条决定「量化卡上的数字」能不能和「生成后校验的数字」直接比。结论：**不能直接比**，
因为两边不是同一个切句器、也不是同一个阈值。

| | 蒸馏侧（档案 / `metric` 卡） | 生成侧（`style_check`） |
|---|---|---|
| 入口 | `narrative.build_deterministic_features(chunk_text)` | `consistency.measure(text)` → `stylometry.features(raw_text, unit_chars=0)` |
| 切句 | `re.split(r"(?<=[。！？…])", chunk_text)` | `stylometry.paragraphs()` 先按换行分段，再 `stylometry.sentences()` 逐字切，终结符 `。！？!?…`，省略号先归一 |
| 句长是否含句末标点 | 含 | 含 |
| 「短句」阈值 | **整句长度 ≤5**（`x <= 5`） | **整句长度 ≤4**（`L <= 4`） |
| 统计单位 | 块级（每块算一次占比，档案报中位数） | 全文 / 每段（`unit_chars=0` 不做长度缩放） |
| 落库位置 | `style_narrative`（叙事审计块） | `style_checks.core` + `projects.style_profile` 对照 |

因此：

1. **`style_check` 与 `projects.style_profile` 同源**（都是 `stylometry`，≤4），可以算 z 值、
   可以判「离档案多远」。这是现在唯一成立的比对。
2. **`style_check` 与叙事审计块（≤5，块级中位）不同源**，差值不是「写崩了」，是两个口径。
   审计块已就地标注「短句(≤5字)」并写明「不是全文统计常用的 <15 字口径」。
3. 量化卡（L5 `metric`）取的是叙事审计那一套（≤5、块级中位），卡上必须标 `metric_scope`
   与阈值，例如 `"metric_scope": "narrative.chunk.le5"`。
4. 若以后要让生成端直接对齐档案卡，必须**先统一切句器**（把 `build_deterministic_features`
   改成调 `stylometry.sentences`），再谈阈值；只改阈值不改切句器仍然是假对齐。

novel 7 的实测差（同一批文本）：块级 ≤5 中位 **15.0%**；全文 ≤15 **41.0%**；外部对照全文 <15 **44.4%**。
差三倍是「阈值 5 vs 15」和「块级中位 vs 全文汇总」叠加的结果，**不是同口径的漂移**。

## 4. 原文锚点与时间线

### 4.1 锚点存储

**新蒸馏**：切章时直接记录证据句所在章号与 `char_start/char_end`，并保存 150–300 字摘录。
**新蒸馏的证据句必须 ≥20 字**（写进抽取提示词），短于 20 字不作为证据，
从源头消灭「短证据无锚点」这一类问题。

**新蒸馏的落库字段（2026-11-12 起，`narrative.py::_anchor_fields`）**：

| 字段 | 值 | 说明 |
|---|---|---|
| `chunk_id` | `novel_chunks.id` | **真实块 id**，不是 `chunk_key` 的 hash；证据跨块时为 `null` |
| `distill_chunk_key` | 蒸馏块的稳定 hash | 保留块分组关系，重跑可对齐 |
| `chapter_range` | `"起-止"` | 蒸馏块覆盖的章范围 |
| `evidence_chapter_no` | 证据实际所在章 | 由证据在该块内的真实命中章回填，**不再用块起始章** |

落库时对该块 5 章的全部 chunk 做一次归一化匹配（去空白/标点/引号差异），
块内命中即写 `chunk_id + evidence_chapter_no`；块级失败再退章级（`chunk_id=null`）。
历史档案没有这些字段，只能事后定位；**偏移分布 `+0:221 / +1:90 / +2:67 / +3:52 / +4:63`**
（重抽 500 实测），其中 272 张需要纠正章号，不能把 `chapter_no` 直接当证据章用。

**历史档案**（不重蒸，只能事后定位）分三级：

| 级别 | 条件 | 做法 | method |
|---|---|---|---|
| 精确 | 清洗后证据 ≥15 字 | 章内逐字匹配（整串优先，其次引号内整句） | `exact` |
| 模糊 | 证据 <15 字 | 首 3 字 + 尾 3 字两端锚定，中间允许 ≤1 字浮动；失败则去标点归一化匹配 | `fuzzy` |
| 缺失 | 上述都失败 | 只留章号，`anchor_missing=true` | `missing` |

补充规则：

1. **章窗口**：历史档案的 `chapter_no` 是蒸馏 chunk 的**起始章**，一个 chunk 覆盖约 5 章，
   证据最远落到 `chapter_no+4`。定位窗口 `[chapter_no, chapter_no+4]`，落在哪章就把
   `anchor.chapter_no` 纠正到哪章，并记录 `chapter_offset`。实测 500 张小样里 281 张
   （56%）需要纠正，偏移分布 `+0:219 / +1:105 / +2:66 / +3:56 / +4:54`——**档案章号不能直接当证据章号用**。
2. 历史证据常是「转述 + 多段引文」的拼接（`药师说“A”原文紧接着写“B”`），整串连续匹配必然失败；
   先取引号内原文，再按 `；。！？…` 切段、剥掉转述前缀，命中的是原文真子串，标 `fuzzy`，
   不拼凑。
3. 多候选取**离 chunk 中心最近**的一条；无 chunk 时用章中点兜底。
4. 章文本来源：`novel_chunks` 按 `chapter_no, idx` **无分隔符拼接**（chunk 是任意切分，
   插换行会让跨块证据定位失败），偏移相对整章。
5. 命中级别、命中方式（`full / inner_quote / short_anchor / normalized / segment`）、
   锚点跨度都要落库，报告里按这三类 + 子类如实列，不合并成一个数。

### 4.2 时间线描述

`timeline_desc` 40–60 字，写「谁在哪、在干什么、上一刻发生了什么」。

生成方式必须是**抽取式压缩**：

1. 取锚点前后各 300 字（与 `anchor` 默认窗口一致）。
2. 按句子切分，选包含人物/地点/动作的句子。
3. 按时间顺序拼接，压缩到 40–60 字；只删不改，不新增信息。
4. `timeline_src.quote` 保存被压缩的原始句子，`chapter_no` 必填。
5. 校验：`timeline_desc` 的每个实词必须能在 `timeline_src.quote` 中找到；找不到就退回只存 quote，不写 desc。

这条是硬要求：不允许模型自由生成「场景总结」，否则就是第二个「漂移分析说对白密度升高、实测反而下降」。

## 5. Agent 工具接口（只读）

### 5.1 公共约束

- 只读；作者 agent 与助理 agent 共用同一实现，权限一致。
- 单轮最多 5 次工具调用；总计最多 3 轮。
- 除 `anchor` 外，单次返回 ≤800 字。
- 每次调用写 `retrieval_logs`：`session_id, agent_role, tool, path, query, hit_ids, chars_returned, latency_ms, context_expansion_count, created_at`。
- 预算超限返回 `budget_exhausted`，返回已取到的部分，不静默截断。

### 5.2 `browse(level, path)`

```json
{
  "status": "ok",
  "level": 2,
  "path": "style",
  "children": [
    {"key": "combat", "label": "战斗对峙", "count": 312},
    {"key": "daily", "label": "日常琐事", "count": 287},
    {"key": "_unassigned", "label": "未细分", "count": 104}
  ],
  "total": 703,
  "truncated": false
}
```

- `level` = 想看的子级（1–4）；`path` 为空时看 L1。
- 只返回计数，不返回卡内容，保证 ≤800 字。

### 5.3 `search(query, path)`

```json
{
  "status": "ok",
  "path": "style/combat/climax",
  "query": "爆发时的短句和拟声",
  "hits": [
    {"id": "r7-637725d1", "summary": "冲突顶点用短句和快节奏动作收束，不写缠斗",
     "path": "style/combat/climax/action", "chapter_no": 16, "score": 0.91}
  ],
  "total_hits": 37,
  "fallback": false,
  "truncated": false
}
```

- `path` 支持前缀；也允许 `l1: ["style","voice"]` 形式的混查。
- 先按卡片路径过滤，再用现有四维总分排序，最后 MMR 取 3–5 条。
- **query 场景先验**（2026-11-12 新增）：
  1. 用同一份 14 场景词表对 query 做最长匹配，命中 ≥1 次即得该场景（Q1 → `combat`；
     Q2 → `groupchat` + `daily`）。
  2. 对 `scene ∈ 命中场景` 的卡片，在排序分上 `+SCENE_PRIOR_WEIGHT`（默认 **0.20**）。
  3. `SCENE_PRIOR_ENABLED=False` 即回到纯文本基线，用于对照实验；权重按 §7.4 的扫描表调。
  4. 只在**排序**上加分，不改变命中集合的组成规则，也不改路径：先验是偏好，不是硬过滤。
     因此 `browse` 的计数、`path` 的归属始终由建卡时的场景决定。
- 命中不足 3 条 → 兜底池补位，`fallback=true`。

### 5.4 `rule(id)`

返回规则全文 + 时间线 + 证据 + 锚点状态。

```json
{
  "status": "ok",
  "id": "r7-637725d1",
  "path": "style/combat/climax/action",
  "text": "爆发：冲突顶点用短句……",
  "timeline_desc": "宋书航与羽柔子在街头被五个醉鬼堵住，对方盯上羽柔子，冲突一触即发。",
  "timeline_src": {"chapter_no": 16, "quote": "那是一条人烟稀少的小路……"},
  "evidence": "原文写‘耳边有一阵风呼啸而过……’",
  "anchor": {"char_start": 8120, "char_end": 9010, "anchor_missing": false},
  "scores": {"execution": 0.85, "distinctiveness": 0.71,
             "evidence": 1.0, "verifiability": 1.0, "total": 0.77}
}
```

- 若全文超 800 字：返回 `text` 前 800 字，`text_truncated=true`，并提示用 `anchor` 取原文。
- 若卡被硬过滤淘汰：`status="card_missing"`，仍返回原文规则与证据，提示「该条未建卡」。

### 5.5 `anchor(id, width?, cursor?)`

#### 响应结构

```json
{
  "status": "ok",
  "rule_id": "r7-637725d1",
  "chapter_no": 16,
  "width": 300,
  "segments": [
    {"side": "center", "from_char": 8120, "to_char": 8720, "text": "……"}
  ],
  "has_more": true,
  "next_width": 600,
  "cursor": "eyJpZCI6InI3LTU0NTAzMmE0IiwiZnJvbSI6ODEyMCwidG8iOjg3MjB9",
  "anchor_missing": false
}
```

- 首次调用默认 `width=300`（左右各 300，合计约 600 字）。
- `width` 由调用方决定，服务端只做上限与预算约束；不写死三档。
- 段落对齐：优先扩到空行段落边界；无空行时扩到句子边界（`。！？…`）；绝不半句开头。
- `cursor` 编码上一轮的 `from_char/to_char`，下一轮只返回**外侧新增的 delta**，不重复正文。

#### 扩展调用（delta）

```json
{
  "status": "ok",
  "rule_id": "r7-637725d1",
  "width": 600,
  "segments": [
    {"side": "left",  "from_char": 7520, "to_char": 8120, "text": "……"},
    {"side": "right", "from_char": 8720, "to_char": 9320, "text": "……"}
  ],
  "has_more": true,
  "next_width": 1200,
  "cursor": "eyJpZCI6InI3LTU0NTAzMmE0IiwiZnJvbSI6NzUyMCwidG8iOjkzMjB9",
  "anchor_missing": false
}
```

#### 上限与预算

- 单次响应：左右合计 ≤4,000 字（约 2,480 token）；每侧最大 2,000。
- 单轮所有 `anchor` 调用累计 ≤8,000 字（约 4,960 token）。
- 到 4,000 字上限：`has_more=false`，`note="已到上下文上限"`，不再给 `next_width`。
- 单轮超 8,000：`status="budget_exhausted"`，返回已取到的 segments，`has_more=true`，`note` 说明剩余额度为 0。

#### 状态码

| status | 含义 | 返回 |
|---|---|---|
| `ok` | 正常 | segments |
| `anchor_missing` | 证据句未能定位 | 章号 + 该章开头 200 字，`fallback="chapter_head_200"`，`has_more=false` |
| `at_limit` | 单次到 4,000 字上限 | 已取部分，`has_more=false` |
| `budget_exhausted` | 单轮 8,000 字用尽 | 已取部分，`has_more=true`，`remaining_chars=0` |
| `not_found` | rule id 不存在 | 报错，不返回空正文 |

**锚点缺失的降级行为**：不静默返回空。返回 `anchor_missing=true`、章号、该章开头 200 字，并提示「证据句未能定位，可先用 `rule(id)` 看证据句。」这样 agent 至少能判断这条规则是否值得继续追。

### 5.6 `similar(id, k)`

```json
{
  "status": "ok",
  "id": "r7-637725d1",
  "items": [
    {"id": "r7-d337f831", "summary": "用诱饵引反派靠近，短句完成刺杀",
     "path": "style/combat/climax/action", "chapter_no": 71}
  ],
  "truncated": false
}
```

- 同 `l4` + 同 `l3` 优先；不足再放宽到同 `l2`。
- 用于「还没真正理解，继续找」。

### 5.7 `context_expansion_count`

- 定义：同一 `rule_id` 在同一检索会话里，**成功返回 delta** 的次数。
- 首次默认窗口不计；重复请求同一范围不计；`anchor_missing` 不计。
- 写入 `retrieval_logs.context_expansion_count`（见 5.8，轨迹表与检索流水是同一张表），并按 rule 聚合到 `rule_quality_stats`。
- 用途：
  - `≥3` → 标 `needs_rewrite`，说明规则原文表达不清，不是模型不会读。
  - 同时记录最后用到的 `width`：600 内读懂算「词法/句式问题」；1,200+ 才读懂算「规则结构问题」。
  - 每周导出 `needs_rewrite` 清单，优先重写或合并；连续 4 周无人扩展且检索命中低的规则进归档候选。

### 5.8 轨迹表（作者 / 助理共用一张 `retrieval_logs`）

**一次工具调用一行**，作者 agent、助理 agent、系统自动调用写同一张表，靠 `agent_kind` 区分。
不另建「助理专用表」——分表会让「谁在越界」这类跨角色统计变成两条 SQL，且字段一改就要改两处。

| 字段 | 类型 | 含义 |
|---|---|---|
| `agent_kind` | str | `author` / `assistant` / `system` |
| `session_id` | str | 一次 agent 会话；`context_expansion_count` 按它分组 |
| `turn_no` | int | 第几轮（一次用户请求 = 一轮） |
| `seq` | int | 轮内调用序号，从 1 递增 |
| `segment_no` | int | 当前写第几段；`adopted_rule_ids` 按段回填 |
| `tool_name` | str | `browse` / `search` / `rule` / `anchor` / `similar` |
| `path` | str | 检索路径（可为短路径） |
| `query` | text | 检索词；非 search 为空 |
| `hit_ids` | JSON | 本次命中的卡片 id 列表（按返回顺序） |
| `returned_chars` | int | 实际返回字数（预算/截断后） |
| `budget_remaining` | JSON | `{"calls": n, "chars": n, "turns": n}`，调用后剩余额度 |
| `budget_pool` | str | `catalog` / `rule` / `anchor` / `writing`，见 5.12；空段不计 |
| `latency_ms` | int | 本次调用耗时 |
| `status` | str | `ok` / `empty` / `budget_exhausted` / `denied` / `error` |
| `context_expansion_count` | int | 同会话同 rule 成功拿 delta 的次数（首次默认窗口不计） |
| `adopted_rule_ids` | JSON | **本段实际采用**的规则 id；段结束回填到该段所有行 |
| `soft_flags` | JSON | 监察官软档标记（见 5.10），只记录不改结果 |

两条写入纪律：

1. **`adopted_rule_ids` 必须段末回填**（`UPDATE retrieval_logs SET adopted_rule_ids=? WHERE session_id=? AND segment_no=?`）。
   不回填的行视为「未统计」，**不能当作「查了不用」**——否则会把「还没到段末」误判成空转。
2. **`denied` / `budget_exhausted` 也要落行**。只记成功调用，会让「被护栏拦下」在轨迹里消失，
   事后无法区分「模型没查」和「查了被拒」。

### 5.9 五类问题怎么查（可直接落成 SQL）

1. **空转**：同段内 `status='ok'` 的调用数 `N`，`adopted_rule_ids` 去重条数 `A`；
   `N ≥ 5 且 A ≤ 1` 记空转。分母用「有 adopted 回填的段」，未回填的段不进统计。
2. **重复**：同 `session_id` 内 `(tool_name, query, path)` 完全相同的调用 ≥3 次；
   只统计 `status='ok'`，重试（`error` 后成功）不算重复。
3. **越界**：`path` 的 L2 场景域与「当前段的目标场景域」不一致。目标场景域取该段写作指令里的
   显式场景词；抽不出场景词时**不判越界**（宁缺毋滥）。跨场景占比 = 不一致调用 / 有 L2 的调用。
4. **查了不用**：`hit_ids ∩ adopted_rule_ids = ∅` **且** `style_check` 在该段检测不到对应措辞特征
   （短句占比、对白段占比、拟声/比喻密度等按规则类型映射）。只有两边都成立才记，
   否则标 `unverified`——单看命中未采用会把「采用了但换了说法」误伤。
5. **凭空编**（**只做提示，不下结论**）：用规则关键词反向扫正文，一条规则都对不上时记提示项。
   它可能只是新写法，不能作为违规判据，也不能触发打回。

### 5.10 监察官（助理 agent）

**软档（默认开启，本期实现）**：只写 `soft_flags`、告警、给建议，不改生成结果。

| 触发 | 阈值 | 建议文案方向 |
|---|---|---|
| 单段 anchor 过多 | >6 次 | 「本段扩窗已 7 次，先读 `rule(id)` 原文再决定是否继续」 |
| 同 query 重复 | ≥3 次 | 「同一 query 查了 3 次，换关键词或换层级」 |
| 命中 0 采用 | `hit_ids` 非空、`adopted_rule_ids` 为空 | 「命中 4 条但一条没用，说明检索词与场景不匹配」 |
| 跨场景域检索 | 占比 >50% | 「写群聊日常却在拉战斗爆发，检查 path」 |

**硬档（本期不实现）**：只允许两种打回——**超出护栏**（轮次 / 字数）与**越界检索**。
- 打回必须落一句具体理由（`reject_reason`），不能只写状态码，否则事后分不清是模型跑偏还是监察官误伤；
- 打回要可回滚：保留该段快照，恢复时按快照回写，不重跑；
- 阈值现在没有数据支撑（>6 次、≥3 次、50% 都是拍的），等小样跑出真实轨迹再校准，
  **先不写死拦截**。

**作者可读自己的轨迹**：只读、按 `session_id` 限定自己的行。理由：模型看到「刚才同一件事查了三次」，
下一轮会自己改；只给监察官看，纠错永远滞后一步。

### 5.11 反哺闭环：轨迹 → 规则权重 → 卡片排序

- 计数口径：`retrieved_count` = 该 rule 出现在 `hit_ids` 的次数；`adopted_count` = 出现在
  `adopted_rule_ids` 的次数（都要去重到段）。
- 写入已有表 `narrative_rule_weights`，**只影响卡片排序分**，不改规则原文、不改档案 JSON。
- 调整方向：
  - `adopted_count / retrieved_count` 高（≥0.5 且 `retrieved_count ≥ 5`）→ 升权，幅度 ≤+0.1；
  - `retrieved_count ≥ 10` 且 `adopted_count = 0` → 降权，幅度 ≤−0.1；连续两周如此进归档候选；
  - 只被检索 1–2 次的规则不动（样本不足，避免噪声放大）。
- 批量节奏：两周一次离线汇总，人工抽查 10 条降权卡，确认不是检索器本身的问题再落库。
- 回滚：每次批量写入带 `batch_id`，出问题按批回退，不逐条改。

### 5.12 目录骨架常驻 + 四池预算

> 2026-11-12 重做：上一版「15 次 / 20,000 字单池」会逼模型跳级——目录还没爬完就得开写。
> 这一版把**目录骨架直接注入系统提示**，并把预算拆成四类池，各自软着陆。

#### 5.12.1 目录骨架常驻（不让模型爬级）

把五级路径压成一张**骨架表**：每条路径只写名字 + 条数，不写规则内容。模型开局就知道
「战斗对峙/爆发/动作 有 188 条」，不需要 L1→L2→L3→L4→L5 一路 `browse` 下来。

**四条硬约束（换书不许破）**

1. **结构层固定、计数层随书。**
   L2 14 个场景域、L3 6 个节拍、L4 8 个技法的**名字与 key 写死在代码里**（§2.3–§2.5
   的三张表即唯一来源），不因书而变；这样跨书路径可比、规则可迁移、同一段 prompt
   在换书后只有数字在动。注入内容 = **路径名 + 当前档案条数**，不拼任何书名/角色名。
2. **空路径与稀疏路径。**
   - `count = 0` 的路径**不列**：绝不能让模型去检索空抽屉白烧调用。
   - **只列条数 ≥5 的路径**；`< 5` 的路径不单独占行，计数并入上一级只留总数。
     完整路径表交给 `browse(path, depth=2)`，骨架只负责「让模型知道大概有哪些、各多少」。
   - **词表冲突要留痕**：若某本书 `count = 0` 的 L2 域 ≥ 1/3（≥5 个），说明这 14 个
     场景域不适合这本书，报告里必须输出「**该书场景域严重偏斜**」并列出空域清单，
     写进 `catalog_skeleton_stats.skewed = true` + `empty_l2[]`；**不允许静默裁掉**。
     实测两本书都只有 1/14（7%），均不触发（见 §5.12.6）。
3. **按三种形状分节，通用排最前。**
   骨架分三节：**通用（global）→ 结构（structural）→ 技法（technique）**。
   通用排前是刻意的：它是全书底子（句长、段落、潜台词这类跨场景约束），模型先看到
   底子、再看场景细化，写任何场景都不会漏掉基线；反过来把通用放尾部，一旦触发字数
   封顶，最先被截掉的恰好是最通用的那批规则。三节内部各自按条数降序。
4. **排序与缓存。**
   - 排序：按本档案条数**降序**（节内 L2 之间、同一 L2 下的 L3/L4 之间都降序）。
   - 缓存键 = `distill_id + catalog_version`（档案 id + 目录版本）；档案重建或路径
     增删时 `catalog_version` 自增，旧骨架自动失效，不每次渲染现算。
   - 落地字段：`style_narrative["catalog_skeleton"]` + `catalog_skeleton_version`
     + `catalog_skeleton_stats`（路径数、字数、空域、生成时间）。它是**渲染缓存**，
     不进 `NARRATIVE_VERSION` 指纹（与节拍骨架同理）。
   - 重建触发：建目录/删路径、条数变化超过 20%、`L2/L3/L4` 常量表或形状映射变更
     （代码发布时把版本号写进 `catalog_version`）。

#### 5.12.2 四个池，分开计

不要用一个总数计费，否则必然出现「目录花完了，原文没额度」。

| 池 | 工具 | 额度 | 返回字数 | 备注 |
|---|---|---|---|---|
| `catalog` 目录类 | `browse` / `search` / `similar` | 30 次 | 8,000 字 | 便宜，宽给 |
| `rule` 规则类 | `rule` | 12 条 | 4,000 字 | 含时间线描述 |
| `anchor` 锚点类 | `anchor` | 6 条规则 | 合计 15,000 字（单条 ≤4,000） | 最贵，单独池 |
| `writing` 写作回查 | `anchor` / `rule` 回查 | 5 次 | 4,000 字 | 独立，前期探索不得占用 |

合计约 30 次调用 / 2.7 万字。数字可按实测微调，但**四类必须分开计**。
- 预算**按单段独立计算**，不按整章、不按会话累计；上一段用得多不影响下一段。
- 探索三池（catalog/rule/anchor）剩余额度**不带入** `writing`；
  `writing` 没用完也不回滚到探索池。
- `writing` 只允许两种调用：已命中规则的 `anchor` 扩窗、`rule(id)` 复读。

#### 5.12.3 防跳级：耗尽时必须说「还缺哪一层」

某个池接近上限时，返回不能只说「额度不多了」，而要指出**当前路径树里还没查的层**：

```json
{
  "budget_pool": "catalog",
  "budget_stage": "consolidate",
  "budget_remaining": {"calls": 2, "chars": 900},
  "missing_layers": ["L3", "L4"],
  "suggested_paths": ["style/combat/爆发", "style/combat/余波"],
  "consolidate_only": true,
  "available_materials": [
    {"path": "style/combat/爆发", "count": 12},
    {"path": "style/groupchat/建置", "count": 3}
  ],
  "instruction": "目录额度剩余 2 次；L3/L4 未查，先用骨架里的 path 直接 browse(depth=2) 或 rule(id) 读已命中规则"
}
```

`missing_layers` 的算法：以当前已查过的 path 为根，对比骨架里该子树存在、但轨迹里
没出现过的层级。模型据此知道「粗颗粒开写会丢什么」，而不是被动被切断。

#### 5.12.4 三档软着陆（**按每个池各自算**，不合并）

```
每个池：使用率
  0% ─────────── 70% ──────── 90% ──────── 100%
     normal        hint       consolidate    exhausted
```

| 档位 | 触发 | 返回里带什么 | 允许的调用（仅限该池） |
|---|---|---|---|
| `normal` | <70% | 无 | 该池全部工具 |
| `hint` | ≥70% | `budget_hint`：该池剩余次数/字数 + 建议收敛 | 该池全部工具（不拦） |
| `consolidate` | ≥90% | `consolidate_only=true` + `missing_layers` + `available_materials` | 该池只允许收束类：`browse(depth=2)`、已命中规则的 `anchor`、`rule(id)` |
| `exhausted` | =100% | **不报错**：该池已获取内容 + `instruction` | 该池关闭；其他池仍可用 |

- 一个池进入 `exhausted` **不影响**其他池。切换信号仍是显式 `enter_writing`；
  若生成侧已开始产出正文却没调用，系统自动切一次并补 `agent_kind='system'` 轨迹行。
- **硬档不得因预算用尽打回**：预算是正常结束，不是违规。硬档只拦越界检索与超出硬护栏。
- **中断可续**：某池耗尽时，把中断点（已查 `path`、已命中未采用的规则）写进轨迹；
  下一段作为**初始材料**注入，不占下一段预算。

#### 5.12.5 「某池耗尽、其他池还有余」的返回语义

| 耗尽池 | 仍可用的池 | 返回里必须写 |
|---|---|---|
| `catalog` | `rule` / `anchor` / `writing` | 「目录额度已尽，直接用 `rule(id)` 读已命中的规则，或 `anchor` 读原文」+ 已命中 id 清单 |
| `rule` | `anchor` / `writing` | 「规则正文额度已尽，可对已命中规则 `anchor` 读原文」+ 已命中 id 清单 |
| `anchor` | `rule` / `writing` | 「原文额度已尽，只能按规则摘要写」+ 已读原文的规则 id |
| `writing` | 无（探索段已结束） | 返回已获取全部内容 + `instruction="用现有材料写完本节"` |

统一字段：`pool_exhausted`（池名）、`pool_remaining`（其余三池余额）、
`available_materials[]`。**禁止**把「某池耗尽」表达成整体失败（`status=error`）。

四条结论：

1. **结构层确实稳**：两本书的三节结构、L2/L3/L4 命名完全一致，只数不同，跨书路径可比。
2. **场景分布不能用一本书的直觉推另一本**：群聊/日常在 novel 7 有量，在书 5/6 近于空；
   换书后骨架必须重算，不能拿旧书的 counts 缓存（这也是缓存键必须带 `distill_id` 的原因）。
3. **structural 护栏只剩节拍序列，两边都过**：15% / 14%。剧情编排/伏笔改判 technique 后，
   不再有「章级骨架被拖去判节拍」的假超标；**原「书 5/6 换书风险」记录销掉**，
   不单独设阈值、不动节拍词表。
4. **global 不是大头，但「跨场景」是**：global 形状只占 36%/28%；若把 technique 里
   判不出场景的 7,519/3,681 张也算进来，则有 **82% / 91%** 的 style 规则不挂场景
   （改判把剧情编排/伏笔的无场景卡也算进来，比例比上一版更高）。
   ——「大部分文风规则跨场景」成立，但它们的形状是 technique（路径 `style/技法`），
   不是 global；通用节只装 global 维度（§2.7 规则 2），不把跨场景技法混进去。

### 7.4 区分度指标

1. **最长公共路径前缀（LCP）**：两张 query 的 top 10 命中卡，逐对计算路径公共前缀层数，取最大值。
   - LCP ≤1（只共享 L1）→ 场景区分度合格。
   - LCP =2（共享 L1+L2）→ L2 场景域需要调整。
   - LCP ≥3 → 路径退化，停止全量。
   - 同时报「LCP ≥2 的配对占比」，避免最大值被单对例外拉高。
2. **场景口径的命中占比与分散度（14 个 L2 场景）**：`topic_ids` 不再用于验收。
   - 目标场景命中占比 = top 10 里 `scene ∈ query 场景` 的条数 / 10。
   - **相对基线增益** = 目标场景命中占比 − 全样本该场景占比。
     全样本基数（重抽 500 张）：`cultivate` 21%、`combat` 16%、`groupchat` 15%、
     `travel` 8%、`trade` 6%，其余 ≤2%；**未挂场景 23%**。
     （首轮 500 小样的旧基数 `combat 19% / cultivate 18% / groupchat 16% / 未挂 26%` 已作废——
     那是维度配额抽样，structural 被抬到 30%。）
   - 分散度 = 覆盖场景数 / 主场景占比 / 未挂场景占比。**先验开时分散度不是质量指标**
     （先验就是要把结果压到目标子树），分散度在**先验关**的检索上统计。
   - **先验权重扫描**（校准用；**0.20 已定为默认值**，写入 `catalog_config`）：

     | w | Q1 目标场景 | Q1 覆盖场景 | Q2 目标场景 | Q2 覆盖场景 |
     |---|---|---|---|---|
     | 0.00（关） | 50% | 3 | 80% | 3 |
     | 0.10 | 80% | 2 | 80% | 3 |
     | **0.20（默认）** | **90%** | 1 | **90%** | 3 |
     | 0.35 | 100% | 1 | 100% | 2 |

     （首轮旧样本扫描 `0.00→10% / 0.10→70% / 0.20→90% / 0.35→100%` 已作废。）

   - 读数：Q1 是纯文本匹配的反例——**先验关时 combat 只占 50%**（旧样本更低，10% vs 19% 基线，
     比随机期望还差 9pt），说明「战斗/爆发/拟声」这些词在卡片摘要里没有把 combat 卡顶上来，
     高频通用词（短句/对白/描写）压过场景词；**场景先验是必需项，不是优化项**（见 §0 第 14 条）。
     先验开到 0.20 后 combat 回到 90%（+74pt）。Q2 先验关就 80%（+62pt），先验只是保险。

3. **命中集合 Jaccard**：`|A∩B| / |A∪B|`，目标 <0.2。
4. **停在 L2 的比例（只卡 `structural`，即节拍序列）**：
   - 统计范围：只算 §2.7 的 `structural` 维度（现在**只剩节拍序列**）；剧情编排、
     伏笔已改判 `technique`，`technique` / `global` 本来就不挂 L3，均不计入。
   - 分母 = structural 里到达 L2 的规则数；分子 = 其中停在 L2 的规则数。
   - **>40% 视为不合格**；节拍序列维度 ≤20%（它自带节拍标签；若它也超，
     说明标签抽取坏了，不是词表问题）。

   **全量实测（2026-11-12，不是 500 小样）**：

   | | novel 7 | 书 5/6 |
   |---|---|---|
   | structural（节拍序列）停在 L2 / 到达 L2 | 204/1,351 = **15%** | 25/173 = **14%** |

   重抽 500 后是 **12/53 = 22.6%**（structural 70 张里 53 张到达 L2）：分母比首轮小样
   （29/105 = 27.6%）小，是因为按全量比例只抽 70 张节拍卡，不是判定变差。

   与全量 15% 不冲突，**以全量 15% 为准**，不据此改词表。
   **口径变更留痕**：2026-11-12 之前按「全部维度、分母=到达 L2」统计，首轮 500 小样报

   **这两个数及旧口径均已作废**，不得再引用。首轮小样的 27.6% 也因抽样口径作废。

   **结论：全量两边都过线（15% / 14%），不存在换书风险。** 剧情编排/伏笔改判 technique 后，
   原先的 99%/93%（novel 7）与 100%/97%（书 5/6）不再参与任何阈值；
   **「书 5/6 换书风险」记录销掉**，不单独设阈值、不动节拍词表。
5. **query 命中里不挂场景的占比**：
   - 分别统计两个 query 的 top 10 里 `scene is None` 的比例，与全样本基数（23%）比。
   - 两个 query **都有一大半**不挂场景 → L2 场景域没把两类内容分开，
     停下来回看场景域划分，**不得直接进全量**。
   - 重抽 500 实测：Q1 **1/10 = 10%**、Q2 **0/10 = 0%**（全样本基数 23%），
     两个 query 的 `style/技法` 命中均为 0 条。
6. **锚点三类分布（只报数，不设通过门）**：
   - 报 `exact / fuzzy / missing` 三类的条数与比例，**再按证据长度拆一次**
     （≥15 字 / <15 字），因为短证据的 `fuzzy` 只保证首尾 3 字在窗口内出现过，
     不能当精确出处。
   - 同时报命中层级（`full / inner_quote / short_anchor / normalized / segment`）
     与锚点跨度中位数。
   - 重抽 500 实测：`exact 159 (31.8%) / fuzzy 334 (66.8%) / missing 7 (1.4%)`；
     长证据（≥15 字）254 张 = exact 159 + fuzzy 88 + missing 7；
     短证据（<15 字）246 张 = fuzzy 246（**全是弱锚点**）；
     命中层级 `short_anchor 244 / inner_quote 80 / segment 79 / full 79 / normalized 11 / none 7`，
     锚点跨度中位数 14 字；章号偏移 `+0:221 / +1:90 / +2:67 / +3:52 / +4:63`，
     纠正 493 张、其中偏移 >0 的 272 张。
   - **读法**：`missing 1.4%` 是「5 章窗口 + 8 字段匹配」的上限，不等于 500 条都锚到了
     语义正确的句子；短证据那 246 条（49%）必须按弱锚点看待。真正的上限由新蒸馏
     （证据 ≥20 字 + `chunk_id/evidence_chapter_no` 落库）决定，见 §4.1。
7. **人工可读性**：随机抽 10 张卡，摘要必须能在原文找到对应分句。

### 7.5 通过标准

- 建卡成功率 ≥90%（硬过滤淘汰不计入分母）。
- **锚点不设 ≤15% 的通过门**，改为如实报告三类分布；`missing` 的卡必须带章号降级。
  报告里必须同时给「按证据长度拆分」的两行，不允许只报一个合计比例。
- **Q1 相对基线有正增益**（先验开 vs 全样本场景基数）；Q2 的 `groupchat + daily`
  占比不低于基线。重抽 500 实测 Q1 **90% vs 16%（+74pt）**、Q2 **90% vs 18%（+72pt）**，**均满足**。
- Q1/Q2 的 LCP ≤1，且 LCP ≥2 的配对占比 ≤10%；Jaccard <0.2。
  重抽 500 实测 LCP 最大 1、≥2 占比 0%、Jaccard 0.000。
- **分散度按 14 个 L2 场景报**（覆盖场景数 / 主场景占比 / 未挂场景占比），
  且**先验关**时未挂场景占比不得高于全样本基数。`topic_ids` 不参与判定。
- **structural 停在 L2 的比例 ≤40%**；structural 现在只剩节拍序列，节拍维度 ≤20%；
  technique / global 不计入。全量实测 novel 7 **15%**、书 5/6 **14%**，
  重抽 500 小样 **22.6%**（12/53），均在 40% 线下。
- 两个 query 的 top 10 命中里，不挂场景占比**不能同时超过一半**；
  若同时过半，回看 L2 场景域划分，停止全量。
- 10 张抽查卡摘要 10/10 可在原文定位。

通过后再接工具层，让作者 agent 真实走一次 `browse → search → anchor → similar`，贴轨迹。

| Zhipu `glm-4-flash-250414` | 不合格 | 200 响应里 10/12 | 无法连续跑（并发 5 → 13/25 是 429） | ¥0 | — | 否 |

**结论：免费模型都不达标，不切换。** 省下的 $9 不值得拿 280 块的证据质量去换。

### Zhipu BigModel（open.bigmodel.cn）实测

- 接入位置：`backend/app/config.py` 的 `zhipu_*` 配置（base_url `https://open.bigmodel.cn/api/paas/v4`）、
  `backend/.env` 的 `ZHIPU_API_KEY`、`backend/config/providers.yaml` 的 zhipu 段；
  **`glm-4-flash` 就是当年「764 章 42 分钟 ≈ 16.5s/块」基准用的模型**。
- `GET /models` 返回 12 条：`glm-4.5 / 4.5-air / 4.6 / 4.7 / 5 / 5-turbo / 5.1 / 5.2 / 5.3 /
  5.3-flash / 5.3-flashx / 5.3-flashx-legal`——**`glm-4-flash` 已被移出列表，但仍可调用**。
- 可用性实测：`glm-4-flash` → 200 / 1.21s；`glm-4.5-air`、`glm-5.3-flash`、`glm-5.3-flashx`
  → **429 `{"code":"1113","message":"余额不足或无可用资源包,请充值。"}`**。
  该账号**只有 glm-4-flash 免费档可用**，新模型全部欠费。
- 5 块试跑（1800–1824、不写库、`max_tokens=8192`、块内 5 并发）：
  HTTP 25/25 = 200、429 = 0；JSON **23/25 = 92%**（两次失败都是「字段坏」：输出仅 702 / 939 字、
  `finish_reason=stop`，维度键缺失）；证据 ≥20 字 **89.2%**（中位 36，最短 11）；
  单块 **44.7 / 633.7 / 55.4 / 53.7 / 58.0s**——**有一次单调用排队 634s**，长尾不可接受；
  `cached_tokens` 恒为 0（无前缀缓存）。
- 结论：历史基准的 16.5s/块是旧提示词（维度少、块小）下的数；v7 五调用口径下 **glm-4-flash
  三条判定线全不过**，不切换。若要长期用 GLM，需用户给 BigModel 账号充值后测 `glm-5.3-flash`。
- 项目默认档 `glm-4-flash-250414`（`config.py` 的 `zhipu_model`）更差：同样 5 并发跑 1825–1849，
  **25 次里 13 次 429 `{"code":"1302","message":"您的账户已达到速率限制"}`**，免费档扛不住
  5 并发；能返回的 12 次里还有 2 次「字段坏」。`glm-z1-flash` 可调（200），但带 think 段、更慢。
  → **该账号的免费档只能单路低速使用，不能作为 635 块批跑的通道。**
- **flash 变体逐 id 探测**（`/models` 不全会漏，必须直接打 id）：

  | id | 结果 | 性质 |
  | --- | --- | --- |
  | `glm-4-flash` | 200 | 免费档可用，已从列表下架 |
  | `glm-4-flash-250414` | 200 | 免费档可用，已下架，5 并发即 1302 |
  | `glm-z1-flash` | 200 | 免费档可用，带 think 段 |

  | `glm-4.7-flash` | 429 `1305 该模型当前访问量过大`（连试 3 次） | 疑似免费但当前过载 |

  | `glm-4.7` / `glm-5.2` | 429 `1113 余额不足` | 付费档，已欠费 |

  `glm-4.5-flash` 的 5 块试跑（1900–1924，**块内 2 并发**，避免把 1302 误判成模型质量）：
  24 次返回里 **5 次 JSON 解析失败（79%）**——全部是「字段坏」（输出 522–935 字、
  `finish_reason=stop`、维度键缺失）；单块墙钟 **376 / 217 / 900（含一次 826s 调用）/ 198s**；
  第 25 次调用挂起超过 10 分钟，被我终止。`cached_tokens` 命中 4–19（缓存确实生效）。
  → **免费档 flash 变体全部不可用于批跑**：要么限流（1302）、要么过载（1305）、
  要么裸提示词 JSON 不稳、要么延迟长尾到十几分钟。
  这些「已下架的免费 id」只能当单路备用，不能写进生产通道。

**额度审计补充**：Go 端点 `GET /inference/go/v1/usage` 返回 `rolling 71% / weekly 54% /
monthly 100%（rate-limited，2026-11-29T02:03:30Z 重置）`，且 GLM 在 Go 上同样 429
（`limitName: monthly`，`Retry-After≈16.6 天`）。**这说明该套餐的月额度是 workspace 级共享，
不是「按模型分开算」**；之前「deepseek 撞墙不影响 GLM」的推测不成立。

### 成本口径

- 卡摘要约 30 字 × 32k ≈ 100 万字，embedding 一次。
- 检索只读卡；只有命中 3–5 条才读原文/锚点。
- 性能目标：`search` P95 <200ms（卡表 + 现有打分缓存）；`anchor` 只做字符串切片，P95 <50ms。

## 9. 风险

1. **路径判定漂移**：L2/L3/L4 若用模型自由判定，会重演「主题名漂移」。约束：显式关键词优先，分类器只做兜底；路径变更必须留 `path_source`（keyword/classifier/manual）。
2. **摘要自由概括**：用 3.2 的包含度校验卡死；不通过就不建卡。
3. **锚点回填失败**：历史档案的证据句可能被改写或跨段，精确匹配失败率高。降级为章号 + 章首 200 字，不静默返回空。
4. **agent 过度探索**：5 次/轮、3 轮、8,000 字 anchor 预算；超限返回 `budget_exhausted`，不无限试探。
5. **规则质量反馈滞后**：`context_expansion_count` 需要至少一个月的真实调用才有统计意义，前期只记录不决策。
