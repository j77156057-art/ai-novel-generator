# 文风一致性校验：设计方案

> 状态：设计稿（只读调研完成，未改任何代码 / 未重启服务 / 未动生成流程）
> 数据基准：项目 5（`novel_dev.db`）、`generations` p1 3 段 + p5 2 段、上一轮 34 段真实生成样本
> 标注约定：**[实测]** = 本库/本轮实验直接量出来的数；**[估算]** = 由实测推导，附推导依据

---

## 0. 结论先行

### 0.1 一句话

**这套校验器只能可靠地做一件事：判断「这一段和这个项目自己过去写的正文，在可计算的文本特征上差得远不远」。它不能判断「像不像参考作者」，也不能判断「规则有没有被遵守」——这两件事上一轮已经被实测证伪，设计里必须把它们从判据降级为解释项。**

### 0.2 关键取舍（推荐值 + 理由）

| 决策点 | 推荐 | 理由（数字见正文） |
|---|---|---|
| 参照系 | **项目自身已接受正文为主判据**；参考语料统计带只在冷启动写偏离说明（不产出判定）；232 条规则只做解释，不做判据 | 用参考带（P10–P90 + ≥2 项越界）判 5 段已接受正文，**4 段 fail，误报 80%** [实测]；规则块整块删掉对正文无可测影响（p>0.86）[实测] |
| 判据指标 | **核心 8 项进阈值**（句长均值、句长 CV、短句占比、段均句数、对白字占比、逗号密度、虚词密度、四字格密度），其余 12 项只展示不判 | 零膨胀特征（参考 p50=0 的段尾升华率、情绪直陈密度、省略号密度）用分位判界会退化成「出现一次即越界」；8 项已覆盖长度 / 节奏 / 对白 / 用词 |
| 阈值分位 | `fail` = 核心 8 中 **≥3 项**落 P1/P99 外；`warn` = **≥2 项**落 P1/P99 外或 **≥4 项**落 P10/P90 外；项目级再要求 **3 段中 ≥2 次** | 20 项「任一越界」误报 87.8%、10 项 65.1% [估算]；核心 8 项 + ≥3 在独立假设下 0.08%，相关性上调后按 1–5% 估 [估算] |
| 第一阶段阻断 | **不阻断**，只记录（影子模式） | 单段重写不可回滚；且现有校准集只有 5 段；误报率在 200 段以内估不准 |
| 阶段推进门槛 | 影子期 ≥200 段且人工抽检误报 ≤10%，才允许进「提示」；≥400 段且误报 ≤5%，才允许对「极端离群」阻断 | 见 §3.5 的样本量计算 |
| 明确判不了的项 | 「与参考作者的文风相似度」「规则服从度」 | 相似度 0.0562 vs 0.0567，无区分度 [实测]；规则块删掉后五项指标 p>0.86 [实测] |

### 0.3 必须先接受的三个事实

1. **校准集只有 5 段，且项目内差异极大。** p1 三段（`style_profile` 同口径）：句长 24.85 / 22.47 / 15.92，短句占比 2.6% / 10.9% / 40.3%，对白字占比 1.4% / 15.1% / 28.5% [实测]。5 段合并后短句占比跨度 2.6%–40.3%（15 倍），对白 1.4%–29.7%（21 倍）。用这 5 个点定阈值，等于用 5 个点画一条正态曲线。
2. **参考带的分布是「另一本书」的分布，而且它离模型输出更近、离用户已接受正文更远。** `buckets.short`（800 个 1500 字单元）短句占比 p10/p50/p90 = 15.1%/21.9%/28.7%，min = 6.9% [实测]；而本项目已接受的 p1 段 1 是 2.6%，比参考书 800 个单元里的最小值还低（z ≈ −3.5），同时段均句数 2.60 高于参考 p90 = 2.07（z ≈ +3.2）、对白 1.4% 低于参考 min = 2.7% [实测]。按参考带 P10–P90 + 「≥2 项越界」判这 5 段，**4 段 fail** [实测]。反过来，上一轮 34 段模型生成样本的短句占比中位 21.5%–29.3%，几乎贴在参考 p50 = 21.9% 上 [实测]。**所以参考带根本区分不了「用户要的风格」和「模型的默认风格」——用它做 fail 会稳定误杀用户已经接受的正文，却放过模型默认文风。**
3. **规则块对正文没有可测影响。** 整块删除 vs 原样保留，字数/句长/短段/对白/参考相似五项 p 值全部 >0.86 [实测]。所以「规则没被遵守」不能当成漂移信号，否则整块规则会变成一个恒亮的红灯。

## 1. 参照系：三个候选、各自盲区、冲突仲裁

### 1.1 候选 A：参考语料统计档（`projects.style_profile`）

- 数据形态：`buckets.{short,medium,long}.feat.<20 个特征>`，每个特征带 mean/std/p10/p50/p90/min/max，`n_units` 分别为 800 / 800 / 655，`unit_chars` 1500 / 3000 / 6000 [实测]。
- 20 个特征：句长均值、句长 CV、句长 p90、短句占比、长句占比、段长 CV、段均句数、对白字占比、对白段占比、逗号密度、句号密度、感叹号密度、问号密度、省略号密度、比喻密度、情绪直陈密度、段尾升华率、四字格密度、短串占比、虚词密度 [实测]。
- **能保证**：给出一条有统计意义的「参考作品正常区间」，样本量足够（800 单元），分布形状稳定。
- **盲区**：
  1. **题材/人称/时代不同**：参考书是古风 + 都市言情，项目 5 是现代悬疑。同口径下 p1 段 1 短句占比 2.6%（参考 min 6.9%、p10 15.1%）、段均句数 2.60（参考 p90 2.07）、对白 1.4%（参考 min 2.7%），**三项同时落在参考带外** [实测]。
  2. **只描述「参考作者怎么写」，不描述「这个项目要怎么写」**。用户的目标未必是复刻参考作者。
  3. **对白占比的带宽虽宽，仍会误判**：参考 p10/p50/p90 = 12.8%/28.6%/48.9%，而项目 5 段真实正文是 1.4%–29.7% [实测]，p1 段 1 直接落在 p10 以下。
  4. **它更接近模型默认输出**：34 段生成样本的短句占比中位 21.5%–29.3%，与参考 p50 = 21.9% 几乎重合 [实测]。用它当判据，等于把「模型本来就这么写」当成「正确文风」。

### 1.2 候选 B：本项目已写正文的自身基线（`generations`）

- 数据形态：`generations(project_id, segment_no, text, summary)`，**没有时间戳**，只能按 `id` / `segment_no` 排序 [实测]。
- **能保证**：同题材、同人称、同角色名、同世界观下的「你自己平时的写法」。这是唯一与「一致性」语义对齐的参照系。
- **盲区**：
  1. **样本少时不稳定**：现有 p1 3 段 + p5 2 段，段间短句占比 2.6%–40.3%、对白字占比 1.4%–29.7% [实测]。
  2. **会漂移**：如果用户在 20 段里换了写法，基线会跟着漂，校验器会把「新写法」慢慢当成正常。
  3. **有冷启动**：项目刚开写时没有基线。

### 1.3 候选 C：蒸馏出的 232 条规则（`projects.style_narrative`）

- 数据形态：15 类、232 条规则，生成时只渲染 60 条（每类前 3 条，角色声音 20 条）[实测]。
- **能保证**：提供「为什么判它漂移」的解释文本，适合做报告里的说明。
- **盲区**：**它本身对正文没有可测约束力**。整块删除后五项指标 p>0.86 [实测]。因此：
  - 不能把「违反某条规则」当判据；
  - 不能把「规则覆盖率」当质量指标；
  - 规则只能作为 L2（LLM 判）的提示材料，不能进阈值计算。

### 1.4 三者冲突时以谁为准（仲裁规则）

```
优先级 1：项目自身基线（当且仅当可用样本 ≥ MIN_SELF_SEGMENTS）
优先级 2：参考语料统计带（只在冷启动/样本不足时使用，只写偏离说明，不产出 verdict）
优先级 3：蒸馏规则（永不参与阈值；只用于报告解释与 L2 提示）
```

- `MIN_SELF_SEGMENTS = 20` [估算]：低于 20 段时，段间方差会把 P10/P90 拉得比参考带还宽，阈值失去意义。
- **冲突示例**：项目自身 P10–P90 是「短句占比 12%–45%」，参考带是「15%–29%」。此时判「正常」按 12%–45%，不按参考带。参考带的偏离只写进报告的一句话说明，不产生 warn/fail。
- **冲突时绝不做的三件事**：不用参考带否决自身基线；不用规则条目否决任何一方；不改写正文去「对齐」参考带。
- **不可调和的冲突**：如果自身基线连续 10 段都落在参考带之外，说明参考语料与本项目不匹配——此时应提示用户「参考语料与当前项目风格差异较大」，而不是判正文漂移。

## 2. 指标分层

### 2.1 L1：确定性可算（唯一可进阈值的一层）

全部复用 `style_profile.buckets` 的口径，避免「校验器算的句长」和「档案里的句长」不是同一个东西。

| 指标 | 算法口径 | 数据来源 | 成本 |
|---|---|---|---|
| 句长均值 | 按 `。！？…` 切句，去空白后字符数均值 | 生成正文 | O(n) |
| 句长 CV | 句长标准差 / 均值 | 同上 | O(n) |
| 句长 p90 | 句长 90 分位 | 同上 | O(n log n) |
| 短句占比 | 句长 ≤ 10 字的句子占比（与档案同口径） | 同上 | O(n) |
| 长句占比 | 句长 ≥ 40 字的句子占比 | 同上 | O(n) |
| 段均句数 | 句数 / 非空段落数 | 同上 | O(n) |
| 段长 CV | 段字符数的 CV | 同上 | O(n) |
| 对白字占比 | 引号内字符 / 正文字符（`“”` 与 `「」` 都算） | 同上 | O(n) |
| 对白段占比 | 含引号的段落 / 非空段落 | 同上 | O(n) |
| 标点密度 ×5 | 逗号/句号/感叹号/问号/省略号 每千字次数 | 同上 | O(n) |
| 比喻密度 | 「像/如同/仿佛/似的」每千字次数 | 同上 | O(n) |
| 情绪直陈密度 | 情绪词表每千字次数 | 同上 + 词表 | O(n) |
| 段尾升华率 | 段末句含总结/升华标记的段落占比 | 同上 | O(n) |
| 四字格密度 | 连续四汉字串每千字次数 | 同上 | O(n) |
| 短串占比 | 长度 ≤ 4 的连续汉字串占比 | 同上 | O(n) |
| 虚词密度 | 「的/了/着/是/在/就/都/也」每千字次数 | 同上 | O(n) |

**成本**：单段 < 5 ms（纯字符串处理），可同步也可异步，不涉及模型。

**哪些进阈值（关键取舍）**：只有 **核心 8 项** 参与判定——句长均值、句长 CV、短句占比、段均句数、对白字占比、逗号密度、虚词密度、四字格密度。其余 12 项只展示，理由分两类 [实测依据见参考带分位]：

- **零膨胀，分位阈值会退化**：段尾升华率（参考 p50 = 0、p90 = 0.032）、情绪直陈密度（p50 = 0）、省略号密度（p50 = 0、p10 = 0）、感叹号密度（p10 = 0）、比喻密度（short 桶 p10 = 0）。这些指标 P1 就是 0，任何一次出现都算「越界」，等于恒亮红灯。
- **高冗余**：句长 p90、长句占比（与句长均值、短句占比共线）、段长 CV（与段均句数共线）、对白段占比（与对白字占比共线）、短串占比。

8 项已覆盖 长度 / 节奏 / 对白 / 用词 四个可判维度，再往上加不会增加区分度，只会增加误报（见 §3.4 的推导）。

### 2.2 L2：只能 LLM 判（不进阈值，只做报告解释）

| 指标 | 判法 | 数据来源 | 成本 |
|---|---|---|---|
| 人物口吻是否匹配「角色声音」 | 把该段对白与该角色的声音条目一起给模型，问「有没有出戏」 | 正文 + `style_narrative.rules.角色声音词典` | 1 次调用/段 |
| 潜台词是否成立 | 问「这段对话有没有言外之意，还是把情绪直接说完了」 | 正文 | 1 次调用/段 |
| 场景/节拍是否完整 | 问「这段有没有铺垫—升级—收束」 | 正文 | 1 次调用/章 |
| 视角是否一致 | 问「叙述视角有没有跳」 | 正文 | 1 次调用/段 |

**限制**：
- 只输出 `{dimension, verdict: ok/suspect, evidence_sentence}`，**不输出 0–100 分**——上一轮的教训是，连续分数看起来精确，实际没有区分度。
- 同一段重复判 3 次不一致时，记为 `unknown`，不记 `suspect`。
- 成本 [估算]：按每段 1500 字、单次 2k token 输入算，一次约 0.01–0.03 元，1000 段约 10–30 元。

### 2.3 L3：本质上判不了（明确排除，不用模糊指标凑数）

| 想判的东西 | 为什么判不了 | 证据 |
|---|---|---|
| 「像不像参考作者」 | 字符三元组余弦在旧/新/无三种提示词下分别是 0.0562 / 0.0536 / 0.0567，方向都不一致 | [实测] 34 段生成 |
| 「规则有没有被遵守」 | 整块 6 千字删掉，五项指标 p 全部 >0.86；换 3 条规则的差异方向还和规则相反 | [实测] n=8/臂 |
| 「这一段写得好不好」 | 没有可操作的文学质量标签；LLM 打分与人类偏好相关性未标定 | [未测] |
| 「是不是 AI 写的」 | 检测器在这个库上没有标注集；且与「一致性」无关 | [未测] |

**处理方式**：这三类不进校验器；报告里不出现「文风相似度 87 分」这类数字。如果产品一定要展示「像不像参考书」，只能标成「参考带偏离度（仅供参照，不作为判据）」，并且默认折叠。

### 2.4 小样本可用性（实测波动，回答「1200 字够不够」）

用上一轮 34 段真实生成，按字数分箱，口径与 `style_profile` 一致 [实测]：

| 字数箱 | n | 句长均值 中位（IQR） | 短句占比 中位（IQR） | 对白字占比 中位（IQR） | 段均句数 中位（IQR） |
|---|---:|---|---|---|---|
| ≤1200 | 8 | 22.9（22.2–32.0） | 21.5%（13.3–30.2） | 25.9%（15.2–35.0） | 2.00（1.96–2.09） |
| 1201–2000 | 8 | 19.3（18.3–22.2） | 20.9%（19.1–24.7） | 18.8%（16.6–32.0） | 2.11（2.02–2.27） |
| 2001–3500 | 9 | 20.1（18.0–20.8） | 29.3%（19.2–36.4） | 22.7%（17.2–27.7） | 2.18（2.03–2.28） |
| >3500 | 9 | 20.3（18.7–24.0） | 24.4%（10.1–33.0） | 34.9%（34.2–35.6） | 2.75（2.26–2.99） |

结论（实测支撑）：

- **≤1200 字：单段不可判。** 句长极值 17.6–55.4（3.1 倍），短句占比 0%–39.1%（出现过 0%），对白字占比 0%–36.4%（出现过 0%）。任何「短句占比 < 5% 判漂移」「对白 < 5% 判漂移」的规则都会误报。
- **段均句数在 ≤1200 箱的 IQR 只有 1.96–2.09（宽 0.13），几乎恒定。** 它是「稳定但没有区分度」的指标：能说明「这段不像散文」，不能说明「这段漂移了」。所以它只做辅助，不能单独触发 fail。
- **1201–3500 字：可做粗判，但带必须取自身 P1/P99。** 句长 IQR 宽 2–4 字，短句 IQR 宽 5–17 个百分点。
- **>3500 字：可用。** 但对白 IQR 仅 34.2–35.6，说明长段内部也高度集中，带宽不应压得更窄。
- **推荐**：单段 ≥1200 字才进判定；<1200 字只记录、`verdict = unknown`。

需要多少样本才能把均值估到 ±10%（95% 置信，n ≈ (1.96·CV/0.1)²）[实测 CV，估算 n]：

| 指标 | ≤1200 字样本的 CV | 所需样本 |
|---|---:|---:|
| 句长均值 | 0.43 | ≈ 71 段 |
| 短句占比 | 0.58 | ≈ 129 段 |
| 对白字占比 | 0.63 | ≈ 151 段 |
| 段均句数 | 0.19 | ≈ 14 段（但区分度低，见上） |

**所以「用 1200 字单段做阈值」在统计上不成立**；1200 字只能做「滚动窗口 5 段合并判定」，窗口合并后等效样本量 ×5，CV 降到约 1/√5，才勉强够用 [估算]。

## 3. 阈值怎么定（不接受拍数字）

### 3.1 校准集现状：不够，必须直说

现有真实正文只有 5 段，口径与 `style_profile` 一致 [实测]：

| | 字数 | 句长均值 | 短句占比 | 对白字占比 | 段均句数 | 段落数 |
|---|---:|---:|---:|---:|---:|---:|
| p1 段1 | 1008 | 24.85 | 2.6% | 1.4% | 2.60 | 15 |
| p1 段2 | 1291 | 22.47 | 10.9% | 15.1% | 2.12 | 26 |
| p1 段3 | 1049 | 15.92 | 40.3% | 28.5% | 2.00 | 31 |
| p5 段1 | 1321 | 14.15 | 40.2% | 29.7% | 1.85 | 47 |
| p5 段2 | 2117 | 16.50 | 24.8% | 24.3% | 1.53 | 79 |

**判断：n=5 不足以定任何阈值。** 同项目内短句占比 2.6%–40.3%（15 倍）、对白字占比 1.4%–29.7%（21 倍）；取这 5 段的中位数 ±1 个标准差，p1 段 1 会被自己项目的基线判成 fail。**这不是「参数没调好」，是样本量不足。**

**参考带能不能救急？也不能。** 用参考带 `buckets.short` 的 P10–P90 + 「≥2 项越界」这一最宽松的判法回判这 5 段 [实测]：

| 段 | 越界项 | 结果 |
|---|---|---|
| p1 段1 | 短句 2.6%（< p10 15.1%）、对白 1.4%（< p10 12.8%）、段均句 2.60（> p90 2.07） | 3 项 → fail |
| p1 段2 | 短句 10.9%（< p10）、段均句 2.12（> p90） | 2 项 → fail |
| p1 段3 | 句长 15.92（< p10 17.56）、短句 40.3%（> p90 28.7%） | 2 项 → fail |
| p5 段1 | 句长 14.15（< p10）、短句 40.2%（> p90） | 2 项 → fail |
| p5 段2 | 句长 16.50（< p10） | 1 项 → pass |

**5 段里 4 段被判 fail（80%）。这 5 段全是用户已经接受、已经落库的正文。** 这一条直接决定了：参考带在冷启动期连 `warn` 都不能按 P10/P90 出，只能按「偏离参考均值 ≥3σ」出，并且只进报告不进 UI。

### 3.2 冷启动先验：用参考带，但只写报告

- 取 `style_profile.buckets[short].feat[<指标>]` 的 **mean / std**（1500 字单元，n=800）[实测]，只在自身样本 < 20 段时启用。
- **冷启动期不产出 `warn` / `fail`，只产出 `unknown` + 一句「参考带偏离」说明。** 理由见 §3.1：按 P10–P90 判，用户已接受的 5 段里 4 段会 fail，误报 80%。
- 冷启动期的偏离口径定为 `|z| ≥ 3`（相对参考 mean/std）[估算]：p1 段 1 的短句 z ≈ −3.5 才会被标出，其余 4 段不会被标——这与「只有 p1 段 1 确实极端」的直觉一致。
- **这一段的核心结论**：冷启动期没有判据，只有先验。任何「新项目一开写就提示文风漂移」的设计都是错的。

### 3.3 主判据：自身基线的滚动分位

- 基线窗口：最近 `W = 30` 段 [估算]。样本达到 70 段后，把窗口扩到 70（与 §2.4 的 ±10% 要求对齐）。
- 对 **核心 8 项**（§2.1）计算窗口内的 P1 / P10 / P90 / P99；其余 12 项只算值，不判界。
- **判定规则（单段）**：

```
越界指标 = { m ∈ 核心8 | v_m < P1_m 或 v_m > P99_m }
疑似指标 = { m ∈ 核心8 | v_m < P10_m 或 v_m > P90_m }

若 |越界指标| >= 3                     -> 该段 fail
若 |越界指标| == 2 或 |疑似指标| >= 4  -> 该段 warn
否则                                    -> pass
```

- **判定规则（连续段）**：

```
最近 3 段中 fail >= 2  -> 项目级「持续漂移」告警（report only）
最近 3 段中 warn >= 2  -> 项目级「风格波动」提示（report only）
```

### 3.4 为什么是「核心 8 项 + P1/P99 + ≥3 项」（误报率推导）

[估算，假设指标间独立]

- 20 项指标、各自 10% 概率落在 P10–P90 外、要求「任一越界」：`1 − 0.9²⁰ = 87.8%`。这就是「任一指标超参考带就报警」绝不可用的原因。
- 缩到 10 项仍 `1 − 0.9¹⁰ = 65.1%`；就算改成「≥2 项」也还有 `26.4%`。
- 核心 8 项 + P1/P99（每项 2%）+ **≥2 项**：`1 − 0.98⁸ − 8×0.02×0.98⁷ = 1.07%` → 用作 `warn`。
- 核心 8 项 + P1/P99 + **≥3 项**：`1 − 0.98⁸ − 8×0.02×0.98⁷ − C(8,2)×0.02²×0.98⁶ ≈ 0.08%` → 用作 `fail`。
- 但核心 8 项里句长均值 / 句长 CV / 短句占比 强相关，独立假设会低估。**保守把 fail 的实际误报按 1–5% 估、warn 按 3–8% 估**，影子期必须用实测替换这两个数。
- **阈值也不能无限收紧**：若改成 P0.1/P99.9 + ≥3 项，真漂移也会漏掉。34 段样本里句长极值 55.4（中位 22.9，3.1 倍）这种离群，只要其余指标不动就仍判 `pass`。**判据只能靠「多指标同向」，不能靠「单指标极端」**——这也是为什么本设计不提供「某单项超阈值即告警」的开关。
- **为什么不加回那 12 项**：加回零膨胀项会把每项的有效越界概率从 2% 抬到接近「出现即越界」（§2.1），误报直接失控；这是上一轮「指标凑数」教训的量化版本。

### 3.5 误报率要多少样本才能估准（Wilson 区间）

[估算] 要把误报率估到 ±e：

| 目标误报率 | 允许误差 | 所需段数 |
|---|---:|---:|
| 10% | ±3pp | ≈ 384 |
| 5% | ±3pp | ≈ 203 |
| 5% | ±2pp | ≈ 456 |
| 1% | ±1pp | ≈ 380 |
| 1% | ±0.5pp | ≈ 1521 |

**结论**：
- 影子期至少 **200 段**，才能把「5% 误报」估到 ±3pp。
- 要把 1% 量级的误报区分出「1% 还是 2%」，需要 ±0.5pp 精度，即约 **1500 段** [估算，n = 1.96²×0.01×0.99/0.005² ≈ 1521]；现实里做不到，所以**不要承诺 1% 误报**。
- 在达到 200 段之前，任何阈值都只能算「初值」，必须允许线上调整。

### 3.6 阈值落地方式

- 阈值不写死在代码里，存 `style_baselines`（见 §5）的一行 JSON，带 `baseline_version`。
- 每次基线滚动更新（每新增 10 段）生成新版本，保留旧版本 30 天，便于回溯「为什么当时判了 fail」。
- 阈值更新只影响之后的新判定，不改历史记录。

## 4. 接入点、动作与不阻断原则

### 4.1 三个时机

| 时机 | 触发点（设计参考） | 判定内容 | 动作 | 是否阻断 |
|---|---|---|---|---|
| 生成单段 | `engine` 落库 `generations` 之后（异步） | L1 单段 + 滚动窗口 | 写 `style_checks`；UI 角标 | **不阻断**（第一阶段） |
| 整章 / 批量写完 | 批量任务收尾 | L1 全章 + L2 抽检 1–2 段 | 写 `style_checks`（scope=chapter）；出报告 | **不阻断** |
| 离线全量体检 | 手动触发 / 定时任务 | L1 全量 + L2 全量（可选） | 只出报告，不改正文 | **不阻断** |

**明确推荐：第一阶段三个时机全部不阻断。** 理由：
1. 单段重写**目前不可回滚**（快照机制在另一条线，未落地）；
2. 校准集 5 段，阈值不可信；
3. 模型服从度非 100%，阻断会把「模型不听话」误判成「文风漂移」。

### 4.2 校验不通过时，系统能做什么

| 动作 | 具体行为 | 代价 | 风险 |
|---|---|---|---|
| 只提示 | UI 显示「这一段可能与你的常规写法有差异」+ 展开明细 | 0 | 误报会消耗用户信任 |
| 标记 | 写 `style_checks.verdict`，列表可筛 | 1 次 INSERT | 标记会长期留存，需可撤销 |
| 重写 | 调模型重写该段并覆盖 | 1 次模型调用；覆盖前写 `pending` 快照 | 可能把好段落改坏；有快照可撤销一次 |
| 回滚 | 恢复重写前正文 | — | **重写路径已可用（2026-11-21）**：助手重写与工作台 `/regenerate-stream` 都走两段式快照；新建段的首次生成不产生快照 |

**推荐动作序列**：
1. 第一阶段：只提示 + 标记。
2. 第二阶段：提示里给「重写这一段」按钮，但**重写前必须由用户确认**，并在 UI 明示「重写会覆盖当前正文，可用快照撤销一次（2026-11-21 起重写路径已接快照）」。
3. 「自动重写」仍不做：快照机制已在重写路径落地，但自动覆盖正文仍需要单独的产品决策与确认流程。

### 4.3 不阻断的边界

- 即使进入阻断阶段，也只对 `fail`（核心 8 项中 ≥3 项落 P1/P99 外）阻断，且只阻断「保存」不阻断「生成」——用户可以看完再决定。
- `unknown`（字数不足、指标缺失）永不阻断。

## 5. 报告形态与留痕

### 5.1 存哪里

新增两张表（设计草案，不改现有表结构）：

```sql
-- 基线快照：阈值随项目演进，必须版本化
style_baselines (
  id            INTEGER PRIMARY KEY,
  project_id    INTEGER NOT NULL REFERENCES projects(id),
  baseline_version INTEGER NOT NULL,
  window_segments  INTEGER NOT NULL,      -- 用了最近多少段
  sample_count  INTEGER NOT NULL,         -- 实际参与计算的段数
  source        TEXT NOT NULL,            -- 'self' | 'reference' | 'blend'
  metrics_json  TEXT NOT NULL,            -- {"核心8项": {p1,p10,p50,p90,p99,mean,std,stale_level}}
  created_at    DATETIME NOT NULL,
  UNIQUE(project_id, baseline_version)
);

-- 单次校验结果
style_checks (
  id             INTEGER PRIMARY KEY,
  project_id     INTEGER NOT NULL REFERENCES projects(id),
  scope          TEXT NOT NULL,           -- 'segment' | 'chapter' | 'project'
  generation_id  INTEGER REFERENCES generations(id),   -- 单段时写；整章为空
  agent_run_id   INTEGER REFERENCES agent_runs(id),    -- 助手触发时写；Writer 路径为空
  segment_no     INTEGER,
  chapter_range  TEXT,
  text_md5       TEXT NOT NULL,           -- 判定时的正文指纹，正文后续被改可发现
  check_version  TEXT NOT NULL,           -- 校验器版本
  baseline_id    INTEGER NOT NULL REFERENCES style_baselines(id),  -- 指向具体快照行
  baseline_version INTEGER NOT NULL,      -- 冗余版本号，便于按版本聚合查询
  verdict        TEXT NOT NULL,           -- 'pass' | 'warn' | 'fail' | 'unknown'
  metric_json    TEXT NOT NULL,           -- {"核心项": {...}, "展示项": {...}}
  missing_json   TEXT,                    -- 缺失/不可用指标及原因
  evidence_json  TEXT,                    -- L2 的句子级证据（可空）
  note           TEXT,                    -- 一句话结论（给 UI 用，不含分数）
  stale_at       DATETIME,                -- 正文被改后置位；NULL = 有效
  created_at     DATETIME NOT NULL
);

CREATE INDEX idx_style_checks_proj_created
  ON style_checks(project_id, created_at);
CREATE INDEX idx_style_checks_gen
  ON style_checks(generation_id);
```

> 两处修正说明：`baseline_version` 在 `style_baselines` 里只是 `(project_id, baseline_version)` 复合唯一，单独一列不能做外键，故 `style_checks` 用 `baseline_id` 指向快照主键、另冗余 `baseline_version` 便于聚合；「正文被改」用 `stale_at` 表达，不塞进 `verdict` 枚举，避免污染判定分布统计。

### 5.2 与 `generations` / `agent_runs` 的关联

- **Writer 生成路径**：`style_checks.generation_id` 直连；`agent_run_id` 为空。原因：`agent_runs` 明确只记录 Assistant 调用，Writer 不写该表 [实测：models.py 注释]。
- **助手调用生成路径**：`agent_run_id` 可填；同时仍写 `generation_id`（生成最终落 `generations`）。
- **不能按时间关联**：`generations` 没有 `created_at` 字段 [实测]，只能按 `id`/`segment_no` 排序。设计里所有「最近 N 段」都用 `id` 倒序，不用时间戳。
- **正文被改过怎么办**：`text_md5` 与重新计算的值不一致时，写 `stale_at`，该行不参与误报率统计、也不在 UI 上展示为「当前结论」。

### 5.3 UI 形态

一句话结论 + 可展开明细，不铺一屏表格：

```
这一段和你近 30 段的写法差不多。            [通过]
────────────────────────────────
若需细看： 句长 22.4（你的常规 18–26）     正常
           对白占比 9%（你的常规 17–34）   偏低
           ...
```

- 一句话结论只从四个模板里选（见 §6），不显示分数。
- 明细默认折叠；每行只给「值 / 常规区间 / 正常或偏离」，不给 z-score。
- 「参考带偏离」单独一行，标灰、默认折叠，注明「仅供参照，不作为判据」。

## 6. 误报的用户话术

原则：**说现象，不说分数；给下一步，不给结论。**

### 6.1 单段被判漂移

> 这一段和你平时的写法有点不一样：对白比平时少一些，段落也更长。可能只是这一段的情节需要，也可能是模型跑偏了。
> [看看明细] [重写这一段]

要点：
- 不说「文风一致性 62 分」；
- 不说「判定失败」；
- 把「可能的原因」说出来（情节需要 / 模型跑偏），把决定权交给用户。

### 6.2 连续 N 段被判漂移

> 最近 3 段都和之前的写法有明显差异：句子变长了、对白变少了。如果这是你有意调整风格，可以忽略；如果不是，可能是参考语料或提示词最近改过。
> [查看这 3 段] [检查文风设置]

要点：
- 不重复三次单段告警（会变成噪音）；
- 给出可解释的原因（换档、改参考语料、改提示词）；
- 不自动重写。

### 6.3 指标缺失 / 无法判定

> 这一段太短（不足 1200 字），还不足以判断风格是否一致。已经记录，等写满 3 段后再一起看。

要点：
- 绝不把 `unknown` 显示成「通过」；
- 不显示「无法判定」这种让用户不安的词，改成「还不够判断」。

## 7. 分阶段上线路径

### 阶段 0：影子模式（只记录）

- 内容：L1 全部指标，每次生成后异步计算，写 `style_checks`，UI 不显示任何告警（只在设置里可查）。
- 验证信号：
  1. 落库成功率 ≥ 99%（`style_checks` 行数 / `generations` 新增行数）；
  2. 单段计算耗时 P95 < 50 ms；
  3. 手工抽检 50 段，确认 `unknown` 判定合理（字数确实不足的段被标为 `unknown`）。
- 通过标准：**≥200 段**且人工抽检「明显错误的判定」≤10%。
- 不通过则：调整指标口径，不进入阶段 1。

### 阶段 1：提示模式（只提示 + 标记）

- 内容：UI 角标 + 明细；`warn` / `fail` 都只提示，不阻断；同时上线 L2 抽检（每 10 段 1 段）。
- 验证信号：
  1. 用户点开明细的比例 ≥ 20%；
  2. 用户主动重写的比例 ≤ 10%（过高说明误报太多）；
  3. 人工标注 100 段，误报率 ≤ 10%。
- 通过标准：**≥400 段**且误报率 ≤5%（Wilson 上界 < 10%）。
- 不通过则：不下调阈值，先改指标集合（去掉高方差的「对白段占比」等），再重测。

### 阶段 2：极端离群阻断

- 内容：仅当 `fail` 且「≥3 个指标落在 P1/P99 外」时，在保存前弹确认框；用户可强制保存。
- 验证信号：阻断后用户选择「仍然保存」的比例 < 30%（说明阻断确实拦到了东西）。
- 通过标准：误报率 ≤5%、且用户投诉（「误报」反馈）< 1/100 次。
- 前置条件：**重写快照机制必须先落地**，否则阻断等于逼用户在没有撤销能力的情况下做决定。

### 阶段 3（可选）：自动重写

- 仅在阶段 2 稳定运行 ≥1 个月、且快照可回滚后评估；本设计不承诺。

## 8. 诚实边界表

| 能保证 | 为什么 |
|---|---|
| 确定性指标的测量、留痕、可复现 | 纯字符串算法，O(n)，同一输入同一输出 |
| 同项目内的**相对**漂移检测（样本 ≥200 段后） | 自身基线 + 滚动分位，参照系与题材一致 |
| 「哪几项指标偏离、偏离多少」的可解释明细 | 每项都有值、区间、越界标记 |
| 判定结果与正文版本可追溯 | `text_md5` + `baseline_id` + `baseline_version` |

| 不能保证 | 为什么 |
|---|---|
| 「像不像参考作者」 | 实测 0.0562 / 0.0536 / 0.0567，区分度不足 [实测] |
| 「规则有没有被遵守」 | 整块规则删掉对正文无影响，p>0.86 [实测] |
| 单段（<1200 字）判定的可靠性 | 短句占比 / 对白字占比实测都出现过 0%，CV 0.58 / 0.63，需 ≈129 / 151 段 [实测/估算] |
| 误报率低于 1% 的承诺 | 要区分 1% 与 2% 需 ≈1500 段，现实达不到 [估算] |
| 跨题材/跨人称的普适性 | 参考带会把 5 段已接受正文里的 4 段判 fail（80%）[实测] |
| 「这段写得好不好」 | 无标注集、无与人类偏好的相关性标定 [未测] |

### 8.1 「模型服从度非 100%」对结论的影响

这是设计里最容易搞错的一点。当指标偏离、但规则本身没问题时，有两种完全不同的原因，**处置相反**：

| 原因 | 判别方法 | 处置 |
|---|---|---|
| **规则无效/不可测** | 把同一批规则用**强指令**重写（「必须：句长 ≤ 18 字」这种），再生成 10 段；如果指标仍不动 → 规则无效 | 删规则 / 改蒸馏，而不是改校验器 |
| **模型不服从** | 强指令下指标明显移动，但常规 system prompt 下不动 → 模型没听 | 改 prompt 位置（前置/末尾复述）、改措辞、加 few-shot，而不是改阈值 |

**推荐先做一次「规则可达性探针」**：
- 取 5 条最容易量化的规则（句长、对白占比、短段、段尾升华、情绪直陈）；
- 每条单独以强指令形式生成 10 段，与无该指令的 10 段对比；
- 单项指标中位移动 ≥10% 记为「规则可达」，否则记为「不可达」。
- 成本 [估算]：约 100 次生成，按上一轮单次 30–180 秒、0.01–0.03 元/次算，约 1–3 小时、1–3 元。
- **探针结论决定校验器的定位**：
  - 若多数规则「不可达」→ 校验器只能做**文本特征体检**，不能叫「文风一致性」；
  - 若多数「可达但常规 prompt 不触发」→ 先修 prompt，校验器才有意义。

**这条必须写进产品文案**：校验器判的是「文本特征的偏离」，不是「模型有没有遵守你的每一条规则」。

### 8.2 与既有约束的关系

- 不改 schema：本设计只新增两张表，不改 `projects` / `generations` / `agent_runs` / `style_distills` 的任何列。
- 不动生成流程：阶段 0–1 全部是「生成后异步读取」，不插入生成链路。
