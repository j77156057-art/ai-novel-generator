# 修炼体系：**提示词接线**、**结果闸门**与「让执行方自己改」的重试

> 适用范围：`POST /api/projects/{id}/power-system/generate`（生成修炼体系，**只建议不落库**）。
> 相关：`docs/power-system-parse-shapes.md`（解析器认得住哪些形态）、
> `docs/power-system-bands.md`（档位派生）。

## 一句话

**解析成功 ≠ 解析正确。** 闸门要拦的不是「有没有返回」，而是「返回的东西像不像一套体系」；
拦下来之后，把**具体错在哪**回灌给模型让它自己改 —— 而不是只说「格式不对」让它重猜。

---

## 0. 根因：那份写着全部要求的提示词，**从没发出去**

这是整件事的起点，也是这一轮最重要的发现。

`app/generation/power_system_gen.py` 里写好了一份 `_SYSTEM_PROMPT`：
三型对照表（「细分型/序列型/粗放型」各是什么）、硬要求（档位 3~6 个、每境要有说明、
细分型才给小境界）、输出格式（「只输出 JSON」）。

**但端点只发了一行**：

```python
system = "你在为一本中文小说设计**修炼体系**。"
prompt = build_system_prompt(...)   # ← "按上述要求给出这一套体系。"
```

`build_system_prompt` 里那句「按**上述**要求」指向的「上述要求」**根本不存在** ——
`_SYSTEM_PROMPT` 定义了，一次都没被引用过。

⇒ 模型收到的是：一句题面 + 一句悬空的「按上述要求」。
它**不知道**要输出 JSON、**不知道**三型怎么选、**不知道**档位怎么分层。
于是实测里它：回 Markdown 表格、回标题结构、把类型猜错、把细分摊平成 90 行。

**修法**：端点把 `_SYSTEM_PROMPT` 当 system 段发出去（`build_system_prompt` 仍作 user 段）。

**怎么防它再犯**：`tests/test_power_system_quality_gate.py` 里有一条守卫测试，
断言端点发给 provider 的 system 段**含**「输出 JSON」「体系类型」「档位」——
提示词再被漏掉，这条测试就红。

---

## 1. 为什么要有这道闸门

只看「解析没解析出来」是不够的：**解析成功但内容错的，会直接落库并显示在界面上**，
比解析失败危险得多（解析失败至少还有重试这道闸）。

真机记录（**App 自己的 MiniMax 通道**，走 `POST /api/projects/{id}/power-system/generate`，
不是假 provider、不是脚本）：

| 轮次 | 提示 | 模型回的形态 | 解析结果 |
|---|---|---|---|
| 1 | 细分型 | 表格（境界 + 说明）+ 标题正文 | HTTP 200、类型对、**29 个境界**，名字是「初期/中期/大圆满」**反复出现 10 次** ⇒ 层级被摊平成行，真正的大境界名整个丢了 |
| 2 | 序列型 | 表格 | HTTP 200、29 境，名字是「列：见隙」「列：识烬」—— 前缀「列」是**表头**，不是境界的一部分；类型还被模型自判成「细分型」 |
| 3 | 粗放型 | 标题 + 正文 | 两版都「没有解析出任何体系」 |
| 4 | 细分型 | 表格 + 标题正文（各带小境界） | **好结果**：9 境，每境带 `小境界=[初期, 中期, 大圆满]`，档位派生正常 |
| 5 | 粗放型 | 标题 + 正文（8,912 字） | 解析合格：4 个大阶段 |

⇒ **同一个提示词、同一天，形态与质量都随机**（第 1 轮和第 4 轮是同一个提示）。
解析器追不完所有形态 ⇒ 只能靠「闸门 + 一次带原因的重试」。

---

## 2. 闸门判据（`system_quality_issues`）

返回**人能读懂的原因列表**（空列表 = 合格），而不是一个布尔 ——
因为原因要能回灌给模型。

| 判据 | 为什么 |
|---|---|
| 解析不出任何体系 | 基础 |
| 境界少于 2 个 | 一个境界不构成体系 |
| 境界名是空的 | 抓错行 |
| 境界名超过 12 字 | 抓到了说明列 |
| 境界名里混进表头词（层次/表现/说明/名称/本质/备注/序号/阶段/档次/定位/位置） | 抓错列 |
| **同名境界重复出现** | 实测第 1 轮：29 境里「初期」出现 10 次 ⇒ 层级被摊平 |
| **境界名带表头前缀**（「列：」「序列：」） | 实测第 2 轮：前缀是列名，不是境界的一部分 |
| **境界超过 40 个** | 实测第 6 轮：90 个境界（感息/纳气/通脉…），名字全合法、不重名 ⇒ 靠「重名」拦不住。超过这个量级几乎必然是把小境界摊平成了行，而且这种体系落不进角色卡（40 是留了余量的：诡秘式 22 条序列在合法上限附近） |
| **体系类型与作者指定的不符** | 见第 6 节 |

`plausible_systems()` 是它的布尔外壳（保持既有调用点不变）。

### 名字里带冒号 ≠ 表头前缀

「开脉：初成」这种带冒号的名字**不算**不合格 ——
只有前缀落在表头词表里（列/序列/阶/境/层/段/级/品/期/重/序/序号/名称/说明/…）才拦。

## 3. 重试 = 门槛 + 回灌（`retry_instructions`）

```
## 输出格式（硬要求）
只输出一个 JSON 对象，不要 Markdown 标题、表格、列表或说明文字。
每个境界只占一条；同一个体系里**境界名不能重名**；境界名只写境界本身，
不带「列：」「序列：」这类表头前缀。
如果某个境界还有细分（小境界），把它们放进该境界的「小境界」字段，
不要摊成一行一个境界。

## 上一版的问题（必须改掉）
- 境界名「初期」重复出现 10 次 —— 同名境界说明层级被摊平成了行，每个境界应该只占一条
```

**为什么把错处写出来**：只说「格式不对」等于让模型重猜；
把「哪个名字重名、重了几次」给它，它才有机会一次改对。
这跟项目里其它地方用的是同一条规矩 —— **拒绝 + 回灌原因让执行方自改**。

## 4. 失败时把模型原文带出来

端点失败时回：

```json
{"ok": false,
 "detail": "AI 回了内容但认不出是一套体系：……（已按格式要求重试一次）",
 "原文": "……模型回的内容（前 2000 字）……"}
```

界面上用 `<details>` 摆在错误提示下面（「看模型回的内容」）。

**为什么**：只说「认不出」等于让人干瞪眼。看到原文才知道
**是模型写歪了**（要改提示词/要求），**还是解析器没认出来**（要改解析器）——
这两者的修法完全不同。

---

## 5. 结构与标签矛盾时，以结构为准

模型把一套**细分**体系标成「序列型」时，原来那段逻辑会按标签把小境界**整段抹掉** ——
而每境分「初期/中期/大圆满」正是这类体系最值钱的部分。

⇒ 规则：**解析出了「小境界」 ⇒ 按定义就是细分型**（覆盖模型给的其它类型）。

小境界只可能来自**标题下的项目符号列表**（表格列不产生小境界），
且 `_bullets_of` 要求名字带层级词（重/层/期/阶/品/级/段/第）——
所以「粗放型正文里的要点列表」不会被误当成细分。

---

## 6. 体系类型：由作者说了算（原来是模型自己猜）

类型一直写在提示词里让模型自己选 ⇒ 实测**两次都不对**：

- 要「序列型」，模型给了一套 29 境的序列，却自判成「细分型」；
- 要「粗放型」（凡人→修行者→圣人→神明），模型给了一套细分阶梯（开府/铸脉/…）
  并自判「细分型」—— **内容与要求根本不是一回事**，但没人能拦它。

⇒ 端点加一个**可选**字段 `system_type`（细分型 / 序列型 / 粗放型）：
- 给了 ⇒ 写进 user 段（「体系类型：**粗放型**（作者指定，必须是这个类型）」），
  解析后再核对 AI 给的类型；不符 ⇒ 记一条问题（带原因回灌）⇒ 触发重试；
- 不给（默认）⇒ 行为与从前一致，由 AI 自己定。

界面上是生成区的一个下拉：**「由 AI 自行决定」/ 细分型 / 序列型 / 粗放型**。

> ⚠️ 注意这条**只管类型对不对，不管内容像不像**：
> 模型完全可能给出「粗放型」标签、配一套细分阶梯。
> 内容质量仍然靠闸门（境界数、重名、表头残留）与作者自己看着采纳。

---

## 7. 还没解决的（别当已完成）

- **闸门只能挡住坏的，给不出好的**。模型这次写歪了，重试也可能再歪；
  这时界面会老实说「认不出」并给出原文，而不是塞一套错的进库。
- **解析器仍有形态盲区**。有一轮「两次都解析不出」的原文还没定位到具体形态
  （原文已随失败响应保留在接口里，等下一轮复现时补形态支持）。
- **类型对了内容仍可能不对**（见第 6 节的提醒）。
