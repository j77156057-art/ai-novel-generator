## 0. 需求拆解：主人要的三件事，逐条翻译成「可验收的产物」

主人的原话里其实有**三件不同的事**，混在一段话里。先拆开，每一件都给一个能判「做没做成」的验收口径 ——
否则做完只能靠感觉说「好像更好了」。

| # | 主人原话要点 | 交付物 | 验收口径 |
|---|---|---|---|
| A | 「自定义蒸馏，支持蒸馏章节数目，可以全部把全部章节蒸馏」 | 蒸馏范围可选：采样 / 指定 N 章 / 章节区间 / **全量** | 产物里能看出**实际用了哪几章**（章号列表 + 计数），且范围变了缓存必须失效 |
| B | 「标准化统计字符密度、用法、段落长度，生成一个标准化的值，要求模型在这个范围生成」 | **文风规格书 StyleSpec**：每项 = 闭集区间 + 中心值 + 单位 + 人话解释 | **提示词里给的区间 = 验收用的区间**（同一条不许两套口径）；生成段逐项判 in/out |
| C | 「作者习惯一个章节写多长，一句话写多长，标点习惯怎么用」 | 规格书补上**章节长度**（现在完全缺失）、句长、段长的闭集 | 「每章多少字」有分布、有区间、能进提示词 |
| D | 「真压缩：整本书真正总结，忽略废话，按时间主角时间线排，给每个角色生平，列出角色面对什么事会说什么话会做什么事，百万字压成十万字」 | **全书精华 BookDigest**：时间线 + 角色生平 + 情境→反应 | 压缩比 ≥ 10:1；主线事件覆盖率；角色覆盖率（三项都要可测） |

**A 是范围控制，B/C 是「写法」的可执行化，D 是「内容」的可压缩化。**
本设计把它们分成三条独立流水线（§2），因为**验收口径完全不同**：
B/C 用尺量（可机检），A 是范围与成本，D 用事实核对（要保真）。
混在一起就会出现「压缩摘要说这本书怎么写」这类胡话。

### 1.2 缺的（本设计要补的）

1. **蒸馏范围不可选**：档位只有「30% 采样」与「固定 30 章」；
   `POST /build-narrative?max_chapters=30` 是**死参数**（采样实际由档位决定，没人用它）；
   蒸馏链**不读** `reference_cutoffs`（检索链读，蒸馏链不读 ⇒ 前后两个世界）。
2. **规格不是闭集**：`describe()` 大部分给的是**均值**（对白占比、每段汉字数、标点用法全是均值），
   只有少数给区间；「每章多少字」**根本没有**。
3. **三道闸门各自为政**：段长闸门走 `_cjk_count`、形态闸门走 `band_check`、告警走 percentile ——
   **没有仲裁点**，可能互相打架（§3.5 给了具体的打架例子）。
4. **参考书侧没有全书压缩产物**：时间线、角色生平、情境→反应，一个都没有。
   `roleplay/bio.py` 的生平只到 **8 章**、只对**单个**角色、零 LLM。
   `style/layers.py` 的 `world` / `timeline` 两层是**空壳**（架构留了位置，没有生产者）。
5. **检索缺过滤参数**：`weighted_search` / `hybrid_search` 没有 chapter / 时间过滤
   （过滤只写在 `strategies.py` 里）；**embedding 入库时一次 HTTP 塞全书 chunk**
   （`ingestion/store.py:120`，超时 30s，异常被吞）⇒ 百万字书必然**静默丢向量**，检索退化成纯 BM25。
6. **文档过期**：`docs/style-distillation-tiers.md` 说「14 维 / 15% 采样」，
   实现是 **17 维 / 30%**；也没写全局库 `style_distills` 这一层。

## 2. 总体架构：三条流水线，一份规格书

```
                         ┌─────────────────────────────────────────┐
参考语料 ──────────────►  │ ① StyleSpec（零 LLM，纯统计）           │
（整本 / 章节区间）        │   章节长度 · 句长 · 段长 · 标点密度       │
                         │   标点用法 · 分段节奏 · 上限项            │
                         │   ⇒ 闭集区间 + 中心值 + 人话解释         │
                         └───────────────┬─────────────────────────┘
                                         │ 同一把尺
              ┌──────────────────────────┼──────────────────────────┐
              ▼                          ▼                          ▼
    提示词「风格目标」          spec_check 逐项验收            规格书落库（可复用）
    （模型照着这个范围写）      （生成段 in/out + 偏差）
              │
              │  ──► ② Narrative（LLM，范围可控）──► 「怎么写」：17 维手法规则
              │
              └─► ③ BookDigest（LLM + 检索）────► 「写什么」：时间线 / 角色生平 / 情境→反应
```

**为什么是三条而不是一条**：

- ① 是**尺**（可机检、零成本、可复算）；② 是**手法**（要证据、要能被模型照着用）；③ 是**事实**（要保真、能被核对）。
- 混在一起的典型症状：压缩产物里出现「作者喜欢用短句」这种**写法判断**，
  或者规格书里混进「主角性格内向」这种**内容判断** —— 两者都不可机检。

## 3. ① StyleSpec：把统计变成「模型能照着写、机器能验」的规格书

### 3.1 数据模型（草案）

```jsonc
{
  "spec_version": 1,
  "source": {"novel_ids": [12, 15], "chapters": [1, 2, "…", 833], "n_chapters": 833},
  "measurement": 4,                 // 与 stylometry.MEASUREMENT_VERSION 对齐（口径变了要失效）
  "items": [
    {
      "key": "章长",
      "unit": "汉字",
      "target": 3200,                // 中心值（p50）
      "lo": 2400, "hi": 4100,       // 闭集区间（p10~p90）
      "kind": "range",               // range | upper | ratio
      "say": "一章写 2400~4100 汉字（平均约 3200）"
    },
    {
      "key": "句长均值", "unit": "字", "target": 28.4, "lo": 21.0, "hi": 38.0,
      "kind": "range", "say": "一句 21~38 字"
    },
    {
      "key": "纯台词段占比", "unit": "%", "target": 22, "lo": null, "hi": 45,
      "kind": "upper", "say": "纯台词段不超过 45%"
    }
  ],
  "source_features": ["句长均值", "段均汉字数", "…"]   // 每项来自哪个特征（可追溯）
}
```

**要点**

- **每项都能追到档案里的哪个特征**（`source_features`）—— 否则规格书就成了「凭空写的数字」。
- `kind` 区分**区间型**（落在带内即合格）与**上限型**（比喻密度、情绪直陈、段尾拔高这类「越少越好」的）。
  混成一种会出两种错：把上限项当成区间 → 模型为了「达标」去凑比喻；把区间项当成上限 → 模型只写短句。
- **闭集来自 p10~p90**：档案自己的分布带（「参考书自己就落在这一带」）。
  中心值取 p50（不是均值 —— 均值会被离群章拉偏）。

### 3.2 数据来源与新增项

| 规格项 | 来源 | 现状 |
|---|---|---|
| 章长（每章多少汉字） | **新增**：`novel_chunks` 按 `chapter_no` 聚合 `cjk_len` → 分布 | ❌ 完全没有 |
| 句长 / 句长 p90 / CV | 档案 `句长均值` / `句长p90` / `句长CV` | ✔ 已有（但 describe 给均值） |
| 段长（每段多少汉字） | 档案 `段均汉字数` | ✔ 已有（只有均值） |
| 每段句数 | 档案 `段均句数` | ✔ |
| 标点密度（逗号/句号/问号/感叹号/省略号） | 档案对应 5 项 | ✔ |
| 标点用法（顿号/分号/冒号/破折号/逗号句内位置/引号内句号占比） | 档案新增 6 项 | ✔（本轮刚加） |
| 分段（段首对白率/对白段连长度/叙述段连长度/空白占比/段间空行密度） | 档案新增 5 项 | ✔（本轮刚加） |
| 上限项（比喻/情绪直陈/段尾拔高/纯台词段占比） | 档案 p90 | ✔ |
| 对白占比 | 档案 `对白字占比` | ✔ |

**章长统计是新东西，也是主人明确点名的（「作者习惯一个章节写多长」）** ——
它必须进规格书，因为它决定「生成一段（章）」该写多少字；
现在生成端只有项目配置里的 `generation_length`（用户拍脑袋定的 3000），**与参考书无关**。

### 3.3 渲染进提示词

现状 `describe()` 输出（实测，8~10 行）：

```
【文体基线】以下数字来自参考语料的统计（每单元约 3000 字），不是形容词，请照着写而不是照着想象。
【句长】一句 15 字 · 参差度 CV 0.57
【每段句数】1.2 句 · 段落长短要参差（CV 0.5）
…
```

问题：**一半是均值**（模型照着「1.2 句」写会写成每段 1 句），而且**没有章长**。

规格书版（草案）：

```
【文风规格】以下区间来自参考语料的实测分布，落在区间内即合格，不必照抄均值。
· 章长：一章 2400~4100 汉字（中心 3200）。本章请写 2400 汉字以上。
· 句长：一句 21~38 字，任何一句都不要超过 38 字。
· 每段：24~52 汉字（中心 33），每段 1.4~3.2 句；段落长短要参差。
· 对白：占正文 31%~45%（中心 38%）；62% 的段落含对白；纯台词段不超过 45%。
· 标点（每千汉字）：逗号 58~76 · 句号 92~101 · ？ 1.8~3.2 · ！ 0.8 · … 0.2
· 标点用法：顿号 ≤0.9/千汉字 · 分号 ≤0.5 · 冒号 1.1~2.7 · 破折号 ≤1.3；
  逗号平均落在句子的 45%~49% 处；对白句号收在引号内 99%~100%。
· 分段：段首即对白 52%~64%；连续对白 2.2~3.3 段；连续叙述 1.7~2.2 段。
· 上限（超出即偏 AI 腔）：比喻 ≤2.9/千汉字 · 情绪直陈 ≤0 · 段尾拔高 ≤1.4% 的段落。
```

**「落在区间内即合格，不必照抄均值」这句必须留着** ——
它是 `describe()` 里最有价值的一句（把「照抄数字」换成「落在带内」），别在改写时弄丢。

**尺寸控制**：规格书比现在的 describe() 长约 40%（多区间与章长）。
system 块实测约 600~900 汉字 ⇒ 约 900~1300 汉字，仍在可接受范围，
但**必须实测**（`describe()` 的字节一致性有闸门，规格书也要有同样的闸门，否则击穿提示词缓存）。

### 3.4 逐项机检：`spec_check()`

```python
def spec_check(text: str, spec: dict, *, unit_chars: int | None = None) -> dict:
    """一段文本相对规格书逐项的落位。

    返回 {key: {value, target, lo, hi, in_band, deviation, unit}}。
    """
```

- 与 `stylometry.band_check` 的关系：**band_check 是「拿档案带当尺」，spec_check 是「拿规格书当尺」**，
  而规格书**由档案导出** ⇒ 同一把尺的两个视图（一个给模型，一个给机器）。
  ⇒ **不允许** spec_check 自己再算一遍密度（会漂）。
- 长度归一化因子要**除掉**（与 band_check 同一处理：档案是按 unit 粒度拟合的）。
- `deviation` 用**相对带中点的偏移**（`-1 = 正好在下界，+1 = 正好在上界`），
  这样「偏多少」可以跨指标比较，也能直接回灌给模型。

### 3.5 与现有三道闸门统一（**当前最该修的打架**）

现状三道闸门互不相识：

| 闸门 | 量什么 | 失败后 |
|---|---|---|
| 段长闸门 `engine._enforce_length` | 整段**总汉字数**（下限 = 目标 80%） | 回灌扩写 ≤2 次 |
| 形态闸门 `engine._rewrite_gate` / `candidate` | 参考书分布带（band_check） | 形态校正 / 文风改写 |
| 风格告警 `engine._style_warning` | percentile / 绝对 z | 只告警 |

**具体的打架**（不是理论上的）：

1. 档案说「每段约 60 汉字」，同一份 system 硬约束说「本段正文 ≥ 2400 汉字」——
   同一提示里两个「段」语义不同（自然段 vs 生成段），模型取哪个都可能。
2. 档案 `unit_chars = project.generation_length`（`engine._style_info`）——
   **改项目段长会让档案重算**，`describe()` 文本随之变化 ⇒ 击穿提示词缓存、
   且新旧档案不可比（这正是今天「档案跟着配置漂」的老问题）。
3. 密度类分母已统一为汉字（2026-11-01），段长闸门也用 `_cjk_count` ⇒ 这条现在是一致的 ✔。

**本设计的仲裁点**（叫 `StyleArbiter`，落 `engine._style_gate`）：

```
生成段出来
   ├─ 段长闸门（总汉字数 vs 目标 × 80%）—— 保留，硬约束
   ├─ spec_check（逐项 in/out）
   │     ├─ 全在带内 → 放行
   │     ├─ 只有区间型出带 → 交给现有 rewrite 流程（回灌偏差）
   │     └─ 上限型出带 → 告警（不阻断，与现状一致）
   └─ 产出 summary.pipeline：每项 in/out + 偏差（可见）
```

**一条纪律**（仓库里已有，必须继承）：**提示词里说的区间 = 验收用的区间**。
规格书是唯一来源，提示词渲染与 `spec_check` 都从它出 ⇒ 不可能两套口径。

### 3.6 失效与版本

- `spec_version` + `measurement` 都在规格书里 ⇒ 换口径（`MEASUREMENT_VERSION`）自动失效。
- 规格书**可以独立于档案缓存**（它更小、更好复用），但**必须能重新导出**（档案变了要能重导）。

## 4. ② 蒸馏范围可控（自定义章数 / 区间 / 全量）

### 4.1 采样轴扩展

`NarrativeTier` 现在只有 `sampling_mode: percentage | fixed_chapters`。
扩成四种：

| mode | 含义 | 参数 | 默认 |
|---|---|---|---|
| `percentage` | 按语料量百分比 | `sample_ratio` | 0.30（完整档现状） |
| `fixed_chapters` | 固定章数 | `fixed_chapters` | 30（平衡/快速档现状） |
| `range` | **章节区间**（含 from/to） | `chapter_from`, `chapter_to` | — |
| `all` | **全部章节** | — | — |

请求体新增（`DistillStartRequest`，继承 `StrictRequest` ⇒ 拼错字段 422 而不是静默按默认跑）：

```jsonc
{
  "tier": "full",
  "force": false,
  "scope": {
    "mode": "all",              // percentage | fixed | range | all
    "chapters": 50,             // mode=fixed
    "from": 1, "to": 200,       // mode=range
    "respect_cutoff": true      // 是否尊重 reference_cutoffs（默认 true）
  }
}
```

### 4.2 指纹必须跟着变

复用键 = `source_ids_hash + tier + tier_signature + content_hash`
（`narrative.py:4608` `_persist_style_distill`）。
⇒ **`scope` 必须进 `tier_signature`**，否则「全量蒸出来的档案」会被「采样蒸出来的档案」顶掉 ——
那是最坏的一种静默错误：用户以为拿到了全量的，实际上是 30%。

### 4.3 全量的两个风险（必须给对策，不能装作没有）

1. **早期文风漂移**：代码里明确避开（`_sample_chapters` 取后 2/3；`_mature_chapters` 取后一半）。
   全量 = 把**生涩的早期章节**也蒸进来 ⇒ 风格档案会偏向早期。
   **对策**：全量档**分两套**（早期段 / 成熟期段各一份档案），提示词默认注入成熟期那份；
   或者全量但**按章加权**（成熟期规则权重更高）。
2. **成本与时长**：833 章语料完整档实测 **42 分钟**（30% 采样）⇒ 全量约 **2 小时**量级。
   后台任务扛得住，但**必须给成本预估**（章节数 × 块数 × 每块调用数），并在 UI 上显示。

### 4.4 cutoff 一致性

现在检索链读 `reference_cutoffs`（防剧透，fail-closed），**蒸馏链不读**。
⇒ 同一本书，「检索得到的片段」和「蒸馏出的规则」可能来自**不同可见性边界**。
本设计：**蒸馏默认也尊重 cutoff**（`respect_cutoff` 默认 true），要绕过得显式关掉并留痕。

## 5. ③ BookDigest：全书压缩（百万字 → 十万字精华）

### 5.1 产物结构（三块，正好补上 `style/layers.py` 的两个空壳层）

```jsonc
{
  "digest_version": 1,
  "source": {"novel_id": 12, "n_chapters": 833, "n_chars": 1_100_000},
  "timeline": [                    // ① 时间线：按故事内时间 + 主角视角排
    {"seq": 1, "chapter_no": 12, "in_story_time": "开篇前三年",
     "event": "沈砚在矿脉塌方里第一次杀人", "actors": ["沈砚", "老陶"], "weight": 0.9}
  ],
  "characters": [                 // ② 角色生平：身份、关系、关键经历、当前状态
    {"name": "沈砚", "role": "主角",
     "arc": "从矿工到执旗", "key_events": [12, 88, 341],
     "relations": [{"name": "老陶", "kind": "师徒", "changed_at": 88}],
     "voice": {"avg_len": 6.2, "habits": ["不用形容词", "答话短"]}}
  ],
  "reactions": [                  // ③ 情境 → 反应：角色面对什么事会说什么/做什么
    {"character": "沈砚", "trigger": "被当众羞辱",
     "says": "短句、不辩解、用动作回应", "does": "转身离开，不看对方",
     "evidence": [{"chapter_no": 207, "quote": "…"}]}
  ],
  "stats": {"chars_in": 1_100_000, "chars_out": 96_000, "ratio": 11.5}
}
```

**关键约束**：

- **每条都必须挂证据**（章号 + 原文片段）—— 与仓库既有的「规则必须附证据」纪律一致
  （`narrative.py:22`：强制附证据是唯一有效的防幻觉手段）。
  没证据的条目**直接丢弃**，不是标注「存疑」。
- **「忽略废话」要有判据**：靠**抽取**（只挑「像一件事」的句子，见 `roleplay/bio.py:24` 的判据）
  + **归并**（LLM 把同章多事件合并成一条），而不是让模型「总结全书」。
- **时间线排序**用「故事内时间」而不是章号 —— 章号是叙述顺序，时间线是因果顺序。
  仓库里 `kg_events.in_story_date` 是自由文本，排序只能靠 `sequence`/`chapter`
  ⇒ 本产物需要自己的 `seq`（由 LLM 给的因果顺序 + 章号双键）。

### 5.2 抽取方式两档 + 自动选择

| 方式 | 何时用 | 怎么走 | 成本 |
|---|---|---|---|
| **检索抽取**（默认） | 书 > 阈值 | ① 按章分块 → ② 启发式预筛「像一件事」的句子（`bio.py` 判据）→ ③ 检索补齐（BM25+向量，按「主角/角色/关键事件」多路查询）→ ④ LLM 归并去重 | 与章节数线性，百万字 ≈ 数百次调用 |
| **整本投喂** | 书 ≤ 阈值（建议 30 万字）且渠道支持长上下文 | 一次把全书丢给模型，要求输出上面那个 JSON | 一次调用，但 token 贵（30 万字 ≈ 40 万 token 起） |

自动选择规则写在 `BookDigestSpec` 里，且**在 UI 上显示选了哪一档、为什么**。

**注意**：主人提到「目前大部分云端模型都有一百万的上下文」——
本仓库的渠道配置里 **deepseek-v4.1-flash / MiniMax-M3** 等是否真的支持百万级，
**必须先查该渠道的实际上限**（`backend/app/llm/provider.py` 与 `providers.yaml`），
不能假设；假设错了就是「请求发出去了、回来被截断、我们以为压缩成功了」。

### 5.3 验收（三项，都要能自动判）

1. **压缩比**：`chars_out / chars_in` ≥ 目标（主人给的是 10:1）。
2. **主线覆盖**：候选关键事件（用检索在原文里找出的高频事件集合）里，
   被 digest 覆盖的比例 ≥ 阈值（建议 0.8）。**否则说明压缩把主线压丢了。**
3. **角色覆盖**：原文里出现频次前 N 的角色，在 digest 里出现的比例 ≥ 阈值。

这三项**可机检** ⇒ 进 `backend/verify_book_digest.py`（照 `verify_stylometry.py` 的形状：
可证伪 + FAIL 闸门 + 阳性对照）。

### 5.4 落库与消费

- **落库**：新表 `book_digests`（照 `character_templates` 的模式：独立产物 + 按源书 + 版本）。
  **不要塞进 `rules`**（那是「怎么写」，这是「写什么」）。
- **消费**（这是它存在的意义）：
  1. **替代整本进上下文**：续写/原创时，注入 digest 里的「相关角色生平 + 相关时间线片段」，
     而不是几万字的原文摘要。
  2. **喂给检索**：把 timeline / reactions 做成可检索条目（进 BM25 索引）。
  3. **给「角色对话」用**：`reactions` 直接就是「他面对这种事会怎么说」的答案 ——
     这正是主人要的第 ③ 块，也是 `roleplay` 现在的空缺。

## 7. 失败分类与处置

| 失败 | 症状 | 处置 |
|---|---|---|
| 渠道上下文不够 | 模型返回被截断的 JSON | **先校验返回能否解析**；截断 ⇒ 报「渠道上限不足」并建议换 `retrieval` 档，**不**当成成功 |
| 证据缺失 | digest 条目没有原文出处 | 该条目**丢弃**并计数；比例超阈值 ⇒ 整次判失败 |
| 章长统计样本不足 | 参考书 < 5 章 | 规格书里**不给章长项**（而不是给 0 或猜） |
| 范围与缓存串档 | 全量档案被采样档案顶掉 | 指纹含 scope（§4.2）；**并加一条测试**：改 scope 必须换缓存键 |
| embedding 静默缺失 | 百万字书检索退化成纯 BM25 | 入库分批 + 重试 + **缺失率超阈值就报错**（现在只吞异常） |
| 规格与提示词不同源 | 提示词说 A 区间、验收判 B 区间 | `describe`/规格渲染与 `spec_check` **都从同一份 spec 出**；加字节一致性测试 |

## 8. 测试与验收标准

**单元/不变量**

1. 规格书每项都能追到档案特征（`source_features` 非空且真实存在）。
2. 区间项在带内即合格；上限项只判上界（把上限项当区间判 ⇒ 必须有测试拦住）。
3. `spec_check` 与 `band_check` 在同一段文本上给**同一组**结论（同一把尺的两个视图）。
4. 提示词里出现的每个区间数字，都能在规格书里找到同一个来源（防止手抄漂移）。
5. 章长统计：给定构造语料，章长分布 = 预期（不含标题行、不含空章）。
6. 范围改动 ⇒ 指纹/缓存键必变。

**离线验证（不烧额度）**

7. 用现成语料做「规格 → 生成 → spec_check」的闭环：改造后**带内项数**应上升。
8. 压缩：用一本真书跑 digest，比对压缩比 / 主线覆盖 / 角色覆盖。

**真跑**

9. 一本书的规格书投进生成，产出的逐项 in/out 落在报告里（可见）。

## 9. 风险登记册

| 风险 | 影响 | 缓解 |
|---|---|---|
| 规格书把模型**逼成套路**（每段都贴着区间写） | 产出假整齐 | 区间给的是**带**，不是点；只对「区间型」回灌，不要求命中中心 |
| 全量蒸馏引入早期文风 | 风格档案偏移 | 分「早期/成熟期」两套档案（§4.3） |
| digest 摘要吃掉关键伏笔 | 续写接不上 | 主线覆盖验收 + 证据强制 + 角色覆盖验收 |
| 长上下文渠道假设不成立 | 请求白花、结果被截断 | 先查渠道上限；返回必须可解析；解析失败 ⇒ 明确报错 |
| 规格书与档案口径漂 | 验收判据失效 | 规格书带 `measurement` 版本；`MEASUREMENT_VERSION` 变 ⇒ 自动失效 |
| 现有三道闸门打架 | 同一段文字两个结论 | §3.5 的仲裁点（本设计里**必须先做这一条**） |
| 成本失控（全量 + 压缩同时跑） | 用户意外烧钱 | 提交前给成本预估；UI 明示；`force` 语义保持 |

## 10. 待拍板（**已拍板，2026-11-01**）

| # | 事项 | 结论 |
|---|---|---|
| 1 | 规格书的严格程度 | **区间 + 中心值**；**只有区间型出带才回灌**；上限型照旧**只告警**不阻断 |
| 2 | 压缩产物的形态 | **结构化 JSON 为主**，叙述性长文由 JSON **渲染**出来（不是反过来） |
| 3 | 压缩的抽取档 | **按书大小自动选**，UI 上**明示选了哪档、为什么**（前提：先查渠道真实上下文上限） |
| 4 | 全量蒸馏的默认 | 默认**仍是成熟期采样**；「全量」是**显式选项**（并显示成本预估） |

**第 1 条的直接推论**（实现时按这个来）：

- 区间型出带 ⇒ 回灌（给改写流程，附**偏差量**）。
- 上限型出带 ⇒ **只告警**，不阻断、不回灌。
- 「中心值」的作用是**方向**（模型该往哪靠），不是**必须命中的点** ——
  逼模型命中中心会把它逼成套路化写法（风险登记册第 1 条）。
- **零方差的项不参与判定**：某项在这本书上恒定（p10 == p90），
  说明它**不构成本书的写法特征**（例如一本从不用顿号的书，顿号密度恒为 0），
  ⇒ 降级为「只陈述不判定」（`kind=info`），否则生成里偶尔用一个顿号就被回灌 —— 那是误伤。

### 12.1 真跑结果（真书，零 LLM）

- 书：现代网文第一本，41.4 万字，切出 **288 章**（章长中位 1695 汉字）；
- 规格项：34 项 = range 19 + upper 4 + info 11；
- **提示词/验收对账：一致** —— 提示词里写的每个区间，就是 `spec_check` 用的那个区间
  （抽样：句长均值 22.35~29.41 / 逗号密度 61.49~79.01，提示词与验收逐字相同）；
- 提示词块 **1589 字节**（体积可控，不击穿 system 块预算）；
- `render_spec` 两次调用**逐字节相同**（提示词缓存的前提）。

### 12.2 实施中发现的三处偏差（与 §3 的草案不同，已按实测改）

**① 判定要带容差，否则回灌句自相矛盾。**
草案说「区间型出带 ⇒ 回灌」，但没定边界怎么比。实测：句号密度带宽 31.2~41.1，
一个真值 30.96 的实测按精确比较判「偏低」，回灌句却写成
「实测 31/千汉字（目标 31~41/千汉字）」—— **实测明明落在展示出来的区间里**。
⇒ 判定加**容差 = 半个展示刻度**（`10^-digits / 2`）：
**按展示精度看不出差别 ⇒ 不算偏离**。

**② 回灌要带门槛，否则模型会去修不存在的问题。**
区间是 p10~p90，实测值是连续量 ⇒ 贴边出带是常态
（实测冒号密度真值 6.04、下界 6.1，差 1%，却是货真价实的出带）。
若全部回灌，模型会收到一堆「差 1%」的要求 ⇒ 只能乱改。
⇒ **判定仍如实**（出带就在 `out_of_band` 里，报告看得到），
但**回灌**只给「超出带宽 5% 以上」的项（`REWRITE_MIN_BAND_EXCEED`）。

**③ 三道闸门不能合成一道：改写闸门是「成本闸门」，不是「风格判定」。**
草案 §3.5 画的是「spec_check 出带 ⇒ 交给现有 rewrite 流程」。但 rewrite **只修得动断句**
（`REWRITE_GATE_FEATURES` 只有句长均值与句号密度两项），
而规格书 34 项在跨书对照里能出 13 项 ⇒ 「有出带就改写」会让**每段都白花一次模型调用**。
⇒ 落成两个分工明确的出口：
- `_style_gate`（仲裁点）：逐项 in/out，**报告用**，落 `summary.pipeline.style_gate`；
- `_rewrite_gate`（成本闸门）：只看改写修得动的那两项，且要「严重偏离」，**才动手**。

两者的尺是同一把（`band_check` 的 p10/p90 = 规格书的 lo/hi），但**判的问题不同**。

### 12.3 顺手修掉的三处提示词歧义

- **「段」有两个含义**：档案说「每段约 24 汉字」（自然段），同一份 system 说「本段正文 ≥ 2400 汉字」
  （生成段）⇒ 规格书里改用**「每个自然段」**，把歧义掐掉。
- **章长是参考书的分节长度**，不是模型这一次的产出目标 ⇒ 措辞改成「参考书一章」，
  且单列一组，不与「长度」组混在一起。
- **回灌专名重名**：渲染时「每段 20~27 汉字」靠单位能分辨，
  回灌句「「每段」偏高」脱离上下文就不行 ⇒ 回灌用**专名**（每段字数 / 每段句数）。

### 12.4 P0 之后的状态

- 三道闸门**没有合成一道**（理由见 12.2 ③），但**段级文风判定有了唯一出口** `_style_gate`，
  且它的逐项结论**落库**（`summary.pipeline.style_gate`）⇒ 事后可查，不必重跑、不必翻日志。
- P1（蒸馏范围轴）与 P2（BookDigest）**尚未实施**。
- 「全量蒸馏」的早期文风漂移风险（§4.3）**未处理** —— 它属于 P1 的事。

## 附：1M 上下文的用武之地在「摘要」，不在「规则」（2026-11-01 实测结论）

> 本节是 P1/P2 的**设计输入**，来自同日做上下文预算时的实测
> （详见 `docs/context-budget-design.md`）。

### 一句话

主人问「模型一百万上下文，问做得畏手畏脚的」。
实测确认：**这个渠道确实是 1M token**（服务端原文
`maximum context length is 1048576 tokens`，中文约 200 万字）。
但**放大蒸馏块并没有带来产出收益** ⇒ 1M 的价值在别处。

### 实测：蒸馏块放大 ⇒ 候选池变小 ⇒ 多样性归零

| 块大小 | 块数 | 每维候选 min | 注入字数 | 墙钟 |
|---|---|---|---|---|
| 2 万 | 28 | 86 | 2297 | 1170s |
| **5 万（定案）** | 11 | **32** | 1754 | **391s** |
| 20 万 | 3 | **8** | 1643 | 120s |

两个反直觉的点（都推翻了我原先的判断）：

1. **每块产出恒定约 40 条**（四种块大小都一样）⇒ 条数由**提示词里写死的
   「每题 1 条，总数 4-8 条」**决定，不是由 `max_tokens` 决定
   ⇒ 「输出预算不够」这个根因**是错的**。
2. **总规则数是候选池，不是产出** ⇒ 下游 `RULES_PER_DIM = 5` 每维只取 5 条
   ⇒ 两档进提示词的条数**一样** ⇒ 该比的是候选池与注入结果。

⇒ 真正的代价是**候选池**：20 万字档每维只剩 8 条候选，却要选 5 条
⇒ 选出来的那 5 条里必然大量重复（本来就出自同一大块）⇒ **多样性归零**。

### ⇒ 对 P1/P2 的直接含义

| 产物 | 对上下文的需求 | 1M 有没有用 |
|---|---|---|
| **规则**（蒸馏：怎么写） | 要**精** —— 每条都要指向原文的具体位置 | ❌ 用不上（2~5 万字/块就够） |
| **摘要**（BookDigest：角色生平 / 时间线 / 精华） | 要**全** —— 覆盖整本 | ✅ **这才是 1M 的用武之地** |

⇒ **P2 的 BookDigest 应当「整本一次投喂」**，而不是沿用「切块抽」的思路：

- 切块抽（现在）：每块独立提规则 ⇒ 块内可精、块间会重复 ⇒ 需要跨块去重；
- 整本投喂：一次给全 ⇒ 模型自己看全局 ⇒ 天然不会重复，且能答
  「主角在第 3 章和第 500 章的关系变化」这种**跨章问题**（切块做不到）。

⇒ 但这带来一个新的验收要求：**摘要必须带原文证据**（哪个角色的哪一段），
否则模型会编。⇒ 证据强制是 BookDigest 的硬需求，不是可选项。

### ⇒ 三条可直接带进 P1/P2 的纪律

1. **要「全」的产物（摘要）用大块；要「精」的产物（规则）用小块** ——
   两者对上下文的需求相反，不能共用一套切块参数。
2. **块大小是「渠道能力 × 下游消费方式」的联合决定** ——
   单看渠道能读多少会得出错误结论（实测就错了一轮）。
3. **验收要比「下游实际用到的」，不是「中间产出的总量」** ——
   总量是候选池，下游只吃一小部分。
