# 评审简报：AI 长篇小说生成器的「记忆与注入体系」设计

> 用途：请外部评审者基于以下**自包含材料**（现状 + 证据 + 已提方案 + 约束）挑错与补充。
> 目标不是泛泛而谈，而是回答第 6 节的 8 个具体问题。

---

## 1. 项目与目标

**产品**：AI 小说生成器（wayfinder 方法论）。用户向导式建项目 → 选参考语料 → 选类型/风格平台 → 填大概内容 → 构思剧情圣经 → **点一次生成一段（约 3000 字）** → 逐段续写成长篇。

**核心目标**：连续自动生成 **几十段、数万字**，要求：
1. **不崩** —— 前后一致（人物/物品/境界/时间不矛盾）
2. **不漂移** —— 不跑题、不丢主线、支线有收束
3. **不遗忘** —— 写到第 30 段仍记得主角有什么武器、什么功法、什么境界、埋过什么伏笔
4. **像人写** —— 有参考作者的文风，而不是 AI 腔

**当前痛点**：目标 3、4 基本未达成。

## 2. 系统现状（技术事实）

### 2.1 技术栈
- 后端 Python 3.13 + FastAPI + SQLAlchemy + SQLite（可切 PG）
- 前端 Vue 3 + Vite
- LLM：MiniMax `MiniMax-M3.1-Flash-Preview`（OpenAI 兼容，国内站），按需可切智谱/硅基流动/OpenRouter
- 检索：BM25 + embedding 混合（RRF 融合），embedding 可本地兜底

### 2.2 关键文件
| 文件 | 职责 |
|---|---|
| `backend/app/kg/extractor.py`（594 行） | 知识图谱抽取（**规则式**） |
| `backend/app/kg/build.py` | 图谱落库，按 source 隔离（参考语料图 / 生成后图） |
| `backend/app/kg/queries.py` | `get_reminders`：角色约束 + 未填坑 |
| `backend/app/generation/engine.py`（361 行） | `build_context` 组装上下文 + 续写 + 段级总结 |
| `backend/app/generation/prompts.py`（161 行） | `build_system_prompt` / `build_user_prompt` |
| `backend/app/models.py` | `Project` / `KgNode` / `KgEdge` / `Generation` |

### 2.3 数据模型要点
- `KgNode.type` 注释预留：`character | plothole | relationship | chapter | worlditem | event`
- `KgNode.props` 是 JSON 列（可扩展任意属性）
- `Project` 有：`genre` / `style` / `premise` / `plot_bible`(JSON) / `summary`(JSON 段级摘要链) / `outline` / `reference_novel_ids` / `generation_length`

### 2.4 当前生成链路（端到端）
```
用户点生成
  → build_context(db, project)
      ├ reminders   = get_reminders()          # 角色名 + 未填坑问题（来自规则图谱）
      ├ prior       = project.summary          # 段级摘要链（每段 60 字内）
      ├ rag_context = hybrid_search(k=4)       # 参考语料检索 4 个原文片段
      └ constraints = {characters:[名字], plotholes:[问题]}
  → system = build_system_prompt(标题, reminders, {类型,风格平台}, plot_bible)
      └ 含【角色人设约束】【未填伏笔】【风格】【文风要求：忌 AI 腔】(7 条硬编码)
  → user   = build_user_prompt(前情, RAG, 大纲, 字数, plot_bible, premise)
  → LLM 流式生成 → 落库 Generation → LLM 总结成段级 summary 追加到链
```

## 3. 已实现的能力（请勿重复建议这些）

- 段级**摘要链**（每段总结后注入下一段前情）—— 已有，可工作
- **剧情圣经**（`plot_bible`：梗概/角色/关系/走向/冲突/伏笔）—— 构思阶段产出，已注入 user prompt
- **文风纪律 7 条**（禁金句台词、禁段尾升华、禁情绪直陈、禁对话讲设定、具体优于形容、允许留白、长短句交错）—— 硬编码在 system prompt
- **参考语料隔离**：每张图谱按 source 分隔，多本语料各自成图不混淆
- **图谱按来源幂等重建**
- **防 AI 腔的"坑"抽取句法闸门**（拦掉旁白预告式、叙述者给答案式、金句式陈述混入坑）

## 4. 现状缺陷（附代码证据）

### 4.1 知识图谱是**纯规则抽取**，质量差
`extractor.py` 的 `RuleBasedExtractor` 用正则 + 姓氏/名用字白名单 + 句法闸门。
该文件 docstring 自述：

> "正式质量（人物/坑/关系的高精度抽取）交给 LLM 抽取实现同一接口**后置**。"

即 **LLM 抽取从未实现**。实证后果（真实生成 5 段后的图谱）：
- 把「山门」「左手」等普通名词误判为角色
- 「宁折枝」被截断成「宁折」独立成角；「晏无咎」分裂为「晏无」+「晏无咎」
- 4 条"未填坑"全是台词碎片（"谁杀的？""你师父怎么死的？"），不是真正的悬念
- **关系边 0 条**

### 4.2 图谱类型只有 3 类，实体维度严重缺失
实际只产出 `character` / `plothole` / `relationship`。
**完全没有**：武器、功法、境界、法宝、丹药、势力/组织、地点、时间线、世界规则、剧情转折、事件。
（数据模型的 `type` 注释虽预留了 `worlditem` / `event`，但代码从未实现。）

### 4.3 "语料基底"远未达到蒸馏
现状注入的"风格"只有两项：
- `_style_info()` → 用户下拉选择的两个标签 `{类型: 都市, 风格平台: 番茄}`
- `rag_context` → 检索 4 个 chunk **原文片段**

也就是说：**风格来自用户选的标签，不是从语料学出来的**。
用户期望的"对全文文风、写法、角色用语、作者习惯、剧情编排、冲突设计、口语习惯做多维蒸馏，形成结构化档案注入 system prompt（类比 vibe coding 里把操作/流程/习惯蒸馏成 skill）"——**目前为 0**。

### 4.4 完全没有"校验层"
生成后不校验一致性、不检测重复、不检测 AI 腔复发。只生成，不纠错。

## 5. 已提出的方案（四层体系）

### L0 事实层（世界此刻是什么样）
角色(身份/性格/动机/当前状态：伤势·中毒·修为) · 物品(武器/功法/法宝/丹药 + 持有者 + 等级 + **归属变化**) · **境界/实力体系**(等级序列 + 各角色位置 + 突破代价) · **时间线**(故事内第几日/季节/昼夜) · **信息不对称表**(谁知道什么) · **承诺/债务/人情** · 势力/组织 · 地点 · **世界规则** · **死亡名单** · 人物关系

### L1 叙事层（写到哪、该往哪走）
主线进度 · 支线进度 · 伏笔(绑定到具体实体) · **伏笔回收窗口**(埋了多久/该何时收) · **悬念阶梯**(本章/中段/长线三级钩子) · **冲突升级阶段** · **爽点节拍**(距上次爽点几段) · 情绪基调曲线 · 剧情转折

### L2 风格层（像谁写的）
叙事视角/人称 · 句式节奏 · 用词偏好 · 比喻密度 · 对话风格 · 剧情编排模式 · 冲突设计模式 · **角色声音词典**(每个角色口头禅/自称/敬语/句长) · **反向禁忌清单**(作者从不用的词句) · 感官描写侧重 · **内心戏 vs 动作配比** · **断章位置惯例**(章末钩子形态)

### L3 校验层（当前空白）
**一致性校验器**(用了不存在的武器 / 境界跳级 / 时间倒流 / 死人说话) · **重复检测**(句式·比喻·桥段复用) · **AI 腔模式库**(现有 7 条硬编码 → 可配置) · **冲突裁决**(抽取与既有事实矛盾时标记人工裁决)

### 架构原则（关键判断）
**不是注入越多越好**。分层记忆 + 按需检索 + Token 预算：
- 与当前段**强相关**（本场景角色/地点/手持物/即时伏笔）→ 全量注入
- **中距离**（主线进度、未收伏笔）→ 压成摘要注入
- **远距离**（完结支线、次要角色）→ 仅被检索到时注入
- **风格档案** → 常驻但精简

建议落地顺序：线 1 = L0 + L3（防崩，地基）；线 2 = L2（语料蒸馏，可离线并行）。

## 6. 请评审的 8 个具体问题

请逐条回答，并**明确指出我方案中的错误、过度设计或遗漏**。

**Q1（优先级）** 我判断"L0 事实层 + L3 校验层"应最先做，理由是"事实错了，文风再像也是主角握着不存在的剑"。这个排序对吗？有没有哪一层其实更早导致崩坏而我低估了？

**Q2（维度遗漏）** 针对**中文网文长篇**（仙侠/都市/悬疑等），我列的实体与状态维度有哪些关键遗漏？例如：金手指/系统、打脸节奏与装逼打脸节拍、换地图（场景跃迁）、配角退场与登场时机、读者预期管理、势力格局演化——这些该不该进 KG？

**Q3（架构）** "分层记忆 + 按需检索 + Token 预算"之外，有没有更成熟、更适合本场景的现成架构可参考（如 MemGPT 式分层记忆、GraphRAG、分层摘要树、 episodic memory）？在 SQLite + 单机 + 单模型的前提下，哪一个性价比最高？

**Q4（校验层）** 一致性校验怎么做才**有效且不昂贵**？规则校验 vs LLM 自校验 vs 混合？校验应在生成前（约束提示）还是生成后（检错重写）？"生成后检错→自动重写"的代价是否可接受？

**Q5（语料蒸馏）** 如何设计蒸馏 prompt，才能产出**可注入的结构化档案**而不是"文风细腻、节奏明快"这类空话？如何**量化验证**蒸馏质量（比如 A/B 生成对比、人工盲评、可计算指标）？

**Q6（冲突裁决）** 增量抽取出现与既有事实矛盾时（境界倒退、死人复活、物品易主又出现），自动裁决（以最新为准 / 以置信度高为准）还是标记人工？各自的触发条件？

**Q7（砍项）** 我列的 30+ 项里，哪些是**过度设计**、可以推迟或砍掉？请给出你认为的 MVP 最小集合（能撑住 30 段不崩的最小记忆集）。

**Q8（预算）** 单段 3000 字生成，注入多少 token 合理？各层（事实/叙事/风格/前情/RAG）大致占比怎么分配才不挤占生成空间、又能保住一致性？

## 7. 硬约束（请在此前提下给建议）

- **单机本地运行**（Windows，12GB 显存 + 31GB 内存），无分布式
- **模型**：MiniMax M3.1-Flash-Preview（较快较便宜），token 成本敏感，不能每段都跑多次大模型
- **交互方式**：用户点一次 = 生成一段（默认 3000 字），SSE 流式返回，**首字延迟要低**
- **数据模型可改**：`KgNode.props` 是 JSON 列，可扩属性；`Project` 可加列（有 sqlite 增量迁移机制）
- **参考语料**：用户上传的小说全文，已切片入库（chunk 1200 字 / overlap 200），带 BM25 + embedding
- **已有生成链路**：段级摘要链 + 剧情圣经 + 7 条文风纪律，改动应尽量复用而非推翻
