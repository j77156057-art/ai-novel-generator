## 1. 关系归化

### 1.1 生效情况（样本 B，229 章）

`normalize_extraction` 覆盖的字段：`relations.from/to`、`events.subject/object/location`、`state_changes.character`、`entity_knowledge.character/knows`，外加 `entities.canonical_name`。

分母拆成两类：
- **层内写法**：原文值恰好等于称呼层里某个非恒等写法 → 按规则**应该**改写成 canon；没改写记为失效。
- **层外写法**：层里没有这个写法 → 归一天然管不到（覆盖缺口，不是失效）。

### 1.3 legacy 与 mixed 的差异

`_index()` 在 legacy 下返回空 dict（`canon_source._index()` 只在 cleaned/mixed 生效），因此：

- mixed：1,127 次改写。
- legacy：**0 次**。同样 1,127 个写法原样落库，`长公主` / `临安公主` / `怀庆公主` / `许二叔` / `许二郎` 会各自成为独立节点。
- 差异 = 1,127 条端点（394 条 relations + 360 条 events + 99 条 state_changes + 208 条 entity_knowledge + 372 个实体名）。

这是设计使然，不是 bug；但意味着「归一能力」只存在于 mixed，legacy 口径下这批数据必然分裂。

## 3. 方案（只写改哪里、影响多少、是否新增边）

### 3.1 归化

1. **地点/势力归一（收益最大）**：`events.location` 5,308 个值 / 849 种写法，0 次改写。同一处宅子被写成 许府 109 + 许家 55 + 许府前厅 23 + 许家新宅 22 + 许宅 18 + 许七安的小院 15 + 许府书房 15 + 许家祖宅 11 = 268 次 / 8 个节点。做法：在 `canon_layers.json` 增加 location 层（不复用人物层），或在 `normalize_extraction` 里对 location 走「后缀剥离 + 前缀归并」。
   - 影响：约 268 条 location 值折成 3–4 个节点；会**产生重复边**（同章同关系的两端点归一后撞车），需要在 persist 时去重，不会新增边。
2. **亲属称名映射**：`许七安的二叔/叔叔→许平志`、`许七安的堂弟→许新年`、`许七安的父亲→许平峰`，加上 `许二婶/许家婶婶/许七安的婶婶/许夫人→许二婶`。
   - 影响：8 条 + 20 条；同样只改名、不新增边，但会产生自环/重复边，需同步丢弃。
3. **自环丢弃**：`_persist_extraction` 落库前加 `if row["from"] == row["to"]: skip`（events 同理 `subject == object`）。
   - 影响：229 章里 4 条关系 + 1 条事件；不新增边，净减 5 条。
4. **白莲类约束**：`require_any` 在无上下文时默认拒绝折叠，安全但不生效。建议保留该默认，只在 `entity` 行（有 aliases 可作上下文）时传 context；否则把这类写法在统计里标「未决」而非「失效」。
5. **不要做的**：不要上模糊匹配。`魏公子`（15 次，禹州知府侄儿）就是反例——一旦按「魏」前缀或「公子」后缀模糊归并，会直接并进魏渊。
6. **许铃月→许玲月** 这类形近写法，走 `alias_rules.judge_alias` 的两章证据 + 人工确认，不进自动规则。

### 3.2 挂载

1. **v3 侧补上位节点门**（这是当前真正的漏洞）：v3 只折名、不筛节点，集合/上位剔除门在 v3 上等于不存在。做法：在 `_persist_extraction` 里对 `belongs_to` 加「个体性」判定——两端有一端是集合节点、且同章没有具体人名作为真正主体时，降级 `candidate`，不落正式边。
   - 影响：138 条里约 21 条错挂（8+5+3+5）会被拦；**不会新增边**，会减少约 21 条（占 138 的 15%）。
   - 风险：正确成员边（恒远→佛门、丽娜→蛊族）也会命中「集合端点」，必须要求「同章存在具体人名」才降级，否则会像 mixed 在样本 A 上那样丢掉 52.6% 的正确边。
2. **极性与类型互斥门**：`ally`/`enemy` 同一对实体同一章冲突时先按 `SAME_CHAPTER_CLASH` 处理（已有 `polarity_spans`）；`located_at` 要求一端是地点后缀、`owns` 要求一端是 item。
   - 影响：样本 B 里 11 条（极性 5 + 类型 6）；不新增边。
3. **否定/假设门**：原句含「也许我的假设是错误的」「根本不是」「若是」时不建边。
   - 影响：4 条（ch137 镇北王等）；不新增边。
4. **事件/抽象词不得作端点**：`events.subject/object` 落在「案/祭祖/体系/封印物」等词上时，不建人物边。
   - 影响：6 条；不新增边。

### 3.3 未解决 / 需要决策

- 集合节点到底「保留 + 加门」还是「剔除」：样本 A 显示剔除会丢 52.6% 正确边，样本 B 显示保留会带 21% 错边。建议保留 + 加门，但需要你确认是否接受「同一批边里既有正确成员边又有错挂」这种混合。
- 918 章全量验证目前做不了（无 v3 落库产物）。要跑全量，需要先落一份 918 章的 v3 抽取缓存，否则归化/挂载的所有率都只代表 229 章。

## 七、落地：集合/上位节点「保留 + 加门」（2026-11-10）

本节是代码改动与回归数据，不是新审计。四项待办（地点/势力归一、亲属称名映射、
落库丢 `from == to`、极性/类型互斥门）**本轮未动代码**。

### 7.1 改了什么

| 位置 | 改动 |
| --- | --- |
| `canon_source._nonchar_domain` | 集合节点（妖族/蛊族/南疆蛊族/万妖国/佛门/道门/阉党）由「`return None` 剔除」改为 `return "faction"` 保留 |
| `canon_source.mixed_nodes` | 集合/上位端点打 `upper_level: True`；`stats` 新增 `upper_level` 计数，日志行同步 |

| `canon_source.character_forms` / `gate_window` | 人名写法表（词表人物 + 调用方传入）、判定窗口（两端同句优先，退回整段） |
| `generated_extract._collect_edges` | 原著层链路：命中 `belongs_to`/`member_of`/`subordinate`/`superior` 且过门 → 进 `candidates`、不落正式边 |
| `batch_worker._persist_extraction` | v3 链路：同一门，命中则 `status='candidate'`；已有 active 行只升不降 |
| `models.KgRelation` + `db._migrate_sqlite_columns` | 新增 `status VARCHAR(16) NOT NULL DEFAULT 'active'`，老库补列即 active |
| `retrieval_v3` / `routers/kg_v3` / `kg/bible` | 三条读路径加 `status == 'active'`，候选边不进邻域、关系图、冲突扫描 |

门的条件写死、顺序不可省：① 关系 ∈ `{belongs_to, member_of, subordinate, superior}`；
② 至少一端 `is_collective`；③ 窗口里没有出现任何具体人名。第 ③ 条是**反向硬条件**——
有人名就放行，省掉它就会重演剔节点那轮丢掉 52.6% 正确成员边的结果。

命中只降候选，**不删边、不删节点**；v3 侧候选边仍在表里，只是读路径过滤。

### 7.2 词表变化（同一套 `load()`，只是口径不同）

| 口径 | 节点 | faction | 边 | upper_level |
| --- | --- | --- | --- | --- |
| mixed 改前 | 184 | 80 | 710 | — |
| mixed 改后 | **191（+7）** | **87（+7）** | **724（+14）** | 7 |
| legacy | 1595（不变） | 155（不变） | 1956（不变） | — |

legacy 本来就不过节点过滤，集合节点一直在词表里，所以前后一致；这次变化只发生在 mixed。

**仍不进 canon 的上位/拆名写法（逐条理由，不是一刀切）**

- `西域`：区域上位，无机构后缀，legacy 里 kind 被误标 faction；留着会和「西域佛门」抢同一指称。
- `魏渊阵营`：`阵营` 后缀 = 上位集合，指称就是魏渊的人马；留着会把魏渊拆成两个节点。
- `西域佛门` / `西方佛门` / `道门地宗` / `道门天宗` / `道门天地人三宗`：同一教派的拆名写法，
  教派本身已由 `佛门` / `道门` 承载；全收会让一个教派变成 4–5 个节点、成员边被摊薄
  （B 组 ch74「地书→道门地宗」就是被这种拆名带偏的例子）。
- 这些名字**仍然算集合端点**：`is_collective` 按名字形态判（含 `佛门` 子串、`道门` 前缀、
  `阵营` 后缀），所以 v3 抽到「道门地宗」时门照样生效，不会漏判。

### 7.3 回归（样本不换：A 组原著层 38 条、B 组 v3 138 条；mixed / legacy 各跑一次）

判定窗口说明：按批准原文的「同章」实现会在两组样本上 **0 命中**——每章都有人名
（离线预跑 G1：A 0/20、B 0/62）。所以实现取「同句优先、无同句退回整段」；
两端始终不同句的边在回归里按放行处理（整段必有人名，结果等价）。

**A 组（原著层，审了 38 条：集合端点 31 条，其中成员类 20 条进门；另 7 条端点是机构/共指，不在门的作用面）**

| 口径 | 进门样本 | 拦下 | 真错 / 误伤 | 门前错率 | 门后错率 |
| --- | --- | --- | --- | --- | --- |
| mixed | 9 | 1 | 0 / 1 | 1/9 = 11.1% [2.0, 43.5] | 1/8 = 12.5% [2.2, 47.1] |
| legacy | 20 | 2 | 0 / 2 | 7/20 = 35.0% [18.1, 56.7] | 7/18 = 38.9% [20.3, 61.4] |

**B 组（v3，审了 138 条：集合端点 86 条，其中成员类 64 条进门）**

| 口径 | 进门样本 | 拦下 | 真错 / 误伤 | 门前错率 | 门后错率 |
| --- | --- | --- | --- | --- | --- |
| mixed | 64 | 4 | 1 / 3 | 11/64 = 17.2% [9.9, 28.2] | 10/58 = 17.2% [9.6, 28.9] |
| legacy | 64 | 4 | 1 / 3 | 11/64 = 17.2% [9.9, 28.2] | 10/58 = 17.2% [9.6, 28.9] |

**误伤的正确成员边单独列（这是代价，不混进「拦下几条」）**

- A mixed：ch73 `地宗 → 道门`（子教派归属母教派，正确）
- A legacy：ch73 `地宗 → 道门`、ch40 `佛门 → 西域`（教派落在区域，属正确挂载）
- B mixed/legacy：ch73 `地宗 → 道门`、ch77 `地宗 → 道门`、ch77 `天人两宗 → 道门`

去重后误伤 3 个键：`地宗→道门`、`天人两宗→道门`、`佛门→西域`。
四次运行合计降级正确边 9 条次、错边 2 条次（同一键在 mixed/legacy 各计一次；
去重后 = 3 个正确键 / 1 个错误键）。

A 组 legacy 另有 3 条错边（`妖族→朝野`、`佛门→朝野` 等）在 918 章里**从未两端同句**，
按「无窗口即放行」通过——这不是门挡住了，而是门根本没有判定依据，需要如实计入「没挡住」。

**B 组 mixed 与 legacy 仍 0 差异的原因**：v3 链路的端点来自 LLM 输出，本来就不经过
节点过滤，两口径只差称呼层别名折叠；这 64 条的写法在两侧一致，所以门后数据相同。
门本身确实生效（4 条落 `status='candidate'`，见 `tests/test_kg_collection_gate.py`），
不再是「读了开关但没执行」。

### 7.4 结论（只减不增，别把降级当修好）

1. **门能生效，但收益为负**：四次运行共降级 3 个正确键（9 条次）和 1 个错误键（2 条次）。
   B 组 17.2% → 17.2%（挡 4/64 = 6.2% [2.5,15.0]，1 真错 3 误伤），
   A 组 legacy 35.0% → 38.9%（挡 2/20，0 真错 2 误伤，分母变小错误率反升）。
2. **B 组审计的 21 条错挂，门只挡住 1 条（4.8%）**。其余 20 条错边所在句子里都有人名
   （例如 ch151「礼部尚书帮助万妖国余孽…」——`礼部尚书` 本身就在人名表里），
   按「有人名就放行」的硬条件必然放行。
3. **误伤集中在「子教派→母教派」**：`地宗/天宗/天人两宗 → 道门` 是合法的集合归属，
   窗口里天然不会有人名。这是当前门规的结构性盲区，不是实现 bug。
4. **节点保留是对的、可复现**：mixed 边 710 → 724，集合端点边从 1 条恢复到 14 条，
   不再出现「剔节点连带丢掉正确成员边」。这部分是本轮唯一确定的净收益。
5. **候选降级 ≠ 修好**：v3 侧候选边只是不参与检索/图渲染/冲突扫描，错误内容仍在库里；
   若要真正修，需要「子教派→母教派」白名单或把门的判据从「句内有人名」改成
   「集合端点的另一端是个体实体」，这两项都超出本轮范围，未动。
