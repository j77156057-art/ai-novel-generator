## 二、判定口径（为什么 NULL 不能随手改成 5）

1. **`novel_id` 的语义**：`kg_entities.novel_id` 指「这条事实来自哪本书」，取值域是 `raw_novels.id`（本项目为 2/3/4/5/6）。NULL 表示项目级通配：不参与书过滤、也不算跨书冲突方。
2. **读侧怎么用 NULL**：`book_for_project()`（`backend/app/kg/book_scope.py`）按 `continuation_novel_id → active_novel_id → None` 取当前书；`resolve_entity_by_name()`（`backend/app/kg/entity_lookup.py#L54-L66`）在传了 `novel_id` 时按 **「这本书 + NULL 通配」** 收窄，且同名时**真书行优先于 NULL 行**。
3. **唯一键**：`(project_id, kind, canonical_name, COALESCE(novel_id, -1))`（见 `backend/migrations/2026-11-17-kg-entity-mention-novel-v1/apply_kg_book.py#L311-L312`）。NULL 是独立槽位，所以「NULL 行 + 书 5 行」可以同时存在，读侧不会报错，但列表类接口会重复计数。
4. **上一轮归书规则**：只看「名字在项目参考语料里的唯一命中」，唯一命中才归书（`apply_kg_book.py#L192-L203`）。这轮 22 条的成因分布（取自快照 `snapshots/kg_book_20261111-013854.json`）是：

| 上一轮给的原因 | 条数 |
|---|---|
| 语料里没有这个名字 | 7 |
| 只命中非参考语料 [5,6] | 6 |
| 只命中非参考语料 [6] | 3 |
| 只命中非参考语料 [2,3,4,5,6] | 3 |
| 命中多本参考语料 [5,6] | 2 |
| 只命中非参考语料 [2,5,6] | 1 |
| 合计 | 22 |

5. **本轮的判定原则**（按用户既有裁决「宁可漏也不并错」）：
   - 名字在书本语料里出现过，**不足以**证明这条实体属于那本书（`老李` 就是这么并错的，见 §六）；
   - 必须是「非通用称谓的具体名物」+「项目内确凿证据（组表槽位 / 章号区间 / 提及）」双满足才归书；
   - 通用名词、占位名、普通词一律留在 NULL；
   - 证据不足就进 C 类，不硬给结论。

## 五、三类结论

### A. 明确该归某本书：2 条，都归书 5（大奉打更人）

**#23 玉扳指 → 5。** 证据句（ch190）：*「紫阳居士略一沉思，取下大拇指戴着的玉扳指……『宁宴，这枚玉扳指你收好，本官佩戴多年，以浩然正气温养，可辟邪。』」* 三个独立证据同向：①别名「这枚玉扳指」只在这一句出现；②`first_chapter=190 / last_chapter=203` 是两个真实命中章；③`kg_item_group` 的同名组（id=22）已经 `novel_id=5`。书 6 的唯一命中（ch290「一杯翠玉扳指」）是错字且指另一物，不构成竞争。

**#36 锦囊 → 5。** 首末章 152/227 均为真实命中，ch152 即大奉具体剧情（*「打开一只锦囊，将断手收入其中……锦囊上绣着一只白色的动物，形状似狐」*）。书 6 的唯一命中是成语「锦囊妙计」（ch104），红楼梦/豆棚闲话各 1–2 处是泛指。组表同名组（id=34）已归 5。
之所以只给「中」：锦囊本身是通用器物名，不是专名；它的归属成立依赖章号区间与组表槽位，而不是名字的唯一性。若走最保守路线，可先只归 #23，把 #36 留到有持有段证据后再归。

### B. 明确该保持 NULL：19 条

- **B1 通用名词（13 条）**：#50 出租屋、#51 公司、#52 会议室、#53 办公室、#54 停车场、#56 文件、#57 策划书、#58 笔、#59 咖啡、#60 手机、#61 电脑、#62 邮件、#69 房间。
  理由不是「漏填」，而是它们**本来就没有唯一指称**：`kg_item_group` 里已经把同一性质的名字（`神剑`、`长刀`、`刀`、`法器`、`法宝`）显式登记为 `generic` 且 `novel_id=NULL`，说明系统对「通称/歧义名」的既定处置就是 NULL。这些名字在书 5/6 的语料里出现几百处，指的是不同故事里的不同物件，归书只会把「项目自己生成文里的那杯咖啡」错判成别人的道具。
  （#58 笔是单字名，#50/#52/#54/#57/#62/#69 甚至只由项目生成文支撑，连语料都不该作为依据。）

- **B2 生成文自造角色（4 条）**：#49 李浩、#63 小杨、#64 失踪者A、#65 失踪者B。
  它们的证据全部落在 `generations`（项目 1 的 2/3/5 段、项目 5 的 1/4 段），两本参考书语料里 0 命中。它们确实有实体意义，但归属对象是「本项目生成出来的正文」，而系统里没有「生成小说」这一行 `raw_novels` 记录，所以 NULL 是唯一合法值。**特别提醒：把它们归 5 会把「小杨」「失踪者A」变成大奉人物，直接污染续写约束。**

- **B3 伪实体（2 条）**：#67 李浩微、#68 成功。
  #67 是切词错误（gen3 原文「李浩微笑着说」），且带着单字脏别名「微」（该别名在五本书里命中 751 章/3393 处，全是「微微」「微臣」类噪声）；它还被错误地写进 #49 李浩的 `aliases`，形成跨角色别名污染。
  #68 是普通词误抽：项目 1 的摘要与生成文里「成功」全部是「成功与否」「他必须成功」；gen5 的「成功随声附和」是模型病句；该行 `mention_count=0`。
  这两行的正确处置是「先判为非实体，再决定删除或降级」，不是归书。

### C. 判不出：1 条

**#55 京城。** 缺三条信息，任一条补齐即可定案：
1. **来源**：它 `first_chapter/last_chapter` 为 NULL、`mention_count=0`、`kg_mentions` 里没有任何记录，项目 1 的 3 段生成文、`projects.outline/summary/premise` 里也搜不到「京城」。它和项目 1 其他实体同为 `2026-11-10 13:31:40` 批量产出，说明抽取器输出了一个**没有提及支撑**的地名。需要那一次抽取的原始响应或 prompt（是否来自共享词表/上一轮图谱）。
2. **语料证据方向相反**：书 5 命中 585 章/2287 处（大奉主场景就是京城），书 6 也命中 19 章/27 处，书 2 命中 2 章。两本参考书都有，按上一轮规则本来就该留 NULL。
3. **项目语义**：项目 1 是现代职场故事，不需要「京城」；把它归 5 等于凭空给一个现代故事塞进大奉的地理设定。

在拿到第 1 条之前，建议保持 NULL 并打 `no_evidence` 标记进人工队列——不要因为它「看起来像大奉地名」就归 5。

## 六、清理脚本设计（只设计，未执行）

### 6.1 作用域

只动 `kg_entities`（和 `kg_mentions.novel_id` 兜底同步）里的 `novel_id` 一列，**按 entity_id 白名单**：

```
ASSIGN = {23: 5, 36: 5}   # 玉扳指、锦囊
FORBIDDEN = 其余 20 条 id，一律跳过并输出「保留 NULL 及理由」
```

不做：不改 DDL、不重建表、不动 `models.py` / `engine.py` / `batch_worker.py`、不碰项目 1/5 之外的任何行、不动 `kg_nodes`/`kg_edges`。

### 6.2 流程

1. **全库快照**：`sqlite3.Connection.backup()` 到 `backend/backups/novel_dev-full-kg-nullscope-<ts>.db`，同时记录源库 sha256 与 `PRAGMA wal_checkpoint(TRUNCATE)` 结果。
2. **指纹校验**（不一致立即退出，不写库）：对白名单每条读出 `(id, project_id, kind, canonical_name, aliases, novel_id, first_chapter, last_chapter)`，与报告 §四 的指纹逐字段比对。
3. **反冲突校验**：若已存在 `(project_id=5, kind='item', canonical_name='玉扳指'|'锦囊', novel_id=5)` 行，退出——新唯一键 `COALESCE(novel_id,-1)` 允许 NULL 与 5 并存，贸然 UPDATE 会撞键或制造双行。
4. **组表一致性校验**：读 `backend/data/generated.db` 的 `kg_item_group`，要求同名组 `novel_id` 与目标书一致（这正是 `apply_kg_book.py#L291-L295` 的停止条件）；不一致退出。
5. **证据闸（防误归，双闸缺一不可）**：
   - **闸一 通用名词黑名单**：`文件/笔/咖啡/手机/电脑/公司/会议室/办公室/停车场/房间/出租屋/邮件/策划书/京城/失踪者A/失踪者B/成功/李浩微` 命中即拒绝归书，除非 `--override-generic --reason "<人工理由>"`。
   - **闸二 项目内实据**：必须满足至少一项——(a) `kg_item_group` 同名组已归目标书；(b) `kg_mentions` 有落在目标书章号区间内的证据；(c) `first_chapter/last_chapter` 全部落在目标书章号范围，且该名在目标书命中 ≥2 章。
   - **明令禁止**：仅凭「这个名字在目标书语料里出现过」就归书。§六.1 的 `老李`（#66）就是这条规则的反例：它被按名字命中归到 5，但它的 2 条提及全部来自项目 5 的生成文，语料里的「老李」是大奉 ch437 的养生堂老吏员——两个不同的人被合成一条。
6. **写入**：单事务，逐条
   `UPDATE kg_entities SET novel_id=?, updated_at=? WHERE id=? AND novel_id IS NULL`，`rowcount` 必须为 1，否则整体回滚；
   随后 `UPDATE kg_mentions SET novel_id=? WHERE entity_id=? AND (novel_id IS NULL OR novel_id<>?)`（当前为 0 行，作为幂等兜底）。
7. **后置校验**：`novel_id IS NOT NULL` 应为 44、`IS NULL` 应为 20；对未涉及的 62 行做 `md5(按 id 排序的行镜像)` 与 before 比对必须一致；未涉及行的 `updated_at` 不得变化。
8. **快照落盘**：`backend/migrations/<新目录>/snapshots/kg_nullscope_<ts>.json`，内容含：白名单与依据原文、每条 before/after 行镜像、未涉及行 md5、组表对照、执行人/时间。**不覆盖** 已有的 `kg_book_20261111-013854.json`。
9. **回滚**：`--rollback` 读快照，按 id 把 `novel_id` 改回 NULL，前置条件是「当前值 == 本次写入值 且 `updated_at` == 本次写入时间」，否则拒绝（防止覆盖并行任务对同行的后续修改）；或直接用 6.2.1 的整库快照恢复。
10. **默认 dry-run**：不带 `--apply` 时只打印 diff（受影响行、前后值、拒绝行及理由），由人确认后再执行。

### 6.3 怎么避免把「本来就该是通配」的行误归到书 5

- 白名单按 **entity_id** 写死，不按名字匹配——上一轮 42 条就是按名字匹配归的，误差全在边界名上；
- 通用名词黑名单前置拦截（B1 的 13 条全部在内）；
- 要求「项目内实据」，而不是「书本语料里出现过」（堵住 `老李` 型误并）；
- 组表与实体表必须同向，不制造新的层间矛盾；
- 对 B2（生成文自造角色）显式拒写，并在脚本输出里打印「归属对象应为生成文，不是书 5」；
- 对 B3（伪实体）拒写且单独列「建议删除/降级」清单，交人工，不在本脚本里删。

## 七、顺带发现（不在本次判定范围，仅登记）

1. **组表/实体表不一致**：`kg_item_group` 里 `玉扳指`(#22)、`锦囊`(#34) 都是 `novel_id=5`，但 `kg_entities` 的 #23/#36 是 NULL。两套分槽规则已经分叉，正是本次 A 类两条的来源。
2. **#66 `老李` 已被归到 5，但它唯一的 2 条提及来自项目 5 的生成文**（`kg_mentions` id 23/27，`novel_id` 已被跟随实体刷成 5）。大奉 ch437 的「老李」是养生堂老吏员，与本项目生成文里「小杨的上司老李」不是同一人。这是「按名字命中归书」的典型误并，建议另案复核（本轮不动）。
3. **#49 `李浩` 的别名 `李浩微` 是跨角色污染**：`李浩微` 是 #67 那条切词伪实体的规范名，被写进了李浩的别名，会让「李浩微的短信」这类句子解析到李浩身上。属写入口的别名归并问题，不是 novel_id 问题。
4. **单字别名**（#67 的「微」）在 `entity_lookup` 里会造成大面积误解析，建议后续统一禁止长度 <2 的别名进 `aliases`。

## 八、如果这 22 条一直保持 NULL，跨书场景下最坏会发生什么

不会崩库、不会报错，**坏在静默串书**：NULL 行在任意一本书的 scope 下都可见（`novel_id IS NULL OR novel_id = 当前书`），而「NULL 通配」又被排除在跨书冲突检测之外，所以没有任何告警。落到本项目最具体的一条链路：项目 5 同时引用了书 5 和书 6，当按书 6 生成时，`玉扳指` 仍会解析到那条 NULL 行——也就是大奉里「紫阳居士所赠、以浩然正气温养可辟邪」的那枚扳指，于是书 6 的现代豪门场景会被塞进一件仙侠法器的语义；`锦囊` 同理。其次是**双行陷阱**：一旦将来有人按书补了同名行，唯一键 `COALESCE(novel_id,-1)` 允许「NULL 行 + 书行」并存，单条查询会靠「真书行优先」侥幸正确，但实体列表、计数、导出会看到两条同名实体，问题只在聚合口径上暴露、很难回溯。再往远一层，`京城` 这种零证据行如果一直挂着 NULL，等某个项目真的挂上书 5，它会立刻以「大奉地名」的身份进入注入上下文，而库里没有任何一条日志能解释它是怎么来的。
